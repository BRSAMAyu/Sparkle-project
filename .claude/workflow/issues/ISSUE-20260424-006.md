## [Audit] 证据

Token 黑名单检查在 Redis 故障时的行为，Go 和 Python 层不一致：

**Go Gateway**（auth.go:305-309）：
```go
if cfg.RedisFailClosed {
    // Fail-Closed: reject token when Redis is unavailable
    return "", false, fmt.Errorf("token validation unavailable")
}
```
生产环境默认 `RedisFailClosed = true`（config.go:579），即 Redis 宕机时**所有请求被拒绝**。

**Python Backend**（security.py:151-163）：
```python
async def is_token_revoked(jti: str) -> bool:
    ...
    except Exception:
        # Fail open if Redis is unavailable to avoid blocking logins.
        return False
```
Python 侧**始终 fail-open**，Redis 宕机时已吊销的 token 仍可通过验证。

虽然正常架构下 Flutter 只与 Go Gateway 通信，但：
1. Python FastAPI 监听 8000 端口，若在部署配置中意外暴露，攻击者可绕过 Go 的 fail-closed
2. Go→Python 的 gRPC 内部调用中，Python `decode_token` 也会走 `is_token_revoked`，如果 Redis 在 Python 进程侧有问题但 Go 侧正常，吊销的 token 仍可被 Python 接受

**期望**：两层在 Redis 故障时应有一致的安全策略（至少 Python 在生产环境也应 fail-closed）。
**实际**：Go fail-closed，Python fail-open，策略不一致。

## [Audit] 建议修复方向

在 `is_token_revoked` 中引入 `settings` 级别的 fail-closed 开关，与 Go 的 `REDIS_FAIL_CLOSED` 对齐。生产环境 Python 也应 fail-closed。修改 security.py:162 的 except 分支，根据 settings 决定是 return False 还是 raise。
