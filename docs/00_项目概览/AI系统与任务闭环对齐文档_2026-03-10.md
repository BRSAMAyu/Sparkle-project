# Sparkle AI系统与任务闭环对齐文档

更新时间：2026-03-10
定位：团队内部对齐稿

## 1. 这份文档的结论

Sparkle 当前 AI 系统的真实主干，不是“某个大模型”或“某个 Agent 框架”，而是：

1. 自研编排系统作为生产主链路。
2. LangGraph 作为复杂规划、多专家协作、HITL 校验层。
3. 任务规划与执行不是一次性生成，而是带有快照、版本、校验、审查、反馈、重规划的闭环。
4. 用户画像不是单点标签，而是由长期偏好、目标、情节记忆、认知碎片、行为模式、知识掌握状态共同组成的上下文系统。

如果只用一句话概括 Sparkle 的护城河：

> Sparkle 的优势在于“业务可执行闭环 + 计划可审查可回流 + 画像可注入可持续更新”，而不是单纯的聊天能力。

## 2. 系统定位对齐

### 2.1 AI 主架构

仓库中的共识已经比较明确：

- 生产骨架仍然是自研系统，而不是全面迁移到 LangGraph。
- LangGraph 的职责是生成 `ExecutablePlan`、承载复杂多 Agent 工作流、做实验性验证。
- 所有关键业务写入、任务/计划落库、状态更新、配额/策略/审计，仍然由自研主链负责。

这点在以下材料中是一致的：

- `docs/architecture/AI_WORKFLOW_STRATEGY.md`
- `backend/app/orchestration/orchestrator.py`
- `backend/app/orchestration/lang_graph_planner.py`

### 2.2 通信与运行时分层

当前运行时分层可以统一理解为：

1. Flutter Mobile：承载交互、状态展示、任务/知识/计划等前端场景。
2. Go Gateway：承接 WebSocket/HTTP，请求鉴权、协议转换、用户上下文拉取、语义缓存、gRPC 转发。
3. Python AI Engine：负责编排、规划、工具执行、校验、审查、记忆、画像、认知分析。

这条链路在以下实现中已经贯通：

- `backend/gateway/internal/handler/chat_orchestrator.go`
- `backend/gateway/internal/handler/chat_orchestrator_chatflow.go`
- `backend/gateway/internal/agent/client.go`
- `backend/app/services/agent_grpc_service.py`

## 3. AI 系统当前真实能力地图

### 3.1 生产主链：自研 Orchestrator

`ChatOrchestrator` 已经不是简单对话调度器，而是生产级编排入口，整合了：

- Session 状态管理
- Request Validator
- ToolExecutor
- ContextPruner / TokenTracker
- UnifiedIntentRouter
- GroundingValidator
- LangGraphPlanner
- StateSnapshotManager
- VersionConflictService
- PlanReviewService
- ShadowPredictionService
- Observability / Circuit Breaker

这意味着 Sparkle 的 AI 主系统已经具备“从路由到执行再到校验”的完整骨架。

### 3.2 LangGraph 的定位

LangGraph 在当前系统中的定位非常清晰：

- 只负责规划，不直接执行工具。
- 输出统一结构 `ExecutablePlan`。
- 支持多 Agent 协作规划。
- 支持基于 `snapshot_id`、`context_version`、`plan_version` 的重规划。

这点很关键，因为它保证了 Sparkle 不会把核心业务控制权交给外部框架。

### 3.3 工具执行层

工具执行不是“LLM 想调什么就调什么”，而是经过：

1. 规划产出 `ExecutablePlan`
2. `GroundingValidator` 校验
3. `preflight_check`
4. `PlanReviewService` 审查
5. `ToolExecutor.execute_plan()` 按 DAG 层次执行
6. 失败时中断、补偿或重规划

这代表 Sparkle 的 AI 不是纯聊天，而是具备业务执行力的 Agent 系统。

## 4. 核心业务链路对齐：任务拆解规划

### 4.1 标准链路

结合设计文档和代码实现，当前“任务拆解规划”主链路可以对齐为：

1. 用户发起目标/问题。
2. Gateway 拉取用户即时上下文：
   - pending tasks
   - active plans
   - focus stats
   - recent progress
3. Python Orchestrator 结合会话上下文、用户上下文、计划上下文做路由。
4. 若判定进入复杂规划模式，先创建 `StateSnapshot`。
5. LangGraph 输出 `ExecutablePlan`。
6. 系统做版本冲突检测：
   - `snapshot_id`
   - `context_version`
   - `plan_version`
7. 通过 `GroundingValidator` 做业务与工具校验。
8. 通过 `PlanReviewService` 做规则审查 + LLM 审查。
9. 若高风险或不确定，进入 HITL。
10. 用户批准/拒绝/要求修改后，系统继续执行、停止或触发重规划。
11. 工具执行后产出任务、计划、知识或系统更新。
12. 执行结果和用户反馈再回流到后续规划。

### 4.2 这条链路为什么是 Sparkle 的核心竞争力

因为它不是“生成一个学习计划”这么简单，而是：

- 有用户当前负载感知
- 有历史计划冲突检测
- 有高风险动作拦截
- 有用户最终裁决权
- 有执行后结果回流
- 有后续重规划能力

这才是“任务拆解规划”从 demo 到产品的本质区别。

### 4.3 当前已经落地的闭环要点

已明确落地：

- `ExecutablePlan` 作为统一计划结构
- `StateSnapshot` 与 `context_version` 管理
- `VersionConflictService` 检查上下文漂移
- `PlanReviewService` 做自动审查 + 深度审查
- gRPC `SubmitPlanReview` 承接用户审批
- 批准后恢复执行，拒绝后停止，修改后重规划
- `ToolExecutor` 支持 DAG 分层执行

这说明“全闭环”并不是口号，而是已经进入主链的工程能力。

## 5. 用户画像系统对齐

### 5.1 我们说的“全方位用户画像”在当前系统里具体是什么

当前代码里，用户画像并不是一个单表或一个 JSON，而是多层组成：

1. 长期偏好记忆
   - `MemoryPreference`
   - 例如回答深度、学习时间偏好等
2. 目标记忆
   - `MemoryGoal`
3. 情节记忆
   - `EpisodicMemory`
4. 计划级上下文
   - `PlanContextBuilder`
   - 包含计划事实、约束、里程碑、任务摘要、反馈记录
5. 认知碎片
   - `CognitiveFragment`
6. 行为模式
   - `BehaviorPattern`
7. 知识掌握状态
   - `UserNodeStatus`
   - 包含 mastery / bkt_mastery
8. Persona 快照
   - `PersonaService.get_snapshot()`
9. 画像透明度接口
   - `/profile/transparent`

因此，“全方位用户画像”的准确表述应该是：

> Sparkle 已经形成“偏好 + 目标 + 记忆 + 行为模式 + 知识状态 + 计划上下文”的组合式画像系统。

### 5.2 已经进入主链路的画像能力

当前已经进入 AI 主链、而不是停留在文档层的画像能力包括：

- Gateway 在请求进入时注入用户即时业务上下文。
- `ContextPackBuilder` 会构建偏好、目标、episodic memory。
- 存在 `plan_context` 注入，且支持 enriched 模式。
- `PlanContextBuilder.build_enriched()` 会把认知状态、行为模式、偏好快照并入计划上下文。
- `UserIntentProfiler` 会基于历史意图分布做个性化路由加权。
- `PersonaService` 能产出带 `persona_version`、`audit_token` 的画像快照。

这意味着画像不是独立产品页，而是已经服务于路由、规划、提示词上下文与系统更新。

### 5.3 画像系统的真实成熟度判断

这里必须和团队对齐一个事实：

#### 已经成熟到可作为卖点的部分

- 偏好记忆持久化
- 目标/情节记忆管理
- 计划上下文注入
- 行为模式与认知碎片沉淀
- 画像透明度与可编辑性元数据
- Persona 快照和审计 token

#### 部分落地、仍需继续打磨的部分

- 任务执行行为到 Prism/画像的自动闭环覆盖率
- 画像变化如何系统性影响下游规划策略
- 预测命中率与反馈学习的线上闭环
- 画像驱动的 Prompt 策略是否形成稳定 AB 机制

#### 主要仍属于远期设计的部分

- 文档中大规模流式认知计算蓝图
- 更完整的贝叶斯/BKT/IRT 联动生产体系
- 更严格的数据分级、回滚、加密抹除与治理闭环

所以，“全方位画像”可以讲，但要讲成“已形成多层画像基座，并在主链开始发挥作用”，不要讲成“所有画像设计都已 fully operational”。

## 6. Sparkle 当前最大的优势，如何统一表述

基于仓库事实，我建议团队统一使用下面这套表述。

### 6.1 对外可讲版本

Sparkle 的 AI 不是单轮问答助手，而是一个围绕学习目标持续运转的闭环系统。它能结合任务、计划、知识状态和用户画像，为用户拆解任务、动态调整计划，并在执行后继续学习用户的状态变化。

### 6.2 对内战略版本

Sparkle 的核心优势有三层：

1. 业务闭环：从意图识别、任务拆解、计划生成、执行校验、用户审批到反馈重规划，链路完整。
2. 用户画像：不是只有偏好标签，而是任务、计划、认知、知识掌握、记忆系统共同组成的动态画像。
3. 工程控制力：核心执行权在自研系统，LangGraph 只是规划与实验层，不会反客为主。

### 6.3 最准确的一句话

> Sparkle 的核心竞争力是“以用户长期状态为中心的任务规划闭环”，而不是“会聊天的 AI”。

## 7. 当前主要差距与风险

为了后续优化不跑偏，需要明确当前差距。

### 7.1 文档愿景大于线上实装的区域

- Cognitive Nexus 文档描绘的是全系统神经中枢，但代码层面仍是分模块逐步接入。
- 贝叶斯画像、认知计算、PersonaTool 规范非常完整，但并非每个能力都已贯穿生产主链。
- “一处更新，处处感知”已经有雏形，但还没有做到所有模块的强一致联动。

### 7.2 闭环里最值得继续打磨的薄弱点

- 执行后反馈的结构化沉淀还需要更稳定地回写到画像和下一轮规划。
- 任务完成/放弃/中断这些行为信号，和规划策略调整之间还需要更强映射。
- 画像驱动的策略变化需要更可观测，否则容易变成“有画像、无收益”。

### 7.3 技术和产品上都要警惕的问题

- 不要把复杂度堆在 Agent 框架上，失去业务主导权。
- 不要把“画像很多”误等同于“策略有效”。
- 不要在没有强证据的情况下让画像直接改变用户体验，避免误判。

## 8. 接下来 AI 系统优化的建议主线

如果接下来要重点打磨 AI 系统，我建议按下面 4 条主线推进。

### 8.1 主线一：把“规划闭环”做得更硬

目标：让任务拆解规划真正成为稳定主链。

优先项：

- 强化 `ExecutablePlan -> Review -> Execute -> Feedback -> Replan` 的指标闭环
- 补齐计划执行后的结构化反馈归档
- 让用户修改意见直接映射成可学习的 planning delta

### 8.2 主线二：把“画像注入”从有数据变成有决策价值

目标：让画像真正影响任务生成和策略调整。

优先项：

- 明确哪些画像字段影响任务粒度、时长、难度、解释方式
- 对规划结果输出“为什么这样规划”的画像依据
- 建立画像字段到策略指令的稳定映射表

### 8.3 主线三：把“执行后学习”做成真闭环

目标：让系统每次执行后变得更懂用户。

优先项：

- 将完成、超时、放弃、中断、延期统一成行为事件
- 统一流入 `CognitiveFragment / BehaviorPattern / Memory`
- 在下一次任务规划中显式消费这些变化

### 8.4 主线四：把可观测性和评估体系补齐

目标：证明闭环真的有效。

核心指标建议统一为：

- 任务闭环完成率
- 计划调整延迟
- 用户采纳率
- 计划被拒绝率 / 被修改率
- 画像驱动规划命中率
- 下一步推荐命中率

## 9. 最终对齐口径

最后给团队一个可以直接复用的统一口径：

Sparkle 当前 AI 系统已经形成以自研编排为核心、LangGraph 为规划增强层、任务拆解规划为业务主线、用户画像为长期状态底座的智能闭环系统。我们真正的优势不是单点模型能力，而是“任务可拆解、计划可审查、执行可反馈、画像可积累、策略可迭代”的全链路产品能力。

接下来的优化重点，不是再堆更多 Agent 名词，而是把这条闭环打磨得更稳定、更可解释、更可量化。
