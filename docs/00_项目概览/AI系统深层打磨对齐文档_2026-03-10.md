## 2. 总体改进框架

### 2.1 改进理念

Sparkle 的 AI 系统已经具备完整的骨架（14 步编排、三层上下文注入、双层审查、反馈闭环基座）。深层打磨的核心目标不是"加新能力"，而是：

1. **让已有的能力更精准** — 上下文聚焦、反馈回路、证据质量
2. **让用户感受到差异** — 主动洞察、理解深度、适配可感知性
3. **让系统自己能进化** — 策略自校准、失败学习、Cohort 实验

### 2.2 改进阶段

| 阶段 | 主题 | 核心交付 |
|------|------|----------|
| **阶段一** | 上下文动态聚焦 | 意图感知权重、语义相关性门控、首句强调 |
| **阶段二** | 反馈回路收紧 | 会话内隐式反馈检测、即时适配、transition_hint |
| **阶段三** | UX 表达动态化 | 表达策略个性化、Next Actions 动态生成、阻塞状态温度 |
| **阶段四** | 感知智能 | 主动洞察、成长对比、周报、规划依据 |
| **深水区** | 稳定性与证据 | fail-closed、延迟监控、置信度衰减、cohort 分桶 |
| **自演进** | 系统自校正 | 映射规则进化、回滚学习、理解深度等级 |

## 3. 阶段一：上下文动态聚焦

### 3.1 问题诊断

当前 `build_system_prompt()` 把 user_context、plan_context、cognitive_prism 全部平铺注入。对于 LLM 来说，1500 token 的偏好信息和 500 token 的计划信息混在一起，没有"这次对话应该重点关注什么"的信号。

### 3.2 解决方案

#### 3.2.1 意图感知的上下文权重调节

在 `UnifiedIntentRouter` 分类出意图后，为每类上下文分配注意力权重：

| 意图类型 | plan_context | episodic_memory | cognitive_prism | task_summary |
|----------|--------------|-----------------|-----------------|--------------|
| 调整计划 | ×2.0 | ×0.5 | ×1.0 | ×1.5 |
| 情绪倾诉 | ×0.3 | ×1.5 | ×2.0 | ×0.2 |
| 任务查询 | ×1.5 | ×0.5 | ×0.5 | ×2.0 |
| 知识问答 | ×0.5 | ×1.0 | ×0.5 | ×0.3 |

**实现位置**：`backend/app/orchestration/prompts.py` — `build_system_prompt()`

#### 3.2.2 上下文相关性门控

在 `ContextPackBuilder.build()` 中，对 preferences/goals/episodic 不仅按 evidence_score 排序，还要和**当前用户消息**做语义相关性过滤：

- 使用 embedding 余弦相似度
- 只保留 top-K 相关项
- 可配置阈值（`CONTEXT_SEMANTIC_GATING_RULES`）

**实现位置**：`backend/app/core/context_pack.py` — 语义门控逻辑

#### 3.2.3 首句强调机制（Briefing）

在 system prompt 最前面加一段 50 token 以内的"本次对话关键上下文摘要"：

```
【本轮关键上下文】
- 当前计划：微积分第三章，进度 45%
- 最近反馈：2 次表示任务偏难
- 本周完成率：62%
```

**实现位置**：`backend/app/orchestration/prompts.py` — briefing section

### 3.3 配置项

```python
# settings.py
ENABLE_CONTEXT_SEMANTIC_GATING: bool = False
CONTEXT_SEMANTIC_GATING_RULES_JSON: str = ""

# 默认门控规则
DEFAULT_SEMANTIC_GATING_RULES = {
    "preferences": {"candidate_limit": 12, "top_k": 5, "threshold": 0.55},
    "goals": {"candidate_limit": 10, "top_k": 4, "threshold": 0.50},
    "episodic": {"candidate_limit": 12, "top_k": 4, "threshold": 0.52},
}
```

### 3.4 校准工具

**脚本位置**：`scripts/calibrate_context_semantic_gating.py`

**用法**：
```bash
python scripts/calibrate_context_semantic_gating.py ./dataset.json --output results.json
```

**输出**：最优 `candidate_limit`、`top_k`、`threshold` 参数组合（基于 F1 优化）

## 4. 阶段二：反馈回路收紧

### 4.1 问题诊断

当前反馈信号从 `task_feedback_service` → `preference_service` → `adaptive_replanner` 这条路径是通的，但有两个体验断点：

- 反馈效果不即时（要等下一次完整对话才能感知到变化）
- 没有**会话内微反馈**（用户说"太难了"时，系统没有即时调整）

### 4.2 解决方案

#### 4.2.1 会话内隐式反馈检测

在 orchestrator 的响应后处理阶段，分析用户的下一条消息是否包含隐式反馈信号：

| 信号类型 | 触发词示例 | 系统响应 |
|----------|-----------|----------|
| 否定 | "不对"、"太复杂"、"不是这个" | 重新理解意图 |
| 跳过 | 直接问新问题不回应前一个答案 | 标记前答未解决 |
| 追问 | "能再详细说说吗"、"继续" | 深化当前话题 |
| 满意 | "好的"、"明白了"、"谢谢" | 标记当前轮完成 |

**实现位置**：`backend/app/orchestration/session_feedback.py` — `detect_implicit_feedback()`

#### 4.2.2 即时适配（transition_hint）

当检测到负面信号时，在**当前轮**就调整 prompt 策略，并用自然语言过渡：

```python
_TRANSITION_HINT_POOLS = {
    "simplify": ("好，精简版：", "我先说最关键的："),
    "expand": ("我换个更展开的讲法：", "我按步骤展开说："),
    "mismatch": ("我按你刚才真正想问的来答：", "我先把方向校正一下："),
}
```

**Cohort B 增强**：更强的 transition hint
```python
stronger_hints = {
    "simplify": "好，我直接说最关键的：",
    "expand": "我按更完整的脉络展开说：",
    "mismatch": "我先对准你真正要问的点：",
}
```

**实现位置**：`backend/app/orchestration/session_feedback.py` + `orchestrator.py`

#### 4.2.3 多轮节奏感知

| 信号 | 检测条件 | 系统指导 |
|------|----------|----------|
| `patience_drop` | 消息长度递减（长→短→更短） | "用户正在失去耐心；主动收敛，先给结论" |
| `deepening_focus` | 消息长度递增（短→长→更长） | "用户正在主动深入；可以更展开，保持结构化" |
| `stalled_followup` | 连续 3 轮追问且关键词重叠 | "连续多轮追问，前面的回答没解决问题；换讲法或例子" |

**实现位置**：`backend/app/orchestration/session_feedback.py` — `analyze_conversation_rhythm()`

### 4.3 配置项

```python
# settings.py
ENABLE_SESSION_FEEDBACK_ADAPTATION: bool = False
```

## 5. 阶段三：UX 表达动态化

### 5.1 问题诊断

当前 `ux_envelope.py` 的 5 个 `PresentationProfile` 是静态模板。所有用户在同一 chat_mode 下看到的框架完全一样。

### 5.2 解决方案

#### 5.2.1 表达策略个性化

从 `llm_profile` 中的 `verbosity`、`ai_personality` 字段，动态调整 `companion_frame` 和 `next_actions_title` 的措辞风格：

| 用户类型 | companion_frame | next_actions 数量 |
|----------|-----------------|-------------------|
| 内向/简洁型 | 更简洁的 frame | 2-3 个建议项 |
| 外向/高互动型 | 更丰富的 frame | 4-5 个探索性建议 |

**实现位置**：`backend/app/orchestration/ux_envelope.py`

#### 5.2.2 对话阶段感知的 Next Actions

根据对话进展动态生成：

| 对话阶段 | Next Actions 类型 |
|----------|-------------------|
| 刚开始 | 探索性建议（"你想深入哪个方向？"） |
| 计划已生成 | 执行性建议（"开始第一步？"、"调整时间安排？"） |
| 任务完成后 | 反思性建议（"回顾一下这个过程？"） |

#### 5.2.3 错误/阻塞状态的温度管理

| 场景 | 处理方式 |
|------|----------|
| 用户第一次遇到阻塞 | 详细解释 + 引导 |
| 用户多次遇到同类阻塞 | 更简洁 + 直接给解决方案 |
| 用户情绪低落时遇到阻塞 | 更温和的措辞 |

## 6. 阶段四：感知智能

### 6.1 问题诊断

系统确实在学习用户（偏好记录、行为模式、认知碎片都在沉淀），但用户几乎感受不到这种学习。

### 6.2 解决方案

#### 6.2.1 主动洞察

**触发条件**（全部满足）：
- 场景打分 ≥ 0.55（`MIN_SCENARIO_SCORE`）
- 高频高置信行为模式（confidence ≥ 0.7, frequency ≥ 3）
- 72 小时冷却期（Redis key: `perceptible_insight:{user_id}:{scenario}:{pattern_id}`）
- 单 session 限制（Redis key: `perceptible_insight:session:{session_id}`）

**关键约束**：
- Snapshot-only 不触发 insight（必须有匹配的 behavior pattern）
- Cohort C 更保守（场景打分 +0.1 才触发）

**实现位置**：`backend/app/services/perceptible_intelligence_service.py`

#### 6.2.2 成长对比

**严格同域比较**：
- 知识点：同一 `node_id` 的 mastery 变化
- 任务时长：同一 `plan_id` 或归一化任务标题
- 计划进度：同一 `plan_id` 的完成率变化

**证据格式**：
```
"evidence": "同域依据：知识点「矩阵运算」，2 周前掌握度 45%，当前 68%"
```

**实现位置**：`backend/app/services/perceptible_intelligence_service.py` — `ProgressComparisonService`

#### 6.2.3 周报

**有意义变化优先**：
- 任务完成数变化
- 掌握度变化 ≥ 5%
- 计划进度变化 ≥ 10%
- 近期行为模式
- 进化更新记录

**跳过条件**：evidence_items < 2 时跳过，不 fallback 到任意活跃用户

**交付模式**：`delivery_mode: "deferred_inbox"`（生成但不推送，等用户下次打开时展示）

**画像命中率**：
```python
{
    "matched": 3,
    "total": 5,
    "hit_rate": 0.6,
    "summary": "本周画像驱动的规划建议命中率约为 60%。"
}
```

**实现位置**：`backend/app/services/perceptible_intelligence_service.py` — `WeeklyLearningReportService`

#### 6.2.4 规划依据

**5 维证据源**：

| 证据源 | 字段 | 标签 |
|--------|------|------|
| 完成率 | `task_summary.avg_completion_rate` | "最近执行完成率" |
| 执行时长 | `facts.avg_task_duration_minutes` | "近期执行时长与难度" |
| 反馈信号 | `recent_feedback` 中的 too_long/too_difficult 计数 | "最近反馈信号" |
| 进度快照 | `progress_snapshot.highlights` | "近期进度快照" |
| 计划负载 | `active_plans` 数量 | "当前计划负载" |

**confidence_tier 分级**：

| tier | 含义 | 权重 |
|------|------|------|
| `explicit` | 用户主动提交的结构化反馈 | 1.0 |
| `implicit` | 隐式会话反馈 | 0.8 |
| `inferred` | 系统推断 | 0.6 |
| `weak` | 低命中率规则（3 周命中率 < 40%） | 0.3 |

**实现位置**：`backend/app/orchestration/plan_review_service.py` — `_build_reasoning_payload()`

### 6.3 首次"懂你"时刻

**触发条件**（全部满足）：
- ≥5 次完整任务反馈
- ≥2 个 confidence ≥ 0.7 的行为模式
- ≥1 个可对比的同域进展

**一次性保证**：Redis flag `first_perceptible_moment_sent:{user_id}`

**Cohort B 特殊文案**：
```
"我现在第一次能很明确地说：我真的开始懂你了"
```

**实现位置**：`backend/app/services/perceptible_intelligence_service.py` — `maybe_upgrade_to_first_moment()`

## 7. 深水区：稳定性与证据质量

### 7.1 稳定性保障

#### 7.1.1 Redis Fail-Closed

| 场景 | 行为 | 指标 |
|------|------|------|
| Redis 不可用时主动洞察 | return None，不发送 | `PERCEPTIBLE_INSIGHT_SKIPPED_TOTAL{reason="redis_unavailable"}` |
| Redis 不可用时周报 | return False，阻止发送 | `WEEKLY_LEARNING_REPORT_SKIPPED_TOTAL{reason="redis_unavailable"}` |

**实现位置**：`backend/app/services/perceptible_intelligence_service.py`

#### 7.1.2 LLM 审查超时降级

**3 层策略**：
1. 首次调用 LLM 审查
2. 超时后指数退避重试（最多 2 次）
3. 全部失败后降级为规则审查

**降级结果**：
- Safe/只读计划：自动批准
- 高风险计划：需要确认
- `reasoning_source: "llm_fallback"`

**实现位置**：`backend/app/orchestration/plan_review_service.py`

#### 7.1.3 延迟监控

```python
PHASE4_OPERATION_DURATION_SECONDS.labels(operation="...").observe(duration)
```

**监控操作**：
- `build_best_comparison`
- `maybe_enqueue_session_insight`
- `build_weekly_report`

**告警阈值**：P99 > 200ms 需要优化

**实现位置**：`backend/app/core/business_metrics.py`

### 7.2 证据质量

#### 7.2.1 行为模式置信度衰减

**规则**：
- 超过 14 天没有新证据支撑的 pattern，confidence 按周衰减 10%
- confidence 低于 0.3 时，自动 archive
- 已 archive 的 pattern 不再参与约束生成

**实现位置**：`backend/app/services/analytics/behavior_pattern_decay_service.py`

#### 7.2.2 画像膨胀治理

**消费追踪**：
- `MemoryPreference` / `MemoryGoal` / `EpisodicMemory` 新增 `last_consumed_at` 字段
- 每次被 ContextPackBuilder 选中注入 prompt 时更新

**治理规则**：
- 60 天未消费：importance_score × 0.9
- 90 天未消费 + importance < 0.3：自动归档（`archived_at`）

**DB 迁移**：`backend/alembic/versions/a8c2f4d9b1e7_add_memory_consumption_tracking.py`

**实现位置**：`backend/app/services/memory_jobs.py`

## 8. 深水区：Prompt 策略收敛

### 8.1 问题诊断

当上下文聚焦、会话反馈、双核路由、认知棱镜同时激活时，prompt 里可能有 4-5 段"指令性"内容在竞争 LLM 的注意力。

### 8.2 解决方案

#### 8.2.1 指令优先级标注

| 优先级 | 含义 | 适用 section |
|--------|------|--------------|
| **L1 强制** | 必须遵守 | 当前意图、会话内反馈 |
| **L2 引导** | 优先参考 | dual_core、计划上下文 |
| **L3 背景** | 作为参考 | user_context、对话历史、task awareness |

**实现位置**：`backend/app/orchestration/prompts.py` — 优先级标记

#### 8.2.2 冲突预检

当 session_feedback 要求"精简"但 cognitive_prism 要求"深入解释"时：

1. 检测到冲突
2. 低优先级段落自动软化：`[冲突预检] 仅在不与高优先级指令冲突时参考`
3. 高优先级指令保持不变

**实现位置**：`backend/app/orchestration/prompts.py` — `_soften_section()`

#### 8.2.3 超预算裁剪

**预算限制**：`PROMPT_SECTION_SOFT_LIMIT_TOKENS = 2800`

**裁剪顺序**：
1. 先裁 L3（压到 60%）
2. 再裁 L2（压到 60%）
3. L1 和 briefing 永不裁剪

**实现位置**：`backend/app/orchestration/prompts.py` — `_apply_prompt_budget()`

## 9. 深水区：画像因果与回滚

### 9.1 画像→策略映射表

**生成逻辑**：

| 信号 | → 约束 | → 建议值 | evidence_tier |
|------|--------|----------|---------------|
| `avg_completion_rate < 60%` | `task_difficulty` | `lower` | inferred |
| `avg_task_duration > 1.5x session_length` | `task_granularity` | `finer` | inferred |
| `2+ "too_difficult" feedbacks` | `task_difficulty` | `lower` | implicit |
| `2+ "too_long" feedbacks` | `session_length` | `shorter` | implicit |
| `≥3 active plans` | `concurrency` | `lower` | inferred |
| `2+ "just_right" + 70%+ completion` | `load_shape` | `preserve` | explicit |

**限制**：最多返回 5 条映射

**实现位置**：`backend/app/orchestration/plan_review_service.py` — `_build_persona_strategy_mapping()`

### 9.2 对齐评分

**计算公式**：
```
alignment_score = achieved_weight / total_weight
```

**权重**：按 confidence_tier 加权（explicit 1.0 / implicit 0.8 / inferred 0.6 / weak 0.3）

**约束匹配**：

| 约束 | 满足条件 |
|------|----------|
| `task_difficulty:lower` | tool_count ≤ 5 && risk_count ≤ 1 |
| `task_granularity:finer` | total_steps ≥ 3 || tool_count ≥ 3 |
| `session_length:shorter` | avg_timeout ≤ 15s 或 finer_granularity |
| `concurrency:lower` | 非 parallel 模式 + max_parallel ≤ 1 |
| `load_shape:preserve` | low_scope + confidence ≥ 0.6 |

**评分区间**：
- ≥ 0.8："这次计划和你最近的执行画像基本一致"
- ≥ 0.55："这次计划和你的近期画像大体一致"
- < 0.55：追加警告注释

**实现位置**：`backend/app/orchestration/plan_review_service.py` — `_score_plan_alignment()`

### 9.3 适配回滚

**快照机制**：
- 最多保留 3 版自适应快照（`SNAPSHOT_HISTORY_LIMIT = 3`）
- 存储位置：`plan_state.facts["adaptive_meta"]["adjustment_snapshots"]`

**负反馈检测**：
```python
NEGATIVE_FEEDBACK_CATEGORIES = {"too_difficult", "too_long", "unclear", "irrelevant"}
```

**回滚触发**：连续 2 次负反馈（`negative_streak >= 2`）

**回滚操作**：
1. 恢复前一快照的 `adaptive_adjustments`
2. 更新 `active_snapshot_id`
3. 重置 streak 为 0
4. 打 metric：`ADAPTIVE_ROLLBACK_TOTAL.inc()`

**实现位置**：`backend/app/orchestration/adaptive_replanner.py`

### 9.4 回滚后策略学习

**failed_adjustments 记录**：
```python
{
    "constraint_key": "task_difficulty",
    "direction": "lower",
    "previous_value": 1.0,
    "rolled_back_value": 0.8,
    "reason": "too_difficult",
    "rolled_back_at": "2026-03-10T..."
}
```

**跳过逻辑**：
- 新调整与 failed_adjustments 中某条同 constraint_key + 同 direction
- 跳过该调整
- 打 metric：`ADAPTIVE_ADJUSTMENT_SKIPPED_TOTAL.inc()`

**实现位置**：`backend/app/orchestration/adaptive_replanner.py` — `_matches_failed_adjustment()`

## 10. 深水区：Cohort 实验

### 10.1 分桶策略

**分桶算法**：
```python
bucket = int(hashlib.sha256(user_id.encode("utf-8")).hexdigest(), 16) % 3
cohort = ("A", "B", "C")[bucket]
```

**保证**：同一 user_id 永远分到同一个 cohort

### 10.2 Cohort 差异

| Cohort | 特性 |
|--------|------|
| **A (Baseline)** | 默认策略 |
| **B (Aggressive)** | 更强的 transition hint、更激进的 first_moment 文案 |
| **C (Conservative)** | 主动洞察更保守（场景打分 +0.1 才触发） |

### 10.3 评估脚本

**脚本位置**：`scripts/evaluate_perceptible_cohorts.py`

**评估指标**：

| 指标 | 权重 | 计算方式 |
|------|------|----------|
| 任务完成率 | 40% | completed_tasks / total_tasks |
| 反馈率 | 20% | feedbacks / sessions |
| 洞察采纳率 | 20% | adopted / sent (24h 内) |
| 会话留存 | 20% | current_sessions / previous_sessions |

**晋级条件**：
- 连续 2 期 `promotion_ready == True`
- 推荐同一个 cohort
- margin ≥ 0.05

**实现位置**：`backend/app/services/self_evolution_service.py` — `CohortPromotionService`

## 11. 自演进：理解深度等级

### 11.1 等级定义

| 等级 | 名称 | 晋级条件 |
|------|------|----------|
| **L1** | 基础偏好 | 活跃偏好项 ≥ 3 |
| **L2** | 行为模式 | 高置信度行为模式 ≥ 2（confidence ≥ 0.7） |
| **L3** | 执行预测 | alignment_score 连续 3 次 ≥ 0.7 |
| **L4** | 洞察采纳 | 洞察采纳率 ≥ 50% |
| **L5** | 策略共振 | 策略共振率 ≥ 60%（校准后画像命中率） |

### 11.2 提示规则

**只升不降**：
- 升级时：自然嵌入对话提示
- 降级时：不提醒，不打扰

**自然嵌入**：
```
[L2 引导] 仅当本轮表达自然且不打断当前任务时，用一句话轻带过，不要像系统通知。
"如果自然，可以顺带一句提到：我现在不只记住你的偏好，也开始识别你的行为模式了。"
```

**实现位置**：`backend/app/services/self_evolution_service.py` — `UnderstandingDepthService`

## 12. 自演进：策略自校准

### 12.1 映射规则进化

**3 周命中率追踪**：
- 每周记录每条规则的 hit/miss
- 存储位置：Redis `strategy-calibration:{user_id}:{week_bucket}`

**自动降级**：
- 连续 3 周命中率 < 40%
- confidence_tier 降为 `weak`
- alignment_score 权重降为 0.3
- reasoning_details 中标注"此建议近期命中率较低，仅供参考"

## 17. 上线建议

### 17.1 上线顺序

1. **阶段一 + 阶段二**：先开启上下文聚焦和反馈适配，建立基础体验
2. **阶段三**：开启自适应表达，提升个性化感知
3. **阶段四**：开启感知智能，让用户感受到"系统在懂我"
4. **自演进**：数据积累 2 周后开启，让系统开始自我优化

### 17.2 灰度策略

- 使用 Cohort A/B/C 分桶
- A 组：对照组（旧策略）
- B 组：实验组（新策略激进版）
- C 组：实验组（新策略保守版）
- 2 周后评估，决定默认策略

### 17.3 监控重点

| 指标 | 关注点 | 告警阈值 |
|------|--------|----------|
| `PHASE4_OPERATION_DURATION_SECONDS` P99 | 主链路延迟 | > 200ms |
| `ADAPTIVE_ROLLBACK_TOTAL` 增长率 | 适配策略问题 | 日增长 > 10 |
| `PERCEPTIBLE_INSIGHT_SKIPPED_TOTAL{reason="redis_unavailable"}` | 基础设施问题 | > 0 |
| `alignment_score` P50 | 画像有效性 | 持续 < 0.5 |
