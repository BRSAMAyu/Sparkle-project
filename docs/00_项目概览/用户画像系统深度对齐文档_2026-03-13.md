# Sparkle 用户画像系统深度对齐文档

更新时间：2026-03-13  
定位：面向“深入改造和完善用户画像系统”的内部对齐稿

## 1. 结论先行

Sparkle 当前的“用户画像系统”不是单一表、单一接口、也不是某个单独的 AI Persona 模块，而是一个已经部分落地、部分并行演进中的组合式系统。

它至少由以下六层共同组成：

1. **显式偏好层**：`user_preferences_center` + `PreferenceService` + `PersonalizationEngine`
2. **长期记忆层**：`MemoryPreference` / `MemoryGoal` / `EpisodicMemory`
3. **认知行为层**：`CognitiveFragment` / `BehaviorPattern`
4. **知识状态层**：`UserNodeStatus`（掌握度、BKT）
5. **透明画像层**：`/profile/transparent` 将 L1/L2/L3 画像拼装给前端
6. **AI 注入层**：Gateway 上下文、`UserService.get_context()`、`ContextOrchestrator`、`ContextPackBuilder`、`ChatOrchestrator`

如果只用一句话定义它现在的真实形态：

> Sparkle 已经拥有一个“偏好中心驱动、记忆与认知并存、知识状态参与、透明展示可解释、并开始服务 AI 主链路”的多层画像基座。

同时也必须明确：

- **当前真正进入 AI 生产主链的核心画像能力，是偏好中心 + 用户上下文 + 部分认知上下文，不是全部 Persona 蓝图。**
- **当前前端看到的“我的画像”，是一个聚合视图，不等于唯一事实源。**
- **当前仓库中至少存在两套并行语义：**
  - 一套是已经较稳定的 `preference/personalization` 体系
  - 一套是更宏大的 `persona/cognitive nexus` 体系

后续如果要深改，首要任务不是继续加字段，而是先完成**画像域统一建模与主从边界重构**。

## 2. 我们现在说的“用户画像”到底包含什么

结合代码与文档，当前系统中的“用户画像”实际由以下对象共同构成。

### 2.1 显式偏好与推断偏好

这是当前最明确的生产级主线。

- 主表：`backend/app/models/user_preferences.py`
- 服务：`backend/app/services/personalization/preference_service.py`
- 引擎：`backend/app/services/personalization/engine.py`
- 上下文出口：`backend/app/services/user_service.py`

核心特点：

- `user_preferences_center` 被定义为 **Single Source of Truth**
- 分为 `explicit` 与 `inferred`
- 通过 `version` 管理缓存一致性
- 已明确影响 AI、Push、Task 三大模块策略

这部分是当前仓库里最接近“统一事实源”的画像组件。

### 2.2 长期记忆

- 模型：`backend/app/models/memory.py`
- 服务：`backend/app/services/memory_service.py`
- 透明画像读侧：`backend/app/api/v1/profile_transparency.py`
- LLM 上下文打包：`backend/app/core/context_pack.py`

这里至少包含：

- `MemoryPreference`
- `MemoryGoal`
- `EpisodicMemory`

其中 `MemoryPreference` 与 `Preference Center` 存在明显重叠：

- 两者都能表达用户偏好
- 两者都承接用户显式编辑
- 两者都参与下游个性化

这意味着当前系统已经出现了**“偏好中心”和“记忆偏好”双轨并存**。

### 2.3 认知碎片与行为模式

- 模型：`backend/app/models/cognitive.py`
- 服务：`backend/app/services/cognitive_service.py`
- 行为模式工具：`backend/app/tools/prism_tools.py`

这里的语义不是“我喜欢什么”，而是“我表现出怎样的认知与执行模式”。

例如：

- `CognitiveFragment`：一次想法、一次行为线索、一次被捕捉的状态片段
- `BehaviorPattern`：由多个碎片归纳出的长期行为定式

它们更像是 **认知画像 / 行为画像**，而不是传统偏好画像。

### 2.4 知识掌握状态

- 模型：`UserNodeStatus`
- 相关服务：Galaxy/Analytics/BKT 等多个服务
- 画像汇总使用：`PersonaService._collect_capabilities()`

这层的意义非常关键：

- 它不是用户“偏好”
- 也不是用户“自述”
- 而是用户在知识图谱上的真实学习状态

如果 Sparkle 的核心价值是“学习闭环”，那么这层必须被视为画像主干，而不是旁路数据。

### 2.5 Persona 快照

- 服务：`backend/app/services/persona_service.py`
- 审计模型：`backend/app/models/compliance.py` 中的 `PersonaSnapshot`

当前 Persona 快照做的事情是：

- 聚合 tags
- 聚合 capabilities
- 生成 `persona_version`
- 生成 `audit_token`
- 将快照持久化，用于审计/回滚/透明展示

它更像是**画像快照层**，而不是源数据层。

### 2.6 透明画像

- API：`backend/app/api/v1/profile_transparency.py`
- Flutter 读侧：`mobile/lib/features/user/data/repositories/user_repository.dart`
- 页面：`mobile/lib/features/user/presentation/screens/user_persona_screen.dart`

当前透明画像明确分三层：

- `layer_1`: 偏好、目标
- `layer_2`: persona tags、capabilities
- `layer_3`: patterns、fragments

这说明产品层面已经把画像理解为三层结构，而不是单一 profile。

## 3. 当前真实架构：不是一个画像系统，而是三个子系统叠加

从仓库现状看，用户画像并非一条单线，而是三套语义同时存在。

## 3.1 A 线：偏好中心与个性化引擎

这是当前**最稳、最明确进主链**的体系。

主文件：

- `backend/app/models/user_preferences.py`
- `backend/app/services/personalization/preference_service.py`
- `backend/app/services/personalization/engine.py`
- `backend/app/services/user_service.py`
- `docs/PREFERENCE_SYSTEM_ALIGNMENT_REPORT.md`

主要职责：

- 存储显式/推断偏好
- 作为 User Context 的标准偏好来源
- 映射为 LLM/Push/Task 的运行策略
- 提供版本号做缓存失效

这是现在最像“基石”的一层。

## 3.2 B 线：记忆与透明画像体系

主文件：

- `backend/app/services/memory_service.py`
- `backend/app/api/v1/profile_transparency.py`
- `backend/app/core/context_pack.py`

主要职责：

- 承接可编辑的偏好、目标与历史
- 提供用户可感知、可回滚、可修正的透明画像能力
- 作为 LTM/Context Pack 的输入

这条线在产品感知上很强，但在“唯一事实源”层面还没有完全统一。

## 3.3 C 线：认知画像与 Persona/Cognitive Nexus 体系

主文件：

- `backend/app/models/cognitive.py`
- `backend/app/services/cognitive_service.py`
- `backend/app/services/persona_service.py`
- `backend/app/core/context_manager.py`
- `docs/09_Cognitive_Nexus/*`

主要职责：

- 记录认知碎片
- 归纳行为模式
- 生成 Persona 快照
- 提供更强的审计、溯源、认知中枢设计

这条线代表 Sparkle 的长期护城河方向，但目前仍然是**部分落地、部分蓝图、部分侧链接入**。

## 4. 当前数据主从关系，应如何理解

如果我们从“真实生效”而不是“概念命名”出发，当前主从关系应当这样理解：

### 4.1 当前最接近主事实源的是偏好中心

原因：

- `PreferenceService` 有明确的 get/update 读写模型
- `UserService.get_context()` 明确优先读取它
- `PersonalizationEngine` 明确依赖它
- `ContextOrchestrator` 和 Gateway 版本机制能感知它的 `version`
- 相关对齐文档已经把它定义成 Single Source of Truth

结论：

> 在“用户偏好”这个子域里，`user_preferences_center` 是当前事实源。

### 4.2 当前透明画像并不是事实源，而是聚合视图

`/profile/transparent` 做的事情本质上是：

- 从 `MemoryService` 读取 L1
- 从 `PersonaService` 读取 L2
- 从 `CognitiveService` 读取 L3
- 再拼成给前端展示的结构

结论：

> 当前透明画像 API 是“读模型 / 聚合投影”，不是画像主存。

### 4.3 Persona 快照也不是事实源，而是快照层

`PersonaService.get_snapshot()` 聚合：

- `BehaviorPattern.pattern_name`
- `CognitiveFragment.tags`
- `UserNodeStatus` 的平均能力指标

然后落 `PersonaSnapshot`。

结论：

> `PersonaSnapshot` 是审计快照层，不是画像主写模型。

### 4.4 记忆偏好与偏好中心之间存在域重叠

这是当前最需要对齐的地方。

表现为：

- Onboarding 时同时写 `MemoryPreference` 与 `PreferenceService.update_explicit()`
- `/profile/preferences` 直接更新 `MemoryPreference`
- `UserService.get_context()` 优先读取 `Preference Center`
- 透明画像 L1 偏好又来自 `MemoryPreference`

结论：

> 当前系统在“偏好”这个子域上存在双写与双读语义，后续深改必须优先解决。

## 5. 用户画像如何进入 AI 主链路

这是最关键的问题，因为它直接决定“画像是不是护城河，而不是展示页”。

## 5.1 Gateway 注入用户业务上下文

Go Gateway 会构建用户上下文 JSON，并传给 Python AI Engine。

相关文件：

- `backend/gateway/internal/service/user_context.go`

当前包含：

- pending tasks
- active plans
- focus stats
- recent progress
- `prefs` 版本号

这层是“即时业务状态注入”，还不是完整画像，但它已经是 AI 主链路入口的一部分。

## 5.2 gRPC `UserProfile` 是轻量画像协议层

协议定义：

- `proto/agent_service.proto`

实现：

- `backend/app/services/agent_grpc_service.py`

当前 `UserProfile` 包含：

- nickname
- timezone
- language
- is_pro
- preferences
- extra_context

注意点：

- 这个 `UserProfile` 很轻
- 它主要承载偏好与基础信息
- 它还不足以表达完整认知画像

因此，gRPC 层里的 “GetUserProfile” 目前更接近 **基础用户个性化档案**，而不是完整画像协议。

## 5.3 `UserService.get_context()` 是 AI 侧常用画像入口

相关文件：

- `backend/app/services/user_service.py`

它会将：

- `Preference Center` 中的偏好
- push preference 派生出的 persona/timezone/daily_cap
- 基础用户信息

整理成 `UserContext`。

这说明：

> 当前 AI 主链里最稳定的画像入口是 `UserContext`，而不是 Persona 快照。

## 5.4 `PersonalizationEngine` 真正影响了 AI 行为

相关文件：

- `backend/app/services/personalization/engine.py`
- `backend/app/orchestration/orchestrator.py`
- `backend/app/orchestration/prompts.py`

已落地影响包括：

- `depth_preference` -> verbosity
- `curiosity_preference` -> exploration
- `feedback_style` -> tone
- `persona_type` -> persona prompt additions
- `preference_version` -> metadata / cache freshness

这是当前“画像影响 AI 输出”的最直接闭环。

## 5.5 `ContextOrchestrator` 在做更广义的认知上下文聚合

相关文件：

- `backend/app/core/context_manager.py`

它会聚合：

- knowledge stats
- recent mastery changes
- error summary
- active tasks
- focus stats
- preferences
- engagement metrics
- community context

这说明系统已经开始从“偏好个性化”走向“认知上下文个性化”。

但要注意：

- 这层聚合很重要
- 但它现在更像 **上下文快照编排器**
- 还不是整个画像域的统一领域模型

## 5.6 `ContextPackBuilder` 在做长期记忆注入

相关文件：

- `backend/app/core/context_pack.py`

这层会处理：

- 偏好
- goals
- episodic memory
- 排序
- token budget
- semantic gating

这意味着用户画像并不是只影响 prompt 头部，而是深入影响**LLM 上下文打包策略**。

## 6. 用户画像如何进入产品界面

## 6.1 前端展示的是“三层透明画像”

相关文件：

- `mobile/lib/features/user/data/repositories/user_repository.dart`
- `mobile/lib/features/user/presentation/providers/persona_view_provider.dart`
- `mobile/lib/features/user/presentation/screens/user_persona_screen.dart`

产品上当前已经明确采用三层展示：

- L1：偏好、目标

- L3：patterns、fragments

这套 UI 的价值很大，因为它把画像从“黑箱”变成了“用户可理解的可见系统”。

## 6.2 当前产品已具备初步可编辑、可回滚、可申诉能力

具体能力：

- 编辑偏好
- 回滚偏好版本
- 编辑目标
- 提交画像修正建议
- 查看系统更新
- 重新做 onboarding

这意味着产品方向上已经形成了一个非常重要的原则：

> 画像不是后台给用户打分，而是用户可协作修正的系统状态。

这正是护城河里非常重要的一环。

## 7. 当前仓库里最值得重视的设计优点

## 7.1 画像不是静态标签，而是动态系统状态

从 `Preference Center` 到 `MemoryPreference`、`CognitiveFragment`、`BehaviorPattern`、`UserNodeStatus`，系统已经明显把画像理解成“持续变化的长期状态”。

这是正确方向。

## 7.2 画像已经开始服务多个下游系统

当前已明确影响：

- AI 对话风格
- 推送策略
- 任务拆解与时长倾向
- 透明画像展示
- 系统更新与解释

这意味着画像已经有跨模块价值，而不是孤立中台。

## 7.3 系统已有版本、缓存、审计意识

已有能力包括：

- `Preference Center.version`
- Gateway 对 `prefs` 版本的感知
- `persona_version`
- `audit_token`
- `PersonaSnapshot`
- 画像相关 system updates

这为未来把画像做成“生产基石”打下了工程基础。

## 7.4 画像系统已经开始走向“可解释”

透明画像接口、编辑性元数据、修正建议、回滚能力，这些都非常关键。

很多系统只做到“知道用户”，Sparkle 已经开始做到“让用户知道系统如何理解自己”。

## 8. 当前最核心的问题与风险

这是这份文档最重要的一部分。

## 8.1 最大问题：画像域没有真正统一

当前至少有四个“画像入口”：

1. `user_preferences_center`
2. `MemoryPreference/Goal/EpisodicMemory`
3. `PersonaService` 快照
4. `ContextOrchestrator` 聚合上下文

问题不在于入口多，而在于：

- 各自语义边界没有被清晰定义
- 谁是主写模型、谁是投影、谁是快照，没有完全统一
- 下游不同模块读取的是不同层

这会导致后续改造成本成倍上升。

## 8.2 偏好域存在双轨并存

最典型例子：

- `Preference Center` 说自己是 Single Source of Truth
- 但 `MemoryPreference` 仍被前端透明画像和手动编辑 API 大量使用

如果不处理，未来会出现：

- AI 按 A 数据说话
- 用户在画像页改的是 B 数据
- 两边一段时间内不一致

这是高风险问题。

## 8.3 Persona 语义和 Preference 语义混在一起

当前系统里 “persona” 至少有三种含义：

1. `persona_type`：AI 角色风格，比如 coach/anime/mentor/friend
2. `PersonaService`：用户画像快照服务
3. 产品页里的 `UserPersonaScreen`：透明画像总页

这三个概念不是一回事，但命名上容易混淆。

后续深改时必须拆清：

- AI persona
- user persona
- persona snapshot

## 8.4 认知画像还没有完全成为策略中枢

当前 `BehaviorPattern` 和 `CognitiveFragment` 已经存在，但它们对下游策略的影响仍偏弱。

表现为：

- Prompt 中主要是“合适时调用 `get_user_behavior_patterns`”
- 认知模式更多影响展示与洞察，而不是稳定驱动 planner / executor
- 与 Task / Plan / Push 的联动还不够系统性

所以这部分现在更像“半接入”，不是“主调度核心”。

## 8.5 知识状态是护城河核心，但尚未被提升为画像主轴

`UserNodeStatus` 很强，它能表达：

- 掌握度
- BKT 概率
- 最近学习
- 知识结构位置

但当前它更多在 Galaxy/Analytics 体系中发挥作用，而不是被提升为“画像主骨架”。

如果 Sparkle 的定位是学习系统，这一点后续必须加强。

## 9. 如果我们要把画像系统做成真正基石，建议采用的统一模型

建议把“用户画像系统”明确拆成四层，而不是继续把所有东西都叫 profile/persona。

## 9.1 Layer A：Canonical Profile Core（主画像核心）

这是唯一的领域主模型，建议后续重点建设。

它应只包含真正稳定、跨模块、需全局一致的字段：

- user identity basics
- explicit preferences
- inferred preferences
- stable learning strategy traits
- preference/version metadata

它应该成为：

- AI
- Push
- Task
- Frontend settings

共同依赖的**唯一主画像核心**。

当前最接近它的是 `user_preferences_center + UserContext`。

## 9.2 Layer B：Memory & Intent Layer（长期记忆层）

包含：

- goals
- episodic memory
- editable preference history
- intent traces

这层不应与主画像核心抢“事实源”角色，而应服务：

- personalization recall
- plan continuity
- transparent history

## 9.3 Layer C：Cognitive & Behavioral Layer（认知行为层）

包含：

- cognitive fragments
- behavior patterns
- engagement metrics
- affective/behavioral tendencies

这层的定位应是：

- 洞察与干预
- 规划修正
- 风险识别
- 可解释反馈

而不是直接充当基础偏好源。

## 9.4 Layer D：Knowledge Mastery Layer（学习能力层）

包含：

- mastery
- BKT
- weak spots
- progress deltas
- knowledge graph position

这层是 Sparkle 与通用聊天产品最大的差异化来源，应该被提升为画像系统的核心组成层，而不是附属分析数据。

## 9.5 Snapshot / Projection 层要明确是“投影”

包括：

- `/profile/transparent`
- `PersonaSnapshot`
- 各类 dashboard summary
- AI 注入上下文快照

这些都应该被统一定义为：

> 面向展示、审计、检索和 prompt 注入的投影层，而不是领域主存。

## 10. 面向后续深改的推荐改造方向

## 10.1 第一优先级：统一“偏好”子域

目标：

- 明确 `user_preferences_center` 是主写模型
- `MemoryPreference` 从“事实源”退到“历史与透明记录”
- 或者反过来，但必须二选一

建议方向：

- 让所有显式偏好更新统一进入 `PreferenceService`
- 透明画像读层优先读 canonical profile，再附带历史版本
- `MemoryPreference` 只保留版本史、解释、证据、回滚能力

## 10.2 第二优先级：把知识状态正式纳入画像核心定义

建议：

- 在统一画像文档与接口中，明确 `Knowledge Mastery Layer` 是核心组成
- AI/Task/Plan 策略层默认可读取“薄弱点、最近掌握变化、当前知识阶段”
- 不再把这部分仅仅当作 Galaxy 私有数据

## 10.3 第三优先级：把认知行为层从展示能力升级为策略能力

建议：

- `BehaviorPattern` 不只用于展示卡片和工具查询
- 要能进入 task difficulty calibration、push timing、plan pacing、chat intervention
- 明确“哪些 pattern 会触发哪些策略”

即：

- 从 `insight` 升级到 `policy signal`

## 10.4 第四优先级：统一命名

建议尽快在团队内统一：

- `AI Persona`：AI 风格角色
- `User Profile Core`：用户主画像核心
- `Cognitive Profile`：认知行为画像
- `Persona Snapshot`：用户画像快照投影
- `Transparent Profile`：前端透明画像投影

否则随着功能继续增长，命名冲突会越来越严重。

## 10.5 第五优先级：做画像域事件协议

建议定义统一事件：

- `profile.preference.updated`
- `profile.goal.updated`
- `profile.cognitive_pattern.detected`
- `profile.mastery.updated`
- `profile.snapshot.refreshed`

这样才能真正做到：

> 一处更新，处处感知

这也是 `Cognitive Nexus` 真正落地的前提。

## 11. 我对当前成熟度的判断

为了避免团队在叙事上过度乐观，需要做一个现实判断。

## 11.1 已经成熟、可以作为对外差异化卖点的部分

- 偏好中心与个性化映射
- 透明画像三层展示
- 用户可编辑、可回滚、可修正
- 画像已进入 AI、Push、Task 的部分主链
- 画像快照与版本审计意识

## 11.2 已经形成骨架，但还需要工程性打磨的部分

- 认知行为层对策略的稳定驱动
- 知识状态进入统一画像主骨架
- 各画像层之间的主从边界
- 画像变化到下游效果的可观测性

## 11.3 仍偏设计蓝图或局部落地的部分

- Cognitive Nexus 全域中枢
- 更完整的 PersonaTool 生产协议化体系
- 更严格的法律冻结、加密抹除、DLQ 双人复核等全域合规流程
- 大规模流式认知计算中台

因此最准确的判断是：

> Sparkle 不是“画像系统还没做”，而是“已经做出了多层画像基座，但还没有把这些层真正统一成一个强主干架构”。

## 12. 建议团队统一采用的对外与对内表述

## 12.1 对内表述

Sparkle 当前的用户画像系统由偏好中心、长期记忆、认知行为、知识掌握和透明投影组成，已经开始服务 AI、任务与推送，但尚未完成统一领域建模。后续改造目标不是继续堆功能，而是先统一主画像核心、记忆层、认知层与知识层的边界和事件协议。

## 12.2 对外表述

Sparkle 不是简单根据用户点几个标签做个性化，而是结合用户的学习偏好、长期目标、行为模式和知识掌握状态，持续调整 AI 交互、学习任务和后续建议。

## 12.3 最准确的一句话

> Sparkle 的画像系统本质上是一个“围绕长期学习状态持续演化的多层用户模型”，而不是传统的静态用户标签页。

---

## 13. 建议作为下一阶段改造的决策原则

如果我们要围绕用户画像系统做深改，我建议所有设计决策都遵守下面五条原则：

1. **先统一主从关系，再扩展字段。**
2. **凡是跨模块共享且需要强一致的画像信息，都必须进入 canonical profile core。**
3. **凡是解释性、历史性、可回滚的信息，都优先做投影或历史层，不与主模型抢事实源。**
4. **知识状态必须被视为学习场景画像核心，而不是旁路 analytics。**
5. **认知行为层必须从“可展示洞察”升级为“可执行策略信号”，否则护城河价值释放不出来。**

---

## 14. 对齐后的系统认知

综合本次梳理，我认为我们现在应该把 Sparkle 的用户画像系统认知统一为：

它已经不是“用户偏好设置”功能，也不是“我的画像”页面，而是整个系统的长期状态层。  
但要让它真正成为基石和最大护城河，下一步的核心不是多做几个画像 feature，而是完成一次**画像域架构收敛**：

- 收敛主模型
- 收敛读写路径
- 收敛事件协议
- 收敛命名
- 收敛策略映射

只有这样，画像系统才能从“很有潜力的多层资产”升级为“真正驱动全应用的统一认知内核”。
