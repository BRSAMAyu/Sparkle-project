## 1. 为什么要切换到旅程式关单

当前最核心的问题不是“没有继续修”，而是：

- 缺陷表长期停留在 `PARTIAL`
- 修复工作持续发生，但缺少明确的“完成关闭动作”
- 页面级修补很多，端到端旅程式签收很少

因此，后续不再按“继续广泛 polishing”推进，而改为：

- 先定义真实用户旅程
- 再沿旅程走完整条链
- 只修旅程中真实阻塞点
- 修完立刻补证据
- 最后把对应缺陷从 `PARTIAL` 推进到 `PASS`

---

## 2. 旅程式关单的执行原则

### 2.1 只沿旅程修，不再散点修

每次执行只选一条旅程，禁止同时大面积打磨无关页面。

### 2.2 只有带证据的关闭才算关闭

每条旅程结束后，至少补以下证据中的两类：

- 模拟器截图或录屏
- 自动化测试输出
- acceptance 脚本回执
- 接口/日志摘要

### 2.3 只从缺陷表关闭，不口头关闭

任何“感觉已经好了”的问题，都不能直接算完成。  
必须回写到：

- [阶段0_真实缺陷总表_2026-03-23.md](/Users/brsama/code/GitHub/Sparkle-project/docs/04_测试与验收报告/阶段0_真实缺陷总表_2026-03-23.md)

## 4. 关单规则

每条旅程完成后，必须做三件事：

1. 把旅程覆盖到的缺陷逐条回写状态
2. 在对应缺陷项里补证据和结论
3. 明确哪些仍是 `PARTIAL`，哪些可以升级到 `PASS`

禁止：

- 旅程没走完就提前改成 `PASS`
- 只凭脚本通过就关闭纯前端体验缺陷
- 在没有用户可见证据时用“看起来没问题”结案

---

## 5. 推荐执行顺序

第一批：

1. `J1 First Chat -> Task`
2. `J2 Plan -> Calendar -> Focus`

第二批：

3. `J3 Share -> Adopt -> Land`

第三批：

4. `J4 Achievement & Expression`
5. `J5 Ambient Experience`

原因：

- `J1 / J2` 直接覆盖最多 P0 主链
- `J3` 负责跨系统闭环
- `J4 / J5` 负责完成感与体验层收口
