## 1. 这份文档解决什么问题

这份手册假设你在一台“刚拿到手、还没有任何项目运行环境”的服务器或开发机上，从零开始部署 Sparkle。

- 基础组件安装

- Python / Go / Flutter / Buf / SQLC / CocoaPods 等依赖安装
- 虚拟环境创建

- `pgvector` 与 `Apache AGE` 初始化
- API / Gateway / Agent / Worker / GLM Batch Worker 启动
- AI 供应商配置与主备策略
- Flutter App 联调启动
- 验收脚本
- 更新、回滚、故障排查

目标是: **照着这份文档执行，能从零跑通全部核心链路。**

## 5. 国内网络环境专项说明

如果你在中国大陆部署，这一节必须先看。

### 5.1 你最可能遇到的访问问题

- Docker Hub 拉镜像慢或失败
- GitHub / release 资源下载慢
- `pip install` 卡住
- `flutter pub get` 慢
- CocoaPods 拉取失败
- Firebase / Google 登录相关依赖首次拉取失败

### 5.2 推荐镜像与代理策略

#### Python / pip

项目内已提供:

- [docs/05_部署与运维/CHINA_MIRROR_SETUP.md](/Users/brsama/code/GitHub/Sparkle-project/docs/05_部署与运维/CHINA_MIRROR_SETUP.md)
- [scripts/setup_china_mirrors.sh](/Users/brsama/code/GitHub/Sparkle-project/scripts/setup_china_mirrors.sh)

快速配置:

```bash
bash scripts/setup_china_mirrors.sh
```

或手工创建 `~/.pip/pip.conf`:

```ini
[global]
index-url = https://mirrors.aliyun.com/pypi/simple/
trusted-host = mirrors.aliyun.com
```

备选:

- 清华: `https://pypi.tuna.tsinghua.edu.cn/simple`
- 中科大: `https://mirrors.ustc.edu.cn/pypi/web/simple`

#### Flutter / Dart

加入 shell 配置:

```bash
export PUB_HOSTED_URL="https://pub.flutter-io.cn"
export FLUTTER_STORAGE_BASE_URL="https://storage.flutter-io.cn"
```

#### Go

推荐设置:

```bash
go env -w GOPROXY=https://goproxy.cn,direct
go env -w GOSUMDB=sum.golang.google.cn
```

#### Docker

服务器上建议配置 `/etc/docker/daemon.json`:

```json
{
  "registry-mirrors": [
    "https://docker.1ms.run",
    "https://hub-mirror.c.163.com",
    "https://mirror.baidubce.com"
  ]
}
```

然后:

```bash
sudo systemctl daemon-reload
sudo systemctl restart docker
```

#### CocoaPods

本地 iOS 构建时，如 CDN 不稳定，可切换到清华镜像。

#### 无法完全镜像的服务

这些第一次下载依赖时，仍可能需要科学上网:

- Firebase SDK
- Google Sign-In
- 某些 Google 相关二进制

建议:

- 第一次拉依赖时开代理
- 拉完后依赖可被缓存

## 8. 环境变量配置原则

### 8.1 最容易踩坑的地方

本轮真实踩坑:

- `settings.py` 运行时会优先吃某些旧字段
- 根目录 `.env` 和 `backend/.env` 不一致时，最终实际生效的不一定是你以为的那个值
- 尤其是 `JWT_SECRET` / `SECRET_KEY`

### 8.2 强制要求

必须保证:

- `SECRET_KEY` 至少 32 位
- `JWT_SECRET` 至少 32 位
- `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` 一致
- `REDIS_PASSWORD` 一致
- `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD` 一致
- 所有 AI provider key 填在同一版配置中

### 8.3 推荐最小变量集合

至少要确认:

- `POSTGRES_USER`
- `POSTGRES_PASSWORD`
- `POSTGRES_DB`
- `REDIS_PASSWORD`
- `MINIO_ROOT_USER`
- `MINIO_ROOT_PASSWORD`
- `SECRET_KEY`
- `JWT_SECRET`
- `INTERNAL_API_KEY`
- `ENVIRONMENT`
- `DEBUG`
- 各 AI provider 的 API key / base url

### 8.4 生产环境强制项

- `DEBUG=false`
- `ENVIRONMENT=production`
- `BACKEND_CORS_ORIGINS` 不能用 `*`
- 禁止使用示例密钥

## 13. AI 配置与主备策略

这一节是核心中的核心。

### 13.1 当前策略要求

必须支持这些链路的主备切换:

- LLM
- Translation
- OCR / 文档清洗
- Embedding
- Rerank
- STT

### 13.2 已验证的主备链路

- 通用 LLM: tier 路由 + same-tier fallback
- Translation: `hunyuan -> siliconflow -> generic llm`
- OCR / 文档清洗: `zhipu -> siliconflow`
- Embedding: `dashscope -> siliconflow`
- Rerank: `dashscope -> siliconflow`
- STT: `zhipu -> xunfei`

### 13.3 智谱端点必须区分

真实踩坑结论:

- `GLM batch / coding` 不能走 OCR / STT 那套 endpoint

必须区分:

- `GLM batch`: `https://open.bigmodel.cn/api/coding/paas/v4`
- OCR / STT: `https://open.bigmodel.cn/api/paas/v4`

### 13.4 GLM Batch

当前已验证:

- 高峰期 `14:00-18:00` 并发固定压到 `2`
- 离峰允许自动上探
- 最大不超过 `6`
- 遇到 `429` 自动降并发
- 队列满载时可 spillover 到 standard 层模型

### 13.5 Worker 镜像依赖

本轮真实踩坑:

- `celery_glm_batch_worker` 因 `python-lzo` 缺系统库导致 build 失败

当前已修复:

- `backend/Dockerfile` 已补 `liblzo2-dev` / `liblzo2-2`

## 16. 从零开始部署时最容易踩的坑

### 16.1 Docker 空间不足

现象:

- 容器 build 失败
- 容器频繁异常
- PostgreSQL / Docker Desktop 崩溃

处理:

```bash
docker system prune -af --volumes
docker builder prune -af
docker system df
```

### 16.2 本机 8000 端口被旧进程污染

真实踩坑:

- 本地 `uvicorn` 占用了 `127.0.0.1:8000`
- Docker API 通过另一条地址暴露
- 导致 JWT 明明登录成功，但验证又失败

排查:

```bash
lsof -i :8000
ps -p <PID> -o command=
```

### 16.3 AGE 不是“安装了就完事”

真实踩坑:

- 扩展记录存在
- 但运行时 `age.so` 加载失败

正确做法:

- 使用定制数据库镜像
- 再执行 `init_age_extension.py`
- 再跑 `data_pipeline_health_check.py`

### 16.4 WebSocket 正常结束必须有终止事件

真实踩坑:

- Agent 已经完成
- 网关没发稳定的终止包
- 前端 / 验收脚本会一直等到连接关闭

当前已修复:

- Gateway 正常结束时显式发 `done + finish_reason`

### 16.5 `SECRET_KEY` 改了不代表运行时真的改了

真实踩坑:

- 根 `.env` 改了
- `backend/.env` 旧值还在
- 运行时仍然吃到了旧密钥

处理原则:

- 改密钥时永远同步检查根 `.env` 和 `backend/.env`

## 17. 标准更新流程

当代码有更新时，建议按这个顺序走:

```bash
git pull
make proto-gen
cd backend && .venv/bin/alembic upgrade head
make sync-db
docker compose build
docker compose up -d
docker exec sparkle_agent python3 scripts/init_age_extension.py
docker exec sparkle_agent python3 scripts/data_pipeline_health_check.py
cd backend && .venv/bin/python scripts/ai_expert_acceptance.py
```

说明:

- 改 proto -> `make proto-gen`
- 改 migration / schema -> `alembic upgrade head` + `make sync-db`
- 改 Dockerfile / compose / runtime -> `docker compose build && up -d`

## 18. 回滚策略

### 18.1 代码回滚

```bash
git checkout <last-known-good-tag>
docker compose build
docker compose up -d
```

### 18.2 数据回滚

不要在高风险 migration 后盲目 downgrade。  
优先策略:

1. 事前备份数据库
2. 失败后优先恢复备份
3. 仅在确认 migration 可逆时使用 Alembic downgrade

### 18.3 AI 配置回滚

- 保留上一版 provider 配置
- 修改 `.env`
- 重启 API / Agent / Worker / Gateway
- 跑 AI 验收脚本

## 19. 生产部署建议

### 19.1 必须项

- `DEBUG=false`
- `ENVIRONMENT=production`
- `JWT_SECRET` / `SECRET_KEY` 使用正式高强度密钥
- 使用 HTTPS / WSS
- 数据库不要暴露公网或至少限制白名单
- MinIO 不要使用默认密码
- Redis 不要裸奔

### 19.2 强烈建议

- 数据盘与系统盘分离
- PostgreSQL / MinIO 挂独立卷
- 建立 provider 429 / timeout 监控
- 建立 `/health` 与验收脚本的自动化巡检
- 定期执行无损清理和镜像治理

### 19.3 不建议

- 在生产机上混跑本地 `uvicorn` 与 compose API
- 手工乱改生成代码
- 直接跳过 proto / migration / sqlc 同步步骤
