# 成就体系现状对齐文档

更新时间：2026-03-10

## 1. 文档目的

本文档用于对齐 Sparkle 当前代码库中的“成就体系”真实现状，回答四个问题：

1. 当前成就体系到底由哪些模块组成。
2. 哪些能力已经形成端到端闭环。
3. 哪些设计只是“定义存在”，但尚未真正跑通。
4. 后续如果继续迭代，应该优先收敛哪些边界和约束。

本文基于仓库当前实现梳理，重点覆盖：

- 后端数据模型、成就引擎、REST API、事件消费链路
- 数据初始化与迁移
- 移动端仓库层、状态层、页面层、实时通知层
- 与任务、专注、知识星图、冲刺计划、商城/装备系统的交叉关系


## 2. 一句话结论

当前成就体系已经不是纯原型，而是一个“后端定义驱动 + 多入口事件触发 + 用户进度持久化 + 奖励发放 + WebSocket 通知 + 移动端展示”的半成品业务系统。

但它还没有达到“强一致、可稳定上线、可持续扩展”的状态，主要问题集中在：

- 种子数据与数据库约束不一致
- 成就定义与引擎支持矩阵不一致
- 后端返回结构与移动端消费结构不一致
- 成就奖励装备链路与商城装备链路双轨并存
- 分享卡、部分奖励类型、部分隐藏成就触发仍是占位
- 测试覆盖几乎为空白


## 3. 系统边界与职责归属

### 3.1 后端是唯一业务真源

成就体系的核心业务逻辑全部在 Python 后端：

- 数据模型：`backend/app/models/achievement.py`
- 业务引擎：`backend/app/services/achievement_engine.py`
- 事件消费者：`backend/app/services/achievement_event_consumer.py`
- REST API：`backend/app/api/v1/achievements.py`
- 初始化数据：`backend/app/data/achievement_seeds.py`
- 初始化脚本：`backend/app/data/populate_achievements.py`

这意味着：

- 成就是服务端判定，不是客户端本地判定。
- 客户端主要承担展示、交互、实时反馈消费。
- 触发入口分散，但判定核心集中在 `AchievementEngine.process_event()`。

### 3.2 Gateway 当前不是成就业务层

Go gateway 里可以看到成就相关表结构已经同步到 `schema.sql` / `models.go`，但没有发现专门的成就 handler/service 业务实现。当前成就能力主要还是通过 FastAPI 后端 API 直接对外提供。

结论：

- Gateway 当前更多是“数据库结构知情方”，不是成就系统业务编排方。
- 成就系统暂时仍属于 Python 后端主导能力。

### 3.3 移动端是展示层与消费层

移动端已经有完整成就模块：

- 实体模型：`mobile/lib/shared/entities/achievement_model.dart`
- Repository：`mobile/lib/features/achievement/data/repositories/achievement_repository.dart`
- Provider：`mobile/lib/features/achievement/presentation/providers/achievement_provider.dart`
- 页面：列表页、详情页、解锁弹窗
- WebSocket 实时消费：聊天流事件中消费 `achievement_unlock` / `achievement_milestone`

结论：

- UI/交互面已经比较完整。
- 但其能力上限受制于后端返回结构是否稳定、一致。


## 4. 当前领域模型

当前成就体系并不只包含“成就”本身，而是一个小型领域簇。

### 4.1 核心表

1. `achievements`
   存放成就定义，包括名称、描述、类型、稀有度、触发码、前置条件、视觉效果、奖励配置、排序、分类等。

2. `user_achievements`
   存放用户成就进度与解锁状态，包括：
   - `progress`
   - `progress_value`
   - `progress_target`
   - `unlocked_at`
   - `is_pinned`
   - `share_count`
   - `is_first_unlocker`

3. `user_streak_stats`
   存放连胜相关状态，包括当前连胜、最长连胜、保护卡等。

4. `spark_contracts`
   存放“星火契约”状态，本质上属于成就域的承诺玩法。

5. `galaxy_skins` / `user_galaxy_skins`
   存放通过成就或其他方式解锁的星系皮肤。

6. `user_titles`
   存放由成就解锁出的称号。

7. `study_buddies`
   预留了搭子关系表，但当前没有看到其在成就主链路中真正发挥作用。

### 4.2 定义模型的关键特征

`Achievement` 当前是强配置驱动模型，关键字段如下：

- `trigger_code`
  用于将业务事件映射到成就定义。

- `trigger_config`
  用于承载阈值参数，例如天数、数量、分钟数、领域等。

- `prerequisites`
  用于定义前置成就链。

- `visual_effect_type` / `visual_config`
  用于联动成就解锁时的视觉反馈和星图效果。

- `reward_config`
  用于定义奖励。

这意味着该系统理论上可扩展性较强，但前提是：

- `trigger_code` 必须与引擎支持矩阵一致
- `reward_config` 必须与奖励执行器一致
- 前端必须理解被返回的数据结构


## 5. 成就定义现状

### 5.1 当前种子规模

根据 `achievement_seeds.py`，当前初始化定义为：

- 成就总数：32
- 类别分布：
  - `streak`: 4
  - `exploration`: 6
  - `mastery`: 2
  - `study_time`: 4
  - `tasks`: 3
  - `hidden`: 5
  - `sprint`: 8
- 稀有度分布：
  - `common`: 10
  - `rare`: 9
  - `epic`: 9
  - `legendary`: 4

### 5.2 当前成就簇

现有定义大体分为 7 组：

1. 连胜成就
   例如 `streak_7`、`streak_30`、`streak_100`、`streak_365`

2. 知识探索成就
   例如 `first_light`、`nodes_10`、`nodes_50`、`nodes_100`、`nodes_500`

3. 领域精通成就
   例如 `math_master`、`physics_master`

4. 学习时长成就
   例如累计 1 小时、10 小时、100 小时等

5. 任务完成成就
   例如总完成任务数

6. 隐藏成就
   例如夜猫子、早起鸟、速通、大周末等

7. 冲刺成就
   例如首次冲刺、完美冲刺、连续冲刺、超前完成

### 5.3 当前奖励类型分布

种子里实际出现的奖励类型包括：

- `photon`
- `title`
- `freeze_charge`
- `galaxy_skin`
- `function`
- `ai_persona`
- `avatar_frame`

但引擎当前实际只处理以下 4 类：

- `title`
- `galaxy_skin`
- `freeze_charge`
- `photon`

这说明成就定义层的表达能力已经超前于执行层。


## 6. 事件触发与运行时闭环

### 6.1 核心判定入口

统一入口是：

- `AchievementEngine.process_event(user_id, event_type, **kwargs)`

其内部基本流程为：

1. 更新连胜统计
2. 找到与该事件相关的成就定义
3. 校验前置条件
4. 评估进度
5. 写入/更新 `user_achievements`
6. 达标则解锁成就
7. 发放奖励
8. 发送 WebSocket 通知
9. 发送系统更新事件
10. 触发连击与 25/50/75% 进度里程碑提示

### 6.2 当前真实触发入口

当前成就不是只靠一个入口触发，而是分散接入：

1. 任务完成
   `backend/app/api/v1/tasks.py`

2. 知识点点亮 / 掌握度变化
   `backend/app/services/galaxy/stats_service.py`
   `backend/app/services/galaxy_service.py`

3. 专注会话完成
   `backend/app/services/focus_service.py`

4. 冲刺计划归档
   `backend/app/api/v1/plans.py`

5. Redis EventBus 异步消费
   `backend/app/services/achievement_event_consumer.py`

这说明当前系统是“同步触发 + 异步补偿”并存：

- 一部分业务在请求链路内直接触发
- 一部分通过事件总线消费再触发

### 6.3 当前支持的运行时事件

引擎支持的运行时事件包括：

- `TASK_COMPLETED`
- `DAILY_CHECKIN`
- `NODE_UNLOCKED`
- `NODE_MASTERED`
- `STUDY_MINUTES_ACCUMULATED`
- `NIGHT_STUDY`
- `EARLY_BIRD`
- `WEEKEND_WARRIOR`
- `STREAK_MILESTONE`
- `CONTRACT_COMPLETED`
- `CONTRACT_FAILED`
- `MUTUAL_STUDY`
- `HIDDEN_TRIGGER`
- 冲刺类事件：
  - `SPRINT_STARTED`
  - `SPRINT_COMPLETED`
  - `SPRINT_ABANDONED`
  - `SPRINT_PERFECT`
  - `SPRINT_STREAK`
  - `SPRINT_AHEAD`

但“事件类型已声明”不等于“对应触发码已实现”。这一点是当前最大对齐风险之一。


## 7. 触发码对齐矩阵

### 7.1 已在引擎中实现的触发码

当前 `_evaluate_progress()` 已明确支持：

- `STREAK_DAYS`
- `TASKS_TOTAL`
- `NODES_UNLOCKED`
- `NODES_MASTERED`
- `SECTOR_MASTERY`
- `STUDY_MINUTES_TOTAL`
- `STUDY_MINUTES_SINGLE`
- `NIGHT_OWL_STUDY`
- `PERFECTIONIST`
- `SPRINTS_TOTAL`
- `SPRINT_PERFECT`
- `SPRINTS_STREAK`
- `SPRINT_AHEAD`

### 7.2 已出现在种子定义里，但引擎没有实现的触发码

以下触发码存在于 `achievement_seeds.py`，但在引擎里没有对应 `case`：

- `ALL_SECTORS_UNLOCKED`
- `EARLY_BIRD`
- `SPEED_UNLOCK`
- `WEEKEND_WARRIOR`

这意味着这些成就在当前代码下即使被定义了，也不会被正常解锁，除非：

- 有额外未纳入本次链路的特殊触发逻辑
- 或后续通过手工调用内部事件接口补触发

目前从代码看，更大概率是“定义已写，逻辑未补齐”。

### 7.3 结构性约束冲突

这是当前最严重的问题之一。

当前模型和有效迁移都把 `achievements.trigger_code` 设成唯一：

- 模型：`trigger_code = Column(..., unique=True)`
- 有效基线迁移也创建了唯一索引

但种子数据大量复用同一个 `trigger_code`：

- `STREAK_DAYS` 出现 4 次
- `NODES_UNLOCKED` 出现 5 次
- `SPRINTS_TOTAL` 出现 3 次

这与“一个事件码对应多档阈值成就”的设计天然冲突。

结论：

- 现有 schema 约束与种子定义不一致。
- 在空库首次播种场景下，极有可能在第二条相同 `trigger_code` 插入时失败。
- 仓库中虽然存在移除该唯一约束的迁移，但它位于 `versions_backup`，不是当前正式迁移链的一部分。


## 8. 奖励执行对齐矩阵

### 8.1 当前已真正执行的奖励

`_grant_rewards()` 目前支持：

1. `title`
   解锁 `user_titles`

2. `galaxy_skin`
   解锁 `user_galaxy_skins`

3. `freeze_charge`
   增加连胜保护卡

4. `photon`
   调用 PhotonService 发放光子积分

### 8.2 当前定义存在但不会执行的奖励

种子定义中出现但引擎未实现的奖励类型：

- `function`
- `ai_persona`
- `avatar_frame`

影响如下：

1. 定义层会让产品和设计误以为该能力已存在。
2. 用户即使解锁成就，也拿不到这些奖励。
3. 前端若展示奖励清单，会出现“可见但无兑现”的体验落差。

### 8.3 奖励资源引用不完整

种子中存在奖励皮肤：

- `legendary_anniversary`
- `sprint_legend_galaxy`

但当前皮肤种子中没有 `sprint_legend_galaxy`。

结果：

- 当对应冲刺成就解锁时，奖励发放逻辑会尝试写入 `user_galaxy_skins`
- 但如果数据库无对应 `galaxy_skins.id`，则存在外键或数据一致性风险


## 9. API 现状

### 9.1 已提供的对外接口

当前成就模块暴露的主要 API 包括：

- `GET /api/v1/achievements`
  获取成就列表

- `GET /api/v1/achievements/stats`
  获取成就统计

- `GET /api/v1/achievements/map`
  获取成就地图

- `GET /api/v1/achievements/streak`
  获取连胜统计

- `GET /api/v1/achievements/{achievement_id}`
  获取单个成就详情（canonical）

- `POST /api/v1/achievements/{achievement_id}/share`
  生成真实 PNG 分享卡（canonical）

- `POST /api/v1/achievements/{achievement_id}/pin`
  置顶/取消置顶（canonical）

- `GET /api/v1/achievements/achievements/{achievement_id}`
  兼容旧版详情路由（deprecated）

- `POST /api/v1/achievements/achievements/{achievement_id}/share`
  兼容旧版分享路由（deprecated）

- `POST /api/v1/achievements/achievements/{achievement_id}/pin`
  兼容旧版置顶路由（deprecated）

- `GET/POST/DELETE /api/v1/achievements/contracts`
  契约状态/创建/取消

- `GET /api/v1/achievements/skins`
  获取皮肤列表

- `POST /api/v1/achievements/skins/{skin_id}/equip`
  装备皮肤

- `GET /api/v1/achievements/titles`
  获取称号列表

- `POST /api/v1/achievements/titles/{title_id}/equip`
  装备称号

- `POST /api/v1/achievements/events/process`
  内部事件处理接口（需 `X-Internal-Token`）

- `GET /api/v1/achievements/close-to-unlock`
  获取接近解锁成就

### 9.2 API 设计优点

优点主要有三点：

1. 能力面比较完整
   列表、详情、统计、地图、契约、皮肤、称号、实时事件基本都有。

2. 业务集中
   大多数接口都委托给 `AchievementEngine` 或 `ContractService`。

3. 已考虑增强反馈
   包括临界成就提示、里程碑推送、分享卡入口等。

### 9.3 API 设计问题

当前主要问题已从“占位实现”转为“兼容期边界管理”，主要有四类：

1. `response_model` 大量使用 `dict[str, Any]`
   虽然已有 `schemas/achievement.py`，但接口层没有强类型收口，导致契约漂移风险较高。

2. 旧路由仍在兼容期
   `achievements/achievements/...` 仍保留一阶段兼容，后续需要明确下线窗口。

3. 内部接口仍保留 HTTP 入口
   `/events/process` 已改为 internal-only，但长期仍建议迁移到事件总线唯一入口。

4. 分享链路依赖本地 uploads
   当前可用，但还没有接入对象存储/CDN，后续跨环境分发能力有限。


## 10. 移动端对齐情况

### 10.1 当前移动端已接入的能力

移动端已经完整接入以下能力：

- 成就列表
- 成就详情
- 成就统计
- 连胜面板
- 成就地图
- 皮肤获取与装备
- 称号获取与装备
- 契约创建/取消/查看
- 成就解锁弹窗
- WebSocket 实时成就通知

### 10.2 当前移动端架构

数据流基本是：

1. `AchievementRepository`
   负责 API 调用、Demo 数据回退、JSON 转换

2. `AchievementNotifier`
   负责页面初始化、刷新、装备、契约、事件处理

3. UI 层
   包括：
   - `AchievementListScreen`
   - `AchievementDetailScreen`
   - `AchievementUnlockDialog`
   - 各种卡片/徽章/统计组件

4. Chat WebSocket 事件流
   当后端推送 `achievement_unlock` / `achievement_milestone` 时，移动端通过聊天流模型消费并触发弹窗

### 10.3 当前移动端与后端的主要不对齐点

#### 问题 A：`close-to-unlock` 返回结构不匹配

后端 `GET /close-to-unlock` 返回的是轻量对象：

- `achievement_id`
- `name`
- `description`
- `rarity`
- `progress`
- `progress_value`
- `progress_target`
- `remaining`

但移动端仓库层把它当成 `AchievementWithProgress` 去解析。

这两者不是同一结构：

- 后端没有嵌套的 `achievement`
- 后端没有 `user_progress`
- 后端字段名也不完全一致

结果：

- 该接口在真实线上数据下大概率解析失败
- `SprintScreen` 中“接近解锁成就”能力存在失效风险

#### 问题 B：装备态存在双轨来源

成就系统自己的装备态：

- `user_galaxy_skins.is_equipped`
- `user_titles.is_equipped`

用户模型 / 商城系统的装备态：

- `users.equipped_skin`
- `users.equipped_title`

这意味着当前至少存在两套“谁是当前装备”的真源：

1. 成就域自己的装备表
2. 用户/商城域的装备字段

风险：

- 成就页装备了皮肤，但全局主题不一定同步
- 商城页装备了称号，但成就页的 `is_equipped` 不一定同步
- 后续会出现展示层冲突、缓存冲突、统计冲突

#### 问题 C：移动端 Demo 能力比真实后端更“完整”

仓库层提供了大量 Demo 数据，包含：

- 成就列表
- 成就地图
- 皮肤
- 称号
- 接近解锁成就

这对开发调试有帮助，但也容易掩盖真实接口契约问题，尤其是：

- `close-to-unlock` 的结构不一致
- 某些隐藏成就或奖励在 Demo 中看起来可用，真实链路里却不能触发


## 11. 与其他系统的耦合关系

### 11.1 与任务系统的关系

任务完成是最核心的成就触发入口之一：

- 推进任务总数成就
- 更新连胜
- 可能触发里程碑
- 可能直接返回 `unlocked_achievements` 给任务完成响应

这条链路是当前最真实可用的主链路之一。

### 11.2 与知识星图系统的关系

知识星图系统与成就体系强绑定：

- 点亮知识点 -> `NODE_UNLOCKED`
- 掌握度提升到 80+ -> `NODE_MASTERED`
- 100 分掌握 -> `PERFECTIONIST`

成就体系不仅消费星图数据，也通过：

- 视觉效果
- 星系皮肤奖励

反向影响星图体验。

这是当前系统中产品想象空间最大、也是最值得保留的一条耦合关系。

### 11.3 与专注系统的关系

专注会话完成会触发：

- 学习时长类成就
- 深夜学习类成就
- 早起学习类成就

但由于 `EARLY_BIRD` 触发码未实现，当前只有“夜猫子”类更接近闭环，“早起鸟”仍未跑通。

### 11.4 与冲刺计划系统的关系

冲刺归档时触发：

- 完成冲刺成就
- 完美冲刺成就
- 超前完成成就
- 连续冲刺成就
- 今日首胜奖励

冲刺成就是当前种子里占比最大的簇之一，也是最接近“行为游戏化”的部分。

### 11.5 与商城/背包系统的关系

这里是当前最需要收敛的边界：

- 成就系统可直接解锁称号/皮肤
- 商城/背包系统也可装备称号/皮肤
- 用户表还有全局 `equipped_skin` / `equipped_title`

说明当前设计已经从“成就域内部奖励”扩展成“全局资产系统”，但真源仍未统一。


## 12. 实时反馈链路

### 12.1 当前已形成闭环的实时能力

成就解锁时，后端会：

1. 通过 WebSocket 推送 `achievement_unlock`
2. 发布事件总线消息 `achievement.unlocked`
3. 写入系统更新队列

移动端会：

1. 在聊天 WebSocket 流里识别 `achievement_unlock`
2. 转成 UI 事件模型
3. 展示 `AchievementUnlockDialog`

### 12.2 当前实时反馈质量

这条链路质量不错，原因是：

- 数据结构相对简单
- 后端已显式补充 `photon_granted`、`combo_info` 等字段
- 移动端已经做了视觉分层，稀有度不同，反馈不同

这是当前成就体系里实现完成度最高的用户可感知部分。

## 16. 核心问题清单

按优先级排序，当前最值得先解决的 8 个问题如下。

### P0. 触发码唯一约束与种子定义冲突

这是初始化和持续扩展的硬阻塞问题。

如果不先解决：

- 现有多档成就设计不成立
- 新增同类成就会继续踩雷
- 初始化/补数据链路不可信

### P0. 种子定义与引擎支持矩阵不一致

触发码和奖励类型都存在“定义超前于执行”的情况。

如果不收敛：

- 产品会以为功能已存在
- 客户端会展示无法兑现的奖励
- 线上会出现“解锁不到/奖励不到账”的隐性 bug

### P0. `close-to-unlock` 后端/移动端契约不一致

这是一个明确的跨端接口不一致问题，应优先修。

### P1. 装备真源双轨

必须决定：

- 皮肤/称号装备态是否以成就域表为准
- 还是统一以用户/背包系统为准

否则成就系统和商城系统会长期打架。

### P1. 分享卡仍是占位实现

当前接口存在，但产品能力未真正完成。

### P1. 隐藏成就和早起/周末类触发未收口

事件有、定义有，但触发判断未真正闭环。

### P1. 奖励资源字典未做完整性校验

典型例子是 `sprint_legend_galaxy` 缺失。

### P1. 缺少自动化测试

当前成就系统每次改动都有较高回归风险。


## 17. 建议的收敛顺序

### 第一阶段：先修数据与契约

建议先做 4 件事：

1. 去掉 `trigger_code` 唯一约束，改为普通索引
2. 补齐或下线未实现的触发码
3. 补齐或下线未实现的奖励类型
4. 修正 `/close-to-unlock` 的返回结构，和移动端统一

这是“让系统不自相矛盾”的最低要求。

### 第二阶段：统一装备真源

建议明确一个结论：

- 皮肤/称号最终以哪个表或哪个字段作为唯一装备态

推荐方向：

- “拥有关系”保留在 `user_galaxy_skins` / `user_titles`
- “当前装备态”只保留一个真源
- 其他位置全部改为派生/同步，不再双写

### 第三阶段：把占位能力真正做完

建议补齐：

1. 分享卡生成链路
2. 隐藏成就触发器
3. `ai_persona` / `avatar_frame` / `function` 奖励执行器
4. 资源完整性校验脚本

### 第四阶段：补测试

最低建议覆盖：

1. `AchievementEngine.process_event()` 主路径
2. 关键 trigger_code 的阈值解锁测试
3. 奖励发放测试
4. `/close-to-unlock` 契约测试
5. WebSocket `achievement_unlock` 事件消费测试


## 18. 最终对齐结论

如果用一句更产品化的话总结当前状态：

Sparkle 的成就体系已经具备了“产品骨架”和“用户反馈层”，但业务定义、数据库约束、跨端契约、装备真源还没有完全收拢，所以它目前更适合被定义为“可演示、可局部使用、不可放心扩展”的系统，而不是“已经稳定完成”的系统。

如果用工程化语言总结：

- 领域模型：已成型
- 运行时引擎：已成型
- API 面：已成型
- 客户端展示：已成型
- 契约一致性：未成型
- 数据约束一致性：未成型
- 测试保障：未成型

因此，下一步不建议继续盲目加新成就，而应先做一次“成就体系收敛迭代”，把现有 32 个定义、触发矩阵、奖励矩阵、装备态、接口契约全部收口到一致状态。
