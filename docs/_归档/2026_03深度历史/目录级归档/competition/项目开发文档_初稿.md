## 1 项目概述

### 1.1 项目背景

星火所处的业务领域，是中国大陆大学生的自主学习支持；所处的技术领域，则是“移动端产品 + 实时接入 + 知识组织 + Agent 编排 + 执行闭环”的复合型系统建设。

从中国大陆高校的真实使用习惯看，大学生的学习流程通常被拆散在多种工具中：课程平台负责课件、作业和课堂活动入口，AI 问答与搜题产品负责即时解释和纠错，专注与待办产品负责提醒和打卡。工具越来越多，但学习过程并没有因此自动连成一条主线。学生往往仍要自己在“看资料、提问题、做计划、查漏洞、逼自己执行”之间来回切换。

但作者在实际观察中发现，学生遇到的痛点并没有因为工具变多而消失，反而更容易被切碎。具体表现为：

1. 对于期末复习、竞赛准备、课程项目这类大目标，很多工具能“回答问题”，却很难继续把目标拆成真正可做的行动链。
2. 对于知识积累，学生已经保存了大量资料、截图、聊天记录和错题，但这些内容往往没有长成可以反复利用的知识结构。
3. 对于执行推进，AI 已经能给出越来越多“看起来正确”的建议，但建议之后怎么做、做到什么程度算完成、结果如何回流，很少有系统真正承担。
4. 对于长期成长，课程平台能记录学过什么，待办工具能记录做过什么，搜题工具能记录问过什么，但用户依然很难看见自己“为什么在进步、还差什么、下一步该怎么走”。

从当前较成熟的国内外解决方案看，主流路线大致有四类：

1. 校内课程平台与学习资源平台：负责内容承载、课堂组织和课程入口，但不负责长期个人成长闭环。
2. AI 问答与辅学方案：负责讲解、启发和搜索效率，如夸克、DeepSeek、ChatGPT Study Mode、Khanmigo，但核心仍偏向单次问答体验。
3. 搜题与即时作业辅助方案：负责拍照识题、步骤讲解、快速纠错，如作业帮、小猿搜题、有道小P、StudyX、Gauth，但大多强于点状求解，弱于长期成长。
4. 专注、计划与打卡方案：负责时间管理和坚持反馈，如番茄ToDo、滴答清单、Forest，但通常不了解学习内容本身。

因此，星火的切入点不是在某个已经高度成熟的单点赛道里重复造轮子，而是补当前市场仍明显缺失的一块系统能力：把大学生学习中的目标、知识、执行和反馈重新组织成一条连续主链。

### 1.2 定位说明

星火的定位从三个维度展开：它服务哪些真实学习场景，主要面向哪些人群，以及它究竟以什么方式区别于常见的 AI 辅学工具。

#### 1.2.1 应用场景

星火重点覆盖以下场景。它们都来自中国大陆高校常见的自主学习过程，真正值得被解决的，不是“学生没有工具”，而是“关键断点始终没有被系统接住”。

| 应用场景 | 作者观察到的真实痛点 | 星火准备解决的核心问题 |
|------|------|------|
| 期末复习与课程冲刺 | 学生通常掌握了课程范围，却很难判断先复习什么、哪些知识点真的薄弱、今天晚上先做哪一步 | 解决“目标太大、优先级难确定、起步动作不清晰” |
| 竞赛准备与课程项目推进 | 任务同时涉及知识理解、方案设计、代码实现、材料撰写和展示演练，普通问答工具难以稳定支持 | 解决“复杂目标缺少系统编排与多维分析” |
| 长周期补基础与跨学科学习 | 用户明明学过很多内容，却经常出现“会一点、串不起来、总在同一处卡住”的现象 | 解决“知识碎片化、路径不清、掌握度不可见” |
| 日常计划执行与专注学习 | 待办和专注工具能提醒用户坚持，但不能告诉用户“为什么此刻该做这件事、做完如何继续” | 解决“建议停留在说明层、无法稳定推进执行” |
| 错题复盘与阶段回顾 | 搜题类工具往往在出答案后结束，错题难以沉淀成知识资产，学习过程也缺少阶段反馈 | 解决“做过但没沉淀、完成了却看不到成长” |

这些场景进一步展开后，可以看到更具体的痛点来源：

1. 在期末复习场景中，作者观察到很多同学并不是不努力，而是在“范围太大、时间太少、资料太散”的情况下不知道先做什么。星火希望先替用户完成澄清、排序和拆解，再把复习推进到任务层。
2. 在竞赛和项目场景中，作者观察到最难的不是“查一个答案”，而是“把很多线索组织起来并持续往前走”。星火希望通过 Mirofish 多 Agent、任务链和 OpenClaw 执行闭环，把复杂目标转化为可协作、可推进的链路。
3. 在长期补基础场景中，作者观察到学生往往保存了很多资料，却没有一张属于自己的知识地图。星火希望通过知识星图和 GraphRAG，让“学过什么、缺什么、下一步为什么这样学”变得清晰。
4. 在日常执行场景中，作者观察到很多人已经知道正确答案，却仍然难以真正做下去。星火希望补上从建议到执行再到反馈的关键一跳。
5. 在复盘和成长回顾场景中，作者观察到“做完一堆事但不知道自己是否在变强”是非常普遍的挫败来源。星火希望把报告、剧场、模拟和成长反馈统一起来，让成长更可见。

#### 1.2.2 目标人群

项目核心面向大学生用户，并在此基础上考虑具备相似需求的延伸人群。之所以把人群重新细分，是因为不同用户表面上都在“学习”，但真正卡住的环节并不相同。

1. 有目标但执行不稳定型。典型表现是“知道要学什么，也知道应该努力，但总是迟迟启动不了，或者三天热度后很快中断”。这类用户最需要的不是更多道理，而是有人把大目标拆成当下能做的下一步。
2. 有积累但缺结构型。典型表现是“看过很多视频、做过很多题、记过很多笔记，但脑中仍然没有稳定结构，一遇到综合题或跨章节问题就容易乱”。这类用户最需要的是知识关系被外显、路径被解释、薄弱点被持续追踪。
3. 有学习意愿但缺系统型。典型表现是“愿意长期提升，也愿意尝试 AI 工具，但现有工具都只解决局部问题，难以形成一套长期可复用的方法”。这类用户最需要的是一套真正能陪伴成长的系统，而不是一串零散能力。
4. 需要复杂任务支持的项目型学生。包括竞赛准备、课程大作业、科研训练、求职技能补强等用户，他们的任务往往跨资料理解、任务拆解、方案设计和持续执行，单次问答产品难以满足。

除核心用户外，星火还具备明确的延展空间：

1. 考研、考公、考证等长周期备考用户。
2. 刚进入大学、尚未建立自主学习体系的新生群体。
3. 希望进行技能补课或跨领域学习的职场早期用户。
4. 需要长期知识管理和执行闭环的训练营、社团或小型教学组织。

#### 1.2.3 项目定位

星火统一定位为“面向大学生的 AI 学习成长系统”。这里的“学习成长系统”并不是空泛口号，而是有明确边界的产品定义：

1. 它不是只解决“当下一道题”的问题，而是围绕长期成长主线组织能力。
2. 它不是单纯提升问答体验，而是把对话、规划、知识、执行和反馈连成系统闭环。
3. 它首先服务中国大陆高校学生的真实学习场景，再在此基础上考虑更广泛的延展。
4. “学习操作系统”可以作为内部技术表达，但在对外定位上，我们选择更容易让评委和用户一眼理解的“AI 学习成长系统”。

### 1.3 项目方案

星火采用“移动端体验层 + Go 高并发接入层 + Python AI 智能层”的三层异构架构，把学习主链组织为：对话澄清 -> 计划生成 -> 任务拆解 -> 知识组织 -> 多 Agent 协作 -> 执行闭环 -> 报告与成长反馈。

从问题空间到解空间的映射关系如下：

| 问题空间 | 解空间设计 | 预期输出 |
|------|------|------|
| 对于“目标太大、难以启动”的问题 | 通过对话澄清、目标规范化、阶段计划与任务拆解来实现“把模糊目标转成明确的下一步” | 阶段目标、任务列表、优先级与执行入口 |
| 对于“知识碎片化、缺少路径感”的问题 | 通过知识星图与 GraphRAG 来实现“把知识关系、掌握度和推荐路径结构化表达” | 节点关系、薄弱点、学习路径与复习建议 |
| 对于“复杂任务难以稳定分析”的问题 | 通过 Mirofish 多 Agent 协作来实现“多专家参与、结果聚合和必要重规划” | 结构化分析、多维建议、协作结论 |
| 对于“建议无法落地”的问题 | 通过 OpenClaw 执行闭环来实现“从建议到执行再到回流”的可治理推进 | ExecutionIntent、执行结果、可信回流记录 |
| 对于“成长反馈滞后”的问题 | 通过学习报告、知识剧场、学习模拟、成就契约与多感官体验来实现“可见、可感、可持续的成长反馈” | 阶段总结、预测解释、成长时间线与反馈提示 |

这套方案的核心思想可以概括为一句话：对于学习过程中每一个关键断点，星火都不只停留在“给解释”，而是继续回答“接下来怎么办、做完之后系统如何继续理解你”。

从系统设计上看，星火真正的护城河在于三层闭环同时成立。第一层是数据反馈闭环，用户输入、计划推进、图谱变化、执行结果和成长反馈都会沉淀为后续决策依据；第二层是功能闭环，对话、规划、图谱、协作、执行、报告和反馈并不是并列存在，而是围绕同一条主链连续接力；第三层是体验闭环，用户每推进一步，都能看到状态变化、收到合理反馈，并自然进入下一步动作。这使星火不是“功能堆叠型应用”，而是一套围绕闭环构建的 AI 学习成长系统。

### 1.4 项目目标

1. 打通“理解 -> 规划 -> 执行 -> 回流 -> 成长反馈”的完整主链。
2. 让知识结构、掌握度和路径推荐不再停留在文字描述，而成为可计算、可展示的系统资产。
3. 以 Mirofish、OpenClaw、知识星图、GraphRAG 体现技术创新深度。
4. 在移动端形成有持续使用价值的学习体验，而不是一次性演示体验。
5. 通过测试、验收、benchmark 和系统闸门证明项目不是概念原型。

### 1.5 项目价值

#### 用户价值

对大学生用户而言，星火最直接的价值，是把“抽象的学习焦虑”转化成“可以推进、可以追踪、可以回看的行动链”。用户不再只是在不同工具里来回切换，而是能在同一系统中完成目标澄清、计划生成、任务推进、知识整理和成长反馈。这样做能够显著降低以下三类成本：

1. 启动成本：把“我该开始了吗”变成“我现在先做这一步”。
2. 认知成本：把“我哪里不会”变成“我卡在这几个节点，原因是什么”。
3. 坚持成本：把“我好像没进步”变成“我已经推进了这些节点，下一步是这些动作”。

#### 产品形态价值

对教育类 AI 产品形态而言，星火探索的是一条从“答疑工具”走向“成长系统”的路径。很多产品已经证明，用户需要 AI 讲得更清楚、答得更快、搜得更准；但星火更想回答另一个问题：如果用户要连续学习一门课、一个专题、一项技能，AI 产品能不能不再只做局部帮手，而是成为一套真正组织成长过程的系统。

这意味着星火的产品价值不只是“功能多”，而是“功能之间真正有主链关系”。这种形态一旦成立，产品留存、复盘深度和长期成长价值都会明显高于一次性问答工具。

#### 技术与工程价值

星火把知识组织、多 Agent 协作、执行闭环和多感官体验统一到了一个真实工程体系中，而不是只在 PPT 或演示视频里展示概念。这种整合本身具有明显的工程研究价值：

1. 它提供了一个可观察的 AI-native 学习系统样本，展示异构架构、知识星图、GraphRAG、Mirofish、OpenClaw 如何在同一产品中协同。
2. 它验证了“复杂学习问题”不仅可以靠更强模型解决，也可以通过更合理的系统组织方式解决。
3. 它为今后类似的学习、训练、辅学、知识管理类产品提供了可复用的工程思路。

#### 系统闭环价值

星火最难被简单复制的地方，不是某一个页面设计，也不是某一个单点模型效果，而是全链路、全功能的数据反馈闭环。系统会持续记录用户目标、任务推进、知识掌握度、执行结果和成长事件，再把这些反馈反向作用到后续的澄清、规划、推荐、协作与报告中。随着使用次数增加，系统并不会停留在“每次重新回答”，而是越来越能够理解用户处在什么阶段、为什么卡住、下一步最值得推进什么。

这种闭环价值还体现在产品层面和体验层面。产品层面，10 个模块能够形成连续接力，而不是相互独立；体验层面，报告、剧场、模拟、成就与多感官反馈会把系统理解到的变化重新呈现给用户，帮助用户感受到自己正在前进。对评委而言，这种三层闭环同时成立，正是项目壁垒强于单点功能拼接的重要原因。

#### 教育与社会价值

从教育价值看，星火强调的是自我驱动学习能力的增强。它并不替代老师，也不试图替代课程平台，而是帮助学生在课内外学习之间建立更好的自我管理、自我解释和自我反馈机制。对于高校中普遍存在的期末冲刺、竞赛备赛、项目推进、补基础等场景，这种支持具有很强的现实意义。

从社会效益看，星火有望在一定程度上缓解优质学习支持资源分布不均的问题。并不是所有学生都能稳定获得高质量的一对一指导，但 AI 学习成长系统可以把部分“解释、梳理、反馈、推进”能力以更低门槛提供给更多用户。它不能替代真实教育体系，却有机会成为教育支持的补充。

#### 应用拓展价值

虽然本项目当前聚焦大学生，但其方法和架构并不局限于某一门课或某一种考试。未来可扩展到：

1. 长周期备考场景，如考研、考公、语言考试、职业资格考试。
2. 课程学习与训练营场景，如社团培训、项目营、小型教学组织。
3. 职场继续教育与技能补课场景，如编程学习、写作训练、岗位技能迁移。
4. 知识管理与执行闭环场景，如个人成长规划、长期知识体系建设。

## 2 开发计划

### 2.1 最终呈现形式

项目最终以移动端应用为主形态，结合网关与 AI 引擎形成完整系统。其最终呈现重点不在单个页面是否丰富，而在于是否能够清晰展示“从输入到反馈”的完整主链：

1. 移动端核心页面与交互流程，包括对话、计划、知识星图、学习报告、剧场、模拟、成长反馈等关键页面。
2. WebSocket / HTTP / gRPC 组成的后端主链，能够体现移动端、Go Gateway 与 Python AI Engine 的职责分工。
3. 关键创新能力演示，包括知识星图、Mirofish、OpenClaw、学习报告、知识剧场、学习模拟与多感官体验。
4. 工程可信度展示，包括测试材料、验收记录、性能阈值、环境闸门和可复建证据。

### 2.2 主要功能描述

1. AI 对话与主链编排：作为统一入口，负责理解问题、澄清上下文、判断信息充分性并组织后续主链。
2. 学习规划与任务执行：负责把学习目标转成阶段计划、任务清单和持续推进机制。
3. 知识星图与 GraphRAG：负责把知识点、关系、掌握度和路径推荐做成可计算的结构。
4. Mirofish 多 Agent 协作：负责复杂学习问题的多专家协同分析、聚合与重规划。
5. OpenClaw 执行闭环：负责将适合执行的任务推进到执行层，并在治理与可信机制下回流结果。
6. 学习报告：负责阶段性数据聚合、薄弱点分析、趋势总结和行动引导。
7. 知识剧场：负责把学习状态、可能路径和关键节点以更易理解的方式呈现出来。
8. 学习模拟：负责通过角色扮演、讨论、情景练习等方式强化理解和迁移。
9. 成就契约与成长反馈：负责阶段成就、契约目标、成长时间线与长期激励。
10. BGM 与多感官体验：负责通过音景、触觉和环境反馈增强专注感与成长感知。

## 4 需求分析

### 4.1 数据需求

#### 4.1.1 静态数据

静态数据主要包括知识点元数据、关系类型、学科分类、专家角色配置、界面配置、成就模板、契约模板等。

#### 4.1.2 动态数据

动态数据主要包括聊天记录、用户状态、计划、任务、执行记录、知识节点掌握度、学习报告、通知、成就触发和多感官设置状态等。

#### 4.1.3 数据词典

| 数据对象 | 含义 |
|------|------|
| UserStateSnapshot | 用户某一时刻的学习状态快照 |
| Plan | 围绕学习目标生成的阶段性计划 |
| Task | 可执行任务项 |
| KnowledgeNode | 知识图谱中的知识节点 |
| ExecutionIntent | 面向外部执行器的结构化执行协议 |
| ExecutionRecord | 外部执行后的结果记录 |
| LearningReport | 阶段性学习反馈和总结 |
| Achievement | 用户达成的成长里程碑 |

#### 4.1.4 数据采集

数据采集主要来自四类入口：

1. 用户主动输入：对话、计划、任务、反馈、模拟内容。
2. 系统推导结果：掌握度、推荐路径、报告摘要、预测结果。
3. 执行回流结果：OpenClaw 执行记录、信任评估、状态变更。
4. 端侧交互数据：专注会话、多感官开关、页面使用状态。

### 4.2 功能需求

核心功能模块如下，所有后续设计与测试均与这 10 个模块保持一一对应。这里不仅罗列“有什么功能”，还强调“功能在业务层如何发生作用、如何接入主链、会产生什么结果”。更重要的是，这些模块不是平铺展开，而是共同服务于数据反馈闭环、功能闭环与体验闭环三层系统目标。

#### AI 对话与主链编排

用户通过文本、上下文延续或页面入口发起需求后，系统首先在这一模块中完成意图识别、状态读取、信息充分性检查和主链分流。该模块的业务价值不只是“聊天”，而是把自然语言需求翻译成系统内部可执行的结构化动作，为后续规划、图谱、协作和执行模块提供统一入口。

#### 学习规划与任务执行

用户在明确目标后，系统生成阶段计划、拆解任务、记录状态并持续根据反馈调整。该模块在业务层真正解决的是“今天先做什么”“做完之后系统如何判断下一步”“计划如何随着学习进展不断修正”。

#### 知识星图与 GraphRAG

系统将知识点、关系、掌握度和路径组织成图结构，并通过混合检索为用户提供与当前目标相关的结构化支持。该模块不是一个附属可视化页面，而是负责把“学过什么、卡在什么位置、为什么下一步这样推荐”真正解释清楚。

#### Mirofish 多 Agent 协作

当问题复杂到单次对话无法稳定解决时，系统将问题路由给多个专家节点，通过协作、聚合和必要重规划生成更完整结果。该模块在业务层解决的是“复杂目标如何被拆开、如何分别分析、如何重新合并”的问题。

#### OpenClaw 执行闭环

当某些任务适合进入外部执行层时，系统生成 `ExecutionIntent`，进行路由、边界判断、审批和信任评估，并把结果回流到计划、任务和状态主链。该模块是“从建议到行动”的核心，也是本项目最具差异化的业务链路之一。

#### 学习报告

系统将用户阶段性学习过程转化为反馈报告，包括完成情况、薄弱点、建议路径和后续动作，帮助用户从“做过”走向“理解自己的变化”。它承担的是“把行为沉淀为可理解反馈”的业务职责。

#### 知识剧场

系统通过路径推演、预测和状态可视化，把用户的学习进程和知识关系以更具解释性的方式呈现出来，帮助用户理解“为什么我在这个位置”“如果继续这样推进会走向哪里”。

#### 学习模拟

系统为用户提供情景化练习、角色扮演、辩论和讨论支持，让理解不只停留在阅读和回答层，而能进一步进入表达、迁移和应用层。

#### 成就契约与成长反馈

系统对关键里程碑、阶段达成和持续行为给予反馈，形成契约、成就与成长标记，增强长期使用的持续性。该模块的反馈依据来自计划、任务、知识和执行链路，而不是孤立打卡。

#### BGM 与多感官体验

系统通过路由级 BGM、触觉提示、环境反馈和状态协调，增强专注感和成长反馈的感知强度，但同时控制打扰程度。它在业务层承担的是体验强化作用，而非独立功能堆砌。

### 4.3 性能需求

#### 4.3.1 时间特性

系统的时间特性以“交互连续、状态清晰、关键链路稳定”为目标，重点约束用户最容易感知的等待、切换和回流时延。

1. 响应时间：对话主入口在常规演示环境下应尽快给出首个有效反馈；若需要继续澄清，也应先返回状态说明，避免长时间无响应。
2. 更新处理时间：计划、任务、掌握度和报告更新应在用户可接受范围内完成；对耗时较长链路，应先显示处理中状态，再返回最终结果。
3. 数据转换与传输时间：Flutter、Go Gateway、Python AI Engine 之间的协议转换应避免明显阻塞，尤其要控制大对象频繁传输导致的卡顿。
4. 运行时间：多 Agent 协作、GraphRAG 查询、执行闭环等长链路任务在运行期间应提供阶段反馈、进度提示或可中断说明。
5. 页面交互时间：图谱拖拽、任务状态切换、报告跳转、模式切换等高频操作应保持平滑，不因后端复杂逻辑破坏端侧体验。

#### 4.3.2 适应性

系统在以下变化下应保持可适应性：

1. 操作方式变化：文本交互、任务交互、页面跳转、图谱交互和报告回跳切换时不应破坏主链状态。
2. 运行环境变化：弱网、依赖服务波动、不同设备性能差异下应具备清晰的降级能力。
3. 软件接口变化：模型接口、检索接口、缓存和对象存储接口变化时应保持清晰边界与替换空间。
4. 硬件能力变化：当设备不支持音频、触觉、通知或分享能力时，系统应允许无该能力模式运行。
5. 展示方式变化：无论是日常使用、比赛演示还是录屏展示，系统都应支持固定链路和可复现输出。

2. 对含有系统状态的界面，应明确标注状态来源，如任务状态、掌握度、执行状态、可信度等。
3. 原型阶段与最终运行界面可在视觉细节上继续打磨，但布局关系、区域命名和组件职责应保持一致。

### 4.5 接口需求

#### 4.5.1 硬件接口

项目依赖的硬件能力主要来自移动终端，具体如下：

1. 手机屏幕与触控接口：用于对话、任务、图谱、报告、剧场、模拟等页面的交互展示。
2. 扬声器/耳机输出：用于 BGM、环境音和部分反馈提示。
3. 振动马达：用于低打扰触觉反馈，如任务完成、成长触发、模式切换。
4. 系统通知能力：用于计划提醒、阶段回流提示和关键状态更新。
5. 系统分享能力：用于分享学习报告、阶段成果和卡片海报。

上述能力主要通过 Flutter 端侧服务与系统能力接口调用完成。若某次演示环境不支持其中某项能力，系统应允许降级为“无该能力”模式运行，不影响核心学习主链。

#### 4.5.2 软件接口

软件接口定义了星火对外部服务的依赖方式以及内部服务之间的协同方式，主要包括：

1. LLM 与推理接口：负责对话生成、澄清提问、协作推理、报告总结等内容生成。
2. 检索与存储接口：PostgreSQL、pgvector、Redis、MinIO 等，用于关系数据、向量检索、缓存和对象存储。
3. 通信接口：WebSocket、HTTP、gRPC、Protobuf，用于跨端、跨语言通信。
4. 外部执行接口：OpenClaw 的执行接入、结果返回、可信度评估和主链回流接口。
5. 端侧系统服务接口：音频、通知、分享、触觉反馈等系统能力调用接口。

若某一外部服务发生变化，系统应优先通过接口层适配完成替换，而不是直接修改上层业务逻辑。

### 4.6 其他需求

1. 可使用性：核心链路必须清晰，用户能够快速理解当前状态、关键判断和下一步。
2. 安全性：执行能力必须服从审批、边界和信任评估规则，不允许无边界自动推进。
3. 可维护性：模块边界清晰，移动端、网关、AI 引擎职责分离，关键协议与数据结构显式化。
4. 可移植性：核心逻辑不依赖单一设备或单一模型接口，应支持降级与替换。
5. 可解释性：对计划推荐、路径推荐、执行回流和成长反馈等关键结果，应尽量给出可理解说明。

## 5 概要设计

### 5.1 处理流程

系统主处理流程围绕学习成长主链展开，逻辑顺序如下：

1. 用户输入学习目标、问题或任务请求。
2. 系统进行状态读取、意图识别和信息充分性检查。
3. 根据问题类型进入解释、规划、图谱、协作或执行链路。
4. 结果生成后同步更新计划、任务、知识节点或执行状态。
5. 阶段数据继续汇入学习报告、知识剧场、学习模拟与成长反馈层。

2. Go Gateway 负责高并发接入、会话管理、鉴权、协议转换和统一入口控制。

### 5.6 数据结构设计

系统核心数据结构包括：

1. UserStateSnapshot：描述用户在某时刻的状态。
2. Plan / Task / Subtask：描述计划和执行单元。
3. KnowledgeNode / NodeRelation / UserNodeStatus：描述知识结构及掌握度。
4. ExecutionIntent / ExecutionRecord：描述执行闭环协议与结果。
5. LearningReport / Achievement：描述反馈与成长资产。

这些结构共同服务于“状态可追踪、链路可回流、结果可解释”的总体目标，而不是各模块各自维护一套孤立数据。

### 5.7 接口设计

#### 5.7.1 外部接口

1. Flutter 与 Go Gateway：通过 HTTP / WebSocket 完成请求发送、流式消息返回和会话同步。
2. Go Gateway 与 Python AI Engine：通过 gRPC / Protobuf 完成高频请求转发、结构化调用和结果返回。
3. Python AI Engine 与数据库/缓存/对象存储：通过 SQL、Redis、对象存储接口完成状态读取、缓存和文件访问。
4. Python AI Engine 与 OpenClaw：通过结构化执行请求与结果回流接口完成执行闭环。
5. 移动端与系统服务：通过音频、通知、分享、触觉反馈接口调度设备能力。

#### 5.7.2 内部接口

1. 主链编排接口：包括状态判断、澄清提问、计划请求、结果合成和回流入口等函数/服务接口。
2. 图谱接口：包括节点查询、关系更新、掌握度更新、路径推理、图增强检索等接口。
3. 协作接口：包括专家路由、协作节点、聚合节点、冲突消解与重规划接口。
4. 执行接口：包括 `ExecutionIntent` 构建、执行路由、可信评估、结果摄取与回流接口。
5. 反馈接口：包括学习报告、知识剧场、学习模拟、成就系统、多感官服务之间的调用接口。

### 5.8 错误/异常处理设计

#### 5.8.1 错误/异常输出信息

系统在异常情况下应优先向用户返回可理解的状态说明、当前进度和建议动作，而不是直接暴露底层报错。

#### 5.8.2 错误/异常处理对策

1. 设置超时控制、降级输出和重试策略，确保主链不会因为单点波动完全失去反馈。
2. 对高风险执行能力设置审批、拒绝执行、人工接管和回退机制。
3. 对端侧弱网、无音频、无触觉、无通知等能力缺失场景设置后备方案。
4. 对系统异常提供恢复、再启动、缓存复用和状态重建机制。
5. 对多 Agent 与执行闭环等长链路模块，在失败时优先返回阶段状态与可理解说明。

### 5.9 系统配置策略

配置项按环境、模型、检索、缓存、执行策略和端侧体验分层管理，避免硬编码耦合。配置策略应支持开发环境与演示环境切换、模型与检索策略替换、执行阈值调节以及多感官反馈强度配置。

### 5.10 系统部署方案

本地开发环境采用 PostgreSQL + Redis + MinIO + Go Gateway + Python AI Engine + Flutter 客户端的组合部署方式，便于联调与验收。部署方案强调主链优先、服务清晰、环境可重建，能够支持 from-zero rebuild 和 fresh build 等工程闸门。

### 5.11 跨端应用架构设计

跨端协同通过统一协议和职责边界实现，其目标不是简单完成数据传输，而是在不同端和不同服务之间保持同一套状态语义与反馈节奏：

1. Flutter 与 Go Gateway 统一使用 WebSocket / HTTP，保证端侧交互和实时消息稳定。
2. Go Gateway 与 Python AI Engine 统一使用 gRPC / Protobuf，保证结构化调用和跨语言协同。
3. 状态、计划、任务、图谱和执行记录使用统一数据模型进行回流，避免模块间状态割裂。
4. 端侧体验能力通过路由级配置和通用状态协议协调，使 BGM、触觉、通知等能力跟随主链状态变化。
5. 跨端设计遵循“协议先行、状态统一、职责分离”的原则，以支持后续继续扩展新端形态。

### 5.12 其他相关技术与方案

除主链架构与核心 AI 模块外，Sparkle 还依赖若干关键基础设施共同支撑闭环能力。这些技术看似位于“辅助层”，但它们直接决定了系统能否把状态沉淀下来、把结果稳定回流上来、把体验持续交付出去。

**异步任务与缓存层**

Redis 承担多重职责：会话历史缓存、短期状态快照、消息队列辅助和速率限制。Celery 异步任务队列承接所有不适合同步链路的耗时计算，包括报告生成、知识节点更新、图谱扩展队列处理和大批量嵌入向量刷新。Celery Beat 负责定时任务调度，如夜间回顾生成和掌握度衰减计算。

**对象存储**

MinIO 作为本地兼容 S3 的对象存储服务，承载用户上传的学习材料、文档切片缓存、模型中间产物和演示媒体资源。端侧附件上传与多媒体资源下载均通过预签名 URL 方案进行访问控制。

**图数据库扩展（Apache AGE）**

PostgreSQL 中的 Apache AGE 扩展提供了 Cypher 兼容的图查询接口，使知识星图在同一数据库中兼顾关系数据与图遍历能力，无需引入独立图数据库即可支持前置关系、相关关系、掌握关系和路径推荐查询。

**向量检索（pgvector HNSW）**

pgvector 扩展配合 HNSW 索引用于知识节点语义召回、文档块检索和用户语义记忆查询。与图关系查询融合后，形成 GraphRAG 的双模检索能力（向量召回 + 关系遍历）。

**RunLedger 执行记录追踪**

系统引入轻量级 RunLedger 机制，对 OpenClaw 执行闭环中的每一次 ExecutionIntent 生命周期进行结构化追踪，确保执行行为可审计、可回放、可核查。

**BGM 路由与多感官调度**

BGM 服务采用路由级配置驱动的调度架构，ShellNavigation 层实时感知页面状态并通知 BGMService 执行切换、淡入淡出和降级静默。SensoryFeedbackService 统一管理触觉与音效的分配预算，避免多路反馈竞争干扰体验。

这些辅助技术共同支撑了星火的三层闭环。缓存、任务队列和对象存储保证数据能够沉淀与回放；图扩展与向量检索保证知识结构可以持续参与决策；执行记录追踪保证外部能力接入后仍能保留治理边界；BGM 与多感官调度则把系统对用户状态的理解转化为可感知的体验回应。正因如此，星火的闭环不是概念表达，而是由一整套基础设施共同托住的工程能力。

| 需求类别 | 需求项 | 最低要求 | 推荐配置 | 降级说明 |
|------|------|------|------|------|
| 系统版本 | iOS 版本 | iOS 14.0 | iOS 16.0 及以上 | iOS 14 可运行主链，部分动画效果降级 |
| 系统版本 | Android 版本 | Android 8.0（API 26） | Android 11（API 30）及以上 | API 26 可运行主链，通知样式与触觉 API 受限 |
| 运行内存 | RAM | 3 GB | 4 GB 及以上 | 低内存设备在图谱可视化和 Shader 渲染时可能出现帧率下降 |
| 存储空间 | 可用存储 | 500 MB | 2 GB 及以上 | 含 BGM 音频资源包；存储不足时音频资源按需加载 |
| 网络 | 基本访问 | WiFi 或 4G | WiFi / 5G | 弱网模式下主链启用缓存回放和超时降级提示 |
| 音频能力 | 背景音乐与音效 | 系统音频通道可用 | 立体声耳机 | 无音频权限时静默运行，不影响功能主链 |
| 触觉能力 | 振动反馈 | 系统振动 API 可用 | Taptic Engine（iOS） | 无触觉权限时忽略触觉序列，不影响其他功能 |
| 通知能力 | 推送通知 | 支持本地通知 | 本地 + 远端推送 | 通知权限未授权时，系统内提醒仍正常显示 |
| 传感器 | 屏幕方向 | 支持竖屏固定 | 支持横竖屏切换 | 当前 UI 以竖屏为主，横屏时部分页面限制方向 |
| 安全能力 | 本地存储加密 | 支持系统 Keychain / Keystore | 支持生物识别 | 令牌存储依赖系统安全存储区域 |

在实际部署中，星火优先保证对话、规划、图谱、报告和反馈等主链能力稳定可用；对于音频、触觉、通知、分享等增强能力，则采用“可用时增强、不可用时降级”的策略，以确保不同机型、不同权限状态下都不会破坏整体体验闭环。

## 8 详细设计

### 8.1 AI 对话与主链编排

#### 功能描述

负责对话入口、上下文组织、信息充分性检查、主链路由和结果合成，是所有其他模块的统一进入点。

#### 性能描述

优先保证流式响应和主链可追踪性，避免因复杂判断阻塞用户首个有效反馈。

#### 输入

用户消息、历史上下文、用户状态、图谱摘要、任务状态。

#### 输出

澄清问题、计划结果、模块路由结果、结构化回复。

#### 程序逻辑

PDL：
1. 接收用户输入并读取上下文。
2. 执行信息充分性检查。
3. 根据结果路由到解释、计划、图谱、协作或执行链路。
4. 聚合结果并回写状态。

#### 限制条件

依赖上下文质量和后端服务稳定性；复杂场景下需要合理控制上下文长度。

### 8.2 学习规划与任务执行

#### 功能描述

根据用户目标生成阶段计划，拆解为任务并持续记录执行状态，支撑“下一步行动”能力。

#### 性能描述

强调计划可执行性和任务粒度合理性，避免生成华而不实的大段计划文本。

#### 输入

学习目标、时间约束、用户当前状态、知识图谱结果。

#### 输出

计划节点、任务列表、执行建议、状态更新。

#### 程序逻辑

PDL：
1. 解析学习目标与约束。
2. 生成阶段计划并拆成任务。
3. 为任务绑定优先级和反馈入口。
4. 根据执行结果更新计划状态。

#### 限制条件

复杂目标的拆解质量依赖于输入充分性和图谱支撑程度。

### 8.3 知识星图与 GraphRAG

#### 功能描述

负责知识节点、关系、掌握度、推荐路径和图增强检索，是知识结构表达的核心模块。

#### 性能描述

既要保证图谱可视化体验，也要保证混合检索在比赛演示中的可接受响应时间。

#### 输入

知识查询、学习记录、节点关系、图谱更新请求。

#### 输出

节点集合、关系集合、掌握度变化、推荐路径、检索结果。

#### 程序逻辑

标准流程图：
1. 接收主题或目标节点。
2. 执行向量召回与关系检索。
3. 融合图关系并计算推荐路径。
4. 返回节点详情、路径与掌握度提示。

#### 限制条件

节点粒度与关系质量会直接影响推理效果；复杂图查询需注意性能控制。

### 8.4 Mirofish 多 Agent 协作

#### 功能描述

负责复杂学习问题的专家路由、协作执行、结果聚合和重规划。

#### 性能描述

优先保证协作结果可解释和可聚合，不盲目追求所有场景都启动多 Agent。

#### 输入

复杂问题、上下文摘要、图谱结果、计划约束。

#### 输出

专家协作结果、聚合结论、重规划建议。

#### 程序逻辑

PDL：
1. 根据问题类型选择专家集合。
2. 按 single / sequential / parallel / debate / delegation 运行协作模式。
3. 聚合结果并做一致性整理。
4. 必要时触发重规划。

#### 限制条件

协作链越长，对上下文、时间和展示脚本要求越高。

### 8.5 OpenClaw 执行闭环

#### 功能描述

负责把适合执行的任务从学习主链推进到外部执行器，并将结果安全回流。

#### 性能描述

优先保证边界治理和可信度，不以“执行得更多”取代“执行得可控”。

#### 输入

任务、ExecutionIntent、执行策略、审批信息。

#### 输出

执行状态、执行结果、信任等级、回流记录。

#### 程序逻辑

标准流程图：
1. 构建 ExecutionIntent。
2. 执行路由与边界判定。
3. 调用执行器并接收结果。
4. 由 TrustEngine 评估后回流。

#### 限制条件

高风险任务必须支持人工接管与降级。

### 8.6 学习报告

#### 功能描述

负责把阶段学习过程转化为总结、建议和趋势反馈。

#### 性能描述

重点保证信息浓缩能力和可读性，而不是单纯堆砌统计项。

#### 输入

任务记录、图谱状态、执行反馈、近期行为数据。

#### 输出

学习总结、薄弱点提示、建议动作、趋势摘要。

#### 程序逻辑

PDL：
1. 聚合近期学习数据。
2. 生成结构化总结与建议。
3. 输出报告卡片和可跳转入口。

#### 限制条件

报告质量依赖于前序数据沉淀是否完整。

### 8.7 知识剧场

#### 功能描述

负责以路径推演和预测视角呈现用户当前学习位置及未来可能路径。

#### 性能描述

重点保证解释性和视觉清晰度，避免过度复杂的推演阻碍理解。

#### 输入

用户目标、知识节点、预测规则、历史行为。

#### 输出

路径推演、预测提示、关键节点说明。

#### 程序逻辑

PDL：
1. 读取目标与当前状态。
2. 计算可能路径与关键节点。
3. 生成剧场化解释视图。

#### 限制条件

推演结果需清晰标识其为预测而非绝对事实。

### 8.8 学习模拟

#### 功能描述

负责通过情景化互动帮助用户在讨论、角色扮演或辩论中加深理解。

#### 性能描述

优先保证轮次组织和反馈质量，避免长链对话失控。

#### 输入

主题、角色设定、轮次设置、用户回答。

#### 输出

模拟过程、评价反馈、后续行动提示。

#### 程序逻辑

PDL：
1. 初始化角色与场景。
2. 按轮次推进交互。
3. 记录关键表达并输出反馈。

#### 限制条件

复杂模拟场景依赖较强的上下文管理。

### 8.9 成就契约与成长反馈

#### 功能描述

负责根据任务完成、阶段达成和持续行为触发成就、契约和成长标记。

#### 性能描述

反馈要及时且不过度打扰，强调“强化成长感”而非“刷存在感”。

#### 输入

任务状态、里程碑事件、持续行为、用户设置。

#### 输出

成就触发、契约状态、成长时间线。

#### 程序逻辑

判定表：
1. 满足里程碑条件 -> 触发对应成就。
2. 满足持续行为规则 -> 更新契约进度。
3. 达到阶段阈值 -> 写入成长反馈。

#### 限制条件

反馈机制需要避免刷屏和误触发。

### 8.10 BGM 与多感官体验

#### 功能描述

负责路由级 BGM、触觉提示和氛围反馈，增强专注和成长感。

#### 性能描述

重点保证切页平滑、音频不冲突、反馈不过载。

#### 输入

路由状态、用户偏好、场景模式、系统能力状态。

#### 输出

音景切换、触觉反馈、模式状态。

#### 程序逻辑

PDL：
1. 根据页面和场景选择反馈模式。
2. 检查用户设置和设备能力。
3. 执行音频/触觉切换并监听恢复状态。

#### 限制条件

真机能力与模拟器能力存在差异，需要保留降级路径。
