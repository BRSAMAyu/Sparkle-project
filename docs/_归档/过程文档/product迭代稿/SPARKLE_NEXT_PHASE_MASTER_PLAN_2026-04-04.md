## 0. Why This Document Exists

We have already done a great deal of foundational work:

- built the five bridges
- built the soul/runtime substrate
- built residual diagnosis
- built decision policy
- built experience actuation
- built first-pass evaluation
- materially hardened the backend

This is important.

It is still not the final product.

Sparkle is not being built to become an impressive architecture project.
Sparkle is being built to become:

> **an AI-native growth operating system that genuinely helps a person move toward who they want to become**

This document defines the next complete chapter of work after foundation building.

It is the top-layer plan that should guide all future implementation runs until Sparkle reaches a truthful `Live Alpha`.

The highest principle does not change:

> **If a change does not improve user outcomes, it is not progress.**

Sparkle should not optimize for:

Short version:

> **Helpfulness over elegance.**

## 4. The Five-Layer Configuration System Status

We previously aligned on a five-layer configuration and self-modification model.
That model is still correct and should remain the control framework for future work.

### 4.1 The Five Layers

1. `Constitutional layer`
   What cannot silently change.

2. `Session layer`
   Immediate reversible turn-level adaptation.

3. `Episode layer`
   Short-term persistence for the current journey, sprint, overload period, or exam week.

4. `Profile layer`
   Cross-session learned tendencies that require repeated evidence.

5. `System layer`
   The layer where Sparkle knows and can eventually operate its broader body: models, agents, pipelines, tools, surfaces, and orchestration styles.

### 4.2 Current Status

| Layer | Status | Meaning |
|---|---|---|
| Constitutional | Mostly built | Constitution, identity kernel, drift guardrails exist |
| Session | Built v1 | Immediate bounded writes and live strategy changes exist |
| Episode | Partially built | Promotion exists but needs stronger live proof and control |
| Profile | Partially built | Long-term learning exists but is still immature |
| System | Early | Capability registry/body map has begun, but true system self-governance is not built |

### 4.3 Strategic Meaning

This means:

- the five-layer design was right
- we should keep using it
- we should not pretend it is complete

The next chapter must:

- finish trustworthiness for session/episode/profile
- begin making system-layer self-knowledge real
- keep all of this subordinate to user benefit

## 7. Phase 1: Live Alpha Closure

### 7.1 Goal

Make Sparkle’s primary growth loop stable and trustworthy enough to serve as a real product base.

### 7.2 Why This Phase Exists

We now have architecture.
We need product-grade runtime truth.

This phase closes the gap between:

- “the system works in principle”

and

- “the system survives real integration and can be trusted as the primary path”

### 7.3 Core Work

1. Continue walking the backend suite with `--maxfail=1`
2. Clear core growth-path blockers
3. Ensure optional sidecars and shadow systems fail non-fatally
4. Strengthen live orchestrator acceptance and reduce simulation
5. Expand residual-family acceptance coverage:
   - `R_e`
   - `R_c` overload
   - `R_c` remobilization
   - `R_n`
   - `R_i`
   - continuity across sessions

### 7.4 Required Deliverables

- stabilized backend runtime on the primary growth path
- stronger orchestrator-backed north-star acceptance
- shadow-path non-fatal regression coverage
- residual-family acceptance matrix

### 7.5 Done When

- the primary growth path is not failing on known architecture-integrity blockers
- live acceptance on the primary path is strong enough to trust
- remaining failures are isolated product/integration issues, not foundational instability

### 7.6 What To Avoid

- do not spend this phase redesigning product theory again
- do not keep adding new architectural layers without a real blocker

## 8. Phase 2: Felt Adaptation UX

### 8.1 Goal

Make Sparkle’s intelligence perceptible and emotionally legible to users.

### 8.2 Why This Phase Exists

We have already learned the painful lesson:

> the system can compute intelligence that the user never feels

This phase turns internal adaptation into lived experience.

### 8.3 Core Work

#### Chat

- “I adjusted this because...” moments
- adaptation explanation language
- reversible wording
- grounded explanation language that clearly reflects user materials
- continuity callbacks to earlier struggles and successes

#### Home

- `what changed`
- `what matters now`
- `why the next move is right`
- growth narrative before dashboard mechanics

#### Adaptation Transparency

- show when Sparkle changed:
  - load
  - pacing
  - explanation style
  - session mode
  - grounding emphasis

### 8.4 Required Deliverables

- polished chat adaptation surfaces
- polished dashboard/home narrative surfaces
- language system for visible, calm, truthful adaptation

### 8.5 Done When

- users can clearly point to a real change Sparkle made
- users understand why the change happened
- adaptation feels supportive and truthful, not theatrical

### 8.6 What To Avoid

- decorative empathy without real change
- generic coach language that hides the real diagnosis

## 9. Phase 3: Human Evaluation Loop

### 9.1 Goal

Move Sparkle from engineering-judged to human-judged.

### 9.2 Why This Phase Exists

Automated tests can prove:

- runtime correctness
- contract correctness
- control-flow correctness

They cannot fully prove:

- whether the user felt understood
- whether the timing was right
- whether the adaptation built trust
- whether the system helped in a way that matters

### 9.3 Core Work

1. Run the thermodynamics north-star evaluation protocol with real humans
2. Record transcripts and UI states
3. Review transcripts with a stable rubric
4. Tag issues using the shared taxonomy
5. Feed findings back into product priorities

### 9.4 Required Deliverables

- human-evaluation runs completed
- transcript review records
- issue-tag summaries
- roadmap updates linked to transcript evidence

### 9.5 Done When

- at least one complete human-run north-star journey has been evaluated
- findings from that run have changed the implementation roadmap

### 9.6 What To Avoid

- using human evaluation only for confirmation
- ignoring repeated transcript failures because the architecture “should” work

## 10. Phase 4: Body Awareness v1

### 10.1 Goal

Let Sparkle begin to know its own body.

### 10.2 Why This Phase Exists

Sparkle already has:

- multiple models
- many agents
- OpenClaw pipeline
- prediction systems
- feedback systems
- knowledge galaxy systems
- community systems
- achievement systems
- visual and environment systems

These are only valuable as a true AI-native system if Sparkle can reason about them as capabilities.

### 10.3 Core Work

1. Expand the capability registry
2. Build a structured body map
3. Add runtime-readable capability state
4. Let Sparkle reason over:
   - what it can use
   - what each subsystem costs
   - what is safe
   - what is available
   - what should remain untouched

### 10.4 Required Deliverables

- body-map runtime artifact
- capability registry with costs/risks/uses
- first meaningful runtime use of system self-knowledge

### 10.5 Done When

- Sparkle can use body knowledge in at least one meaningful decision path
- capability metadata is no longer passive documentation only

### 10.6 What To Avoid

- abstract AGI-system design detached from user benefit
- giant prompt stuffing instead of structured self-knowledge

## 11. Phase 5: Complete the Five-Layer Learning System

### 11.1 Goal

Move from shallow adaptation to durable, trustworthy user-specific growth.

### 11.2 Why This Phase Exists

Right now, session-level adaptation is the strongest layer.
For Sparkle to become each user’s real Sparkle, episode, profile, and eventually system-layer behavior must mature.

### 11.3 Core Work

#### Episode Layer

- better promotion rules
- better expiry rules
- better “exam week / overload / recovery” behavior

#### Profile Layer

- stronger evidence thresholds
- conflict resolution
- preference drift control
- profile contradiction handling

#### Constitutional Safety

- prevent silent drift
- prevent manipulation
- prevent goal hijacking

#### System-Layer Preparation

- define bounded rights
- define what Sparkle may eventually control
- define approval and validation boundaries

### 11.4 Required Deliverables

- stronger episode/profile learning rules
- conflict resolution and evidence promotion framework
- bounded system-layer control design

### 11.5 Done When

- Sparkle can safely learn across sessions in a way that feels more personal and more accurate over time
- growth does not come at the cost of constitutional drift

### 11.6 What To Avoid

- giving the AI unrestricted self-modification
- overfitting one user moment into long-term identity

---

## 12. Phase 6: Organic System Integration

### 12.1 Goal

Make Sparkle behave more like one organism than many connected systems.

### 12.2 Why This Phase Exists

The long-term vision is not:

- many smart modules
- many clever prompts
- many pipelines

It is:

> **one AI-native operating system with a coherent body, memory, identity, and growth logic**

### 12.3 Core Work

1. unify prediction, adaptation, memory, galaxy, community, achievements, and environment systems under shared operating logic
2. make body-map awareness influence orchestration decisions
3. make major subsystems contribute to one coherent user trajectory
4. align system-layer control with the constitution and user benefit

### 12.4 Required Deliverables

- system-integration architecture for the major subsystems
- runtime body-state reasoning
- shared operating logic for major user-facing system effects

### 12.5 Done When

- Sparkle feels like one coherent intelligence across surfaces and subsystems
- system behavior is guided by one operating logic, not by isolated component cleverness

### 12.6 What To Avoid

- premature universal orchestration of everything
- integrating subsystems for completeness rather than for user value

## 13. What To Postpone

To stay aligned with the vision, we should postpone these until the earlier phases are sufficiently mature:

- broad multi-domain expansion
- deep system-layer autonomy
- unrestricted self-authored companion growth
- large new feature families unrelated to the north-star wedge
- visual flourish that is not tied to user benefit

This is important.

The product does not win by doing everything early.
It wins by being truly helpful in the highest-value journey first.

## 15. How To Judge Every Future Change

Before approving any major work, ask:

1. Does this improve user outcomes?
2. Does this help Sparkle better diagnose or better help?
3. Does the user feel this change?
4. Does it strengthen trust and continuity?
5. Does it move the five-layer system forward safely?
6. Does it help Sparkle become a more coherent organism?

If the answer is mostly no, it is probably not the next right move.
