## 1 问题聚焦

### 1.1 问题描述

大学生学习表面上看像是"提问、搜题、看课、做题"的简单组合，但从系统角度看，它实际上是一类高度动态、跨时段、跨知识域、跨情境的连续任务。用户的知识状态、目标清晰度、执行能力、情绪波动和时间资源会不断变化，而系统只有在理解这些变化的前提下，才可能持续给出有效帮助。

因此，星火试图解决的并不是"让模型更像老师回答问题"，也不是"让工具更方便记待办"，而是**"如何构建一套既能理解用户长期学习状态，又能把当前目标持续推进下去的 AI 学习成长系统"**。

### 1.2 问题抽象

从技术角度看，该问题可以被抽象为五个相互依赖的子问题：

1. **状态感知**：如何在多轮会话中持续感知用户当前的任务背景、学习节奏、知识状态与认知偏好。
2. **规划生成**：如何把自然语言学习目标拆解成可执行计划，并在执行过程中根据反馈持续修正。
3. **知识组织**：如何让知识检索不只返回相似文本，而是体现前置关系、路径依赖和掌握度变化。
4. **协作推理**：如何在复杂学习任务中组织多角色协作，使系统既有深度又有可解释性。
5. **执行闭环**：如何把外部执行能力安全地纳入主链，让 AI 从建议层进入执行层，但不破坏可控性与责任边界。

这些子问题并不是孤立的。知识状态的判断会影响规划路径，规划结果会影响是否需要多 Agent 协作，执行反馈又会反过来影响画像和下一轮路径推荐，因此系统需要的是一条可回流的主链，而不是若干互不关联的模块。

### 1.3 问题定位

从业务领域看，星火属于教育科技与学习科学交叉场景，核心对象是大学生自主学习、备考、课程消化和能力提升。

从技术领域看，星火处于 AI-native 应用、Agent 系统、知识组织系统、检索增强推理和个性化学习系统的交叉地带。与普通学习 App 相比，星火的问题更偏系统工程；与普通大模型应用相比，星火的问题又更偏"长期状态 + 任务推进 + 知识结构"的复合型场景。这意味着它既不能只靠 prompt engineering，也不能只靠单一功能优化。

### 1.4 问题评估

该问题具有以下技术特征，决定了它需要系统级设计而非单点优化：

#### 长链路特征

学习目标往往不是单轮完成，而是跨多次会话、多天任务和多知识点累积。系统必须具备跨时段状态一致性——`RedisCheckpointer` 实现 LangGraph 检查点持久化，支持长会话中断恢复；会话上下文通过 `ContextPruner` 自动剪枝，保留关键实体和结论，控制 Token 消耗。

#### 结构化特征

用户学习中的错误和进步都带有明显结构性——知识前置关系、错误模式、复习路径、掌握度变化。如果系统只能处理文本表面相似性，就会在关键路径推荐上失真。这要求系统必须具备图级别的知识组织能力。

#### 安全与解释性特征

一旦系统开始从建议层进入执行层，就必须处理审批、边界、可信度和责任归属等问题。否则"能力增强"会直接转化为"系统失控"。这是学习场景与通用 Agent 场景最大的差异之一。

#### 复杂协作特征

学习任务经常同时涉及知识解释、规划、执行、复盘和激励，不同子任务对模型能力、工具使用和输出形式的要求不同。单一策略难以长期稳定覆盖。

#### 规模特征

系统当前代码总量约 **67.5 万行**（Python 约 21.9 万、Go 约 5.9 万、Flutter 约 39.7 万），涵盖 16+ 完整功能模块、100+ 测试文件、7 个 benchmark 文件，复杂度远超一般课程项目。

### 1.5 问题分解

围绕上述问题，星火将系统拆解为以下五条技术主线：

| 主线 | 核心职责 | 关键技术 | 核心文件 |
|------|---------|---------|---------|
| 接入与体验 | 移动端体验 + 高并发接入 | Flutter/Riverpod + Go/Gin/Gorilla WS | `chat_service.dart`, `websocket.go` |
| 主编排 | 上下文构建、意图路由、规划、回流 | Python gRPC + LangGraph FSM + Mixin | `orchestrator.py`(1619行) |
| 知识组织 | 知识结构化、路径推理、图检索 | GraphRAG + pgvector + AGE + NetworkX | `graph_rag.py`, `graph_reasoning_service.py`(436行) |
| 协作与执行 | 多 Agent 协作 + 外部执行闭环 | Mirofish StateGraph + OpenClaw | `workflow.py`(318行), `execution_service.py` |
| 反馈与成长 | 报告、剧场、模拟、成就、多感官 | Theater + Simulation + Achievement | `learning_report_agent.py`, `simulation_engine.py` |

## 2 相关工作

### 2.1 Socratic 学习引导路线

以 ChatGPT Study Mode、Khanmigo 为代表的学习引导型产品，共同强调通过互动式提问、分步解释、基于用户水平的个性化讲解，帮助学习者在对话中获得更好的理解。

**技术分析**：ChatGPT Study Mode 基于 GPT-4 的 system instruction 实现 Socratic 引导模式，依赖 Memory 功能维护跨会话个性化。Khanmigo 进一步与 Khan Academy 课程体系绑定，提供结构化的课程路径导航。

**对星火的启发**：Socratic 交互是一种重要能力，但不足以单独构成学习成长系统的全部骨架。星火在认知核中吸收了引导式交互逻辑，但将其扩展到主链的更多环节。

### 2.2 AI homework helper 路线

以 StudyX、Gauth 为代表的作业辅助型产品，核心优势是输入门槛低（拍照 OCR）、即时反馈快、步骤拆解明确，并常结合图片识别、题库、专家辅助和多模型能力。

**技术分析**：这类产品通常采用 OCR + LLM 的串联架构，重点优化识别准确率和解题步骤生成。后端相对轻量，不需要复杂的状态管理和长链路编排。

**对星火的启发**：证明了学生对即时帮助的高需求，也反向说明了长期学习系统不能只停留在搜题和解题层。星火吸收了即时帮助的设计思路，但将其作为主链入口而非终点。

### 2.3 AI study materials 路线

以 Quizlet 的 Study Guides、Ask Quizlet 等能力为代表，这一路线围绕资料和学习材料组织学习流程。

**技术分析**：Quizlet 的 AI 能力主要用于从上传内容中抽取学习要点、生成闪卡和学习指南，底层依赖内容理解和结构化抽取。其知识组织停留在"资料级别"而非"图谱级别"。

**对星火的启发**：资料加工是学习流程的重要一环，但不等于完整成长闭环。星火的知识组织从"资料加工"推进到了"图推理 + 路径生成 + 掌握度追踪"。

### 2.4 知识组织与图推理路线

传统 RAG（Retrieval-Augmented Generation）更关注语义相似度，而学习路径问题要求系统进一步理解知识点之间的前置、递进、应用与迁移关系。

**技术分析**：纯向量检索（如 FAISS、pgvector）在语义匹配上表现优秀，但无法表达图结构关系。纯图谱方案（如 Neo4j、Apache AGE）能表达结构关系，但缺少语义灵活性。GraphRAG 方案通过融合两种检索模式，在保留语义匹配能力的同时引入图结构推理。

**星火的判断**：如果系统只用语义检索，就无法稳定支撑学习路径推荐、掌握度变化分析和知识星图可视化；如果只用图谱而缺少语义检索，则会损失灵活问答与广义召回能力。因此采用 **pgvector HNSW + Apache AGE + NetworkX** 的 GraphRAG 融合方案。

### 2.5 Agentic execution 路线

随着外部执行型 Agent 的兴起，AI 系统不再局限于"生成文字"，而开始具备调用工具、执行流程、产出结果并返回状态的能力。

**技术分析**：当前主流 Agent 框架（如 LangChain Agent、AutoGPT、CrewAI）更关注通用执行能力，对安全边界和信任评估的内建支持相对薄弱。在教育场景中，这意味着不加治理地引入执行能力会带来不可解释和不可控的风险。

**星火的判断**：不能简单复制通用执行型 Agent 的设计，而需要增加执行意图结构化（`ExecutionIntent`）、执行边界划分（`ExecutionRouter`）、审批确认和结果可信度评估（`TrustEngine`）。这也是星火将 OpenClaw 接入时重点补上的治理层。

## 3 技术方案

### 3.1 技术方向

星火的技术方向是构建一套 **AI-native 的学习成长系统**。这里的关键不是"AI 多不多"，而是系统是否围绕长期成长链条组织。具体技术方向判断标准：

1. **能否持续感知用户状态**——而不是只响应当前输入。→ 认知核 + 贝叶斯画像
2. **能否把目标转成可执行链路**——而不是只生成建议。→ 执行核 + LangGraph 规划
3. **能否理解知识结构**——而不是只做文本检索。→ GraphRAG + 知识星图
4. **能否在复杂问题中协作求解**——而不是只靠单次生成。→ Mirofish 多 Agent
5. **能否将结果回流进画像和后续策略**——而不是一次性交付。→ 回流链路 + 报告/剧场

最终选择的是**"异构架构 + 双核编排 + 多 Agent 协作 + GraphRAG + 外部执行闭环"**的组合路线。

### 3.2 技术选择

#### 3.2.1 为什么采用三层异构架构

星火使用 Flutter 负责移动端表现层，Go Gateway 负责接入层与高并发长连接，Python AI Engine 负责智能编排与知识处理。

**技术论证**：

| 场景需求 | 技术挑战 | 选型 | 关键优势 |
|---------|---------|------|---------|
| 移动端跨平台 UI + 多感官反馈 | 高性能渲染 + 平台特性调用 | Flutter 3.x + Riverpod | 单代码库 iOS/Android；GLSL Shader 支持；热重载 |
| 高并发 WebSocket 长连接 + 鉴权 | C10K 级连接管理 | Go 1.24 + Gin + Gorilla | Goroutine 轻量并发；JWT 鉴权；CQRS 事件总线 |
| AI 编排 + 知识推理 + 模型接入 | 快速迭代 + 丰富 AI 生态 | Python 3.11 + gRPC + LangGraph | LangGraph 状态机；LLM 路由；Celery 异步队列 |
| 跨语言 API 契约 | 类型安全 + 版本管理 | Protobuf + buf.build | 三端类型安全；向后兼容检查 |

异构拆分让三类任务都运行在更适合自己的技术栈中，同时通过 Protobuf 契约确保跨语言通信的类型安全。

#### 3.2.2 为什么采用双核编排

**认知核（Cognitive Core）**：
- `PersistentBayesianLearner`：贝叶斯认知建模，追踪逻辑偏好、记忆强度、好奇心、语言习惯
- `MultiDimensionalLearner`：多维能力图谱，不仅看结果更看解题思路
- `CognitivePrism`：认知棱镜，整合情绪/动机/状态理解
- `auto_optimizer.py`：根据用户采纳率自动调整语调和难度

**执行核（Execution Core）**：
- `SufficiencyChecker`：意图驱动的信息充分性检查，字段要求矩阵（required / clarify_if_missing / can_infer）
- `LangGraphPlanner`：规划阶段不执行工具，生成 `ExecutablePlan` 后交由执行层，明确区分 PONR_TOOLS 和 CREATOR_TOOLS
- `ExecutionRouter` + `TrustEngine`：执行边界划分与信任评估
- `adaptive_replanner.py`：动态重规划，根据执行反馈持续修正计划

**主编排器**（`ChatOrchestrator`，1619 行）采用模块化 Mixin 架构：

```
ChatOrchestrator = ContextBuilderMixin    # 上下文构建
                 + RoutingEngineMixin     # 意图路由
                 + ValidationEngineMixin  # 充分性检查
                 + SessionStateMixin      # 会话状态
                 + ExecutionEngineMixin   # 执行引擎
                 + ResponseBuilderMixin   # 响应构建
                 + PersistenceLayerMixin  # 持久化
                 + ObservabilityMixin     # 可观测性
```

这样做的原因在于，长期个性化和短期任务推进是两种不同的问题：前者强调连续建模，后者强调当前动作和边界控制。如果混为一体，系统很容易在"像你"与"能推进"之间顾此失彼。

#### 3.2.3 为什么采用 Mirofish 多 Agent

**架构设计**：基于 LangGraph StateGraph 构建，包含 11 个专家节点，由 `GraphExpertSpec` 数据类注册，通过 `create_specialist_node()` 工厂函数自动创建。

**工作流编排**：
- **标准图**（`sparkle_graph`）：Router → 专家节点 → ToolNode → Router（循环），支持 `human_node` 中断
- **规划图**（`sparkle_planning_graph`）：规划阶段不执行工具，生成 `ExecutablePlan` 后交由执行层
- **协作图**（Phase 3）：`collaboration_node`（922 行）+ `aggregator_node` 实现多 Agent 协作

**五种协作模式**：single / sequential / parallel / debate / delegation

**工具注册表**（Agent 可调用）：`query_knowledge`、`create_knowledge_node`、`link_nodes`、`create_plan`、`generate_tasks_for_plan`、`create_task`、`batch_create_tasks`、`suggest_focus_session`、`record_error`、`query_error_history`

**审核反馈环**：`reset_collaboration_node` 在 modify/reject 时触发重规划，保存历史协作上下文避免重复提问。

#### 3.2.4 为什么采用 GraphRAG 与知识星图

**双模检索架构**：

| 检索模式 | 技术实现 | 优势 | 局限 |
|---------|---------|------|------|
| 向量语义检索 | pgvector HNSW 索引 | 语义灵活、召回广 | 无法表达图结构关系 |
| 图结构检索 | Apache AGE + NetworkX | 路径推理、前置依赖 | 缺少语义灵活性 |
| **GraphRAG 融合** | 向量 + 图 + 用户兴趣节点 | **两者优势组合** | 工程复杂度更高 |

**GraphReasoningService**（436 行）核心算法：
- 路径生成：Dijkstra 变体，融合节点掌握度权重
- 循环检测：预处理禁止闭合回路
- 个性化：融合用户兴趣节点 + 关系强度（related / application / evolution / composition 四种关系类型）
- 缓存策略：图结构 pickle protocol 5 序列化存储，节点/边变更时自动失效（`invalidate_cache`）

**AgeClient**（394 行）核心能力：异步连接池管理（asyncpg）、Cypher 查询构建器、图谱/顶点/边标签 CRUD 操作、自动 SQL 注入防护。

**RetrievalTrace**：记录每次检索的节点信息、关系信息、检索方法详情和性能指标，实现检索过程完全可解释、可审查。

#### 3.2.5 为什么采用 OpenClaw 执行闭环

**分阶段架构**（Phase 0 → Phase 4）：

| 阶段 | 职责 | 核心组件 | 代码规模 |
|------|------|---------|---------|
| Phase 0 | 路由决策 | `ExecutionRouter` | HUMAN_ONLY / AGENT_ELIGIBLE 分类 |
| Phase 1 | 意图构建 | `ExecutionIntent` 模型 | execution_mode / target_env / policy |
| Phase 2 | 请求翻译 | `IntentTranslator` | 翻译为 OpenClaw 请求格式 |
| Phase 3 | 执行与信任 | OpenClaw Client + `TrustEngine` | HTTP/WS 双传输 + 三级信任评估 |
| Phase 4 | 结果摄取 | `ExecutionIngestor` + `ExecutionLearningService` | 知识图谱更新 + 后续任务触发 |

**ExecutionIntent 生命周期**：`DRAFT → READY → DISPATCHED → RUNNING → WAITING_APPROVAL → SUCCEEDED / FAILED / HANDED_BACK`

**传输层**：支持 `responses_http`（HTTP POST `/v1/responses`）和 `gateway_ws`（实时 WebSocket 双向通信，支持节点调用 + 审批回传）

**信任评估公式**：`quality_score = (validation_ratio × 0.4) + (criteria_met × 0.4) + (completeness × 0.2)`

#### 3.2.6 为什么保留多感官与成长反馈层

对于长期学习系统而言，体验层并不是可有可无的装饰：

- **BGM 服务**：路由感知切换，20+ 场景 track，route > stage > component 三级优先级
- **触觉反馈**：`SensoryFeedbackService` 管理触觉与音效预算
- **视觉系统**：GLSL Shader 星图、Design System V2（SparkleMaterial / NeoGlass / Ceramic）
- **成就系统**：`AchievementEngine` 支持 20+ 事件类型，包含 SparkContract 学习契约、UserStreakStats 连胜统计、UserGalaxySkin 星图皮肤解锁
- **学习报告**：`LearningReportAgent` 使用工具链（query_mastery_scores、query_error_patterns、query_study_timeline、interview_learner、infer_learning_state_from_chat）生成五维度分析报告

技术方案如果只强调"能算"，却不强调"能被长期使用"，最终仍然不成立。

## 4 技术实践

### 4.1 使用的开发框架及依赖的库

星火当前技术栈核心组合：

**移动端**：
- Flutter 3.x + Riverpod 2.x：状态管理、交互构建和设计系统
- Feature-First 架构：模块独立，可单独开发和测试
- GLSL Shader：知识星图视觉渲染

**接入层**：
- Go 1.24 + Gin 框架：HTTP/WebSocket API 网关
- Gorilla WebSocket：高并发长连接管理
- sqlc + pgxpool：类型安全数据库访问（默认 10 连接池）
- CQRS 事件总线（`redis_bus.go`）：Command Query Responsibility Segregation

**智能层**：
- Python 3.11 + gRPC：主编排器与服务间通信
- LangGraph：FSM 状态机 + 黑板模式（Blackboard State）+ 检查点机制
- LangChain：LLM 抽象层
- Celery + Redis：异步任务队列（文档解析、知识摘要等耗时操作）

**数据层**：
- PostgreSQL 16+ with pgvector：关系型 + 向量化存储（HNSW 索引）
- Redis 7+：会话缓存、LangGraph 检查点、RunLedger 追踪日志、BGM 偏好、任务队列
- MinIO / S3：用户上传文件、头像、知识文档

**可观测性**：
- Prometheus：指标采集（TOKEN_USAGE、execution_mode_decisions 等）
- OpenTelemetry：全链路分布式追踪（自动 trace_id 注入、gRPC 拦截器、DB 查询追踪）
- RunLedger：Redis 后端统一控制塔（trace_id 粒度追踪请求生命周期）

**LLM 路由**：
- `LLMRouter`：支持 Qwen（默认 qwen-plus）、DeepSeek（reasoning model）、OpenAI、小米、Hunyuan、Zhipu
- 分层策略：TaskType → AgentRole → ModelTier

**协议**：
- Protobuf + buf.build：Go/Python/Dart 三端代码生成，类型安全跨语言通信
- Proto 文件：`agent_service.proto`（主 Agent RPC）、`galaxy_service.proto`（知识图谱）、`error_book.proto`（错题本）、`websocket.proto`（WebSocket 消息类型）

### 4.2 技术实践过程

#### 4.2.1 主链编排实践

系统以 `ChatOrchestrator` 为主编排器，将上下文构建、意图识别、充分性检查、路由决策、计划生成、执行结果汇总、会话持久化和可观测性串成统一主链。

**关键设计决策**：
- 采用 8 个 Mixin 组合而非单体类，实现关注点彻底分离
- 意图识别采用 `UnifiedIntentRouter`（快路径）+ BERT 意图分类器（`bert_intent_classifier.py`）双层策略
- 会话反馈信号（`SessionFeedbackSignal`）具备检测、应用、计数和置信度四个维度
- 对话节奏感知（`analyze_conversation_rhythm`）动态调整响应策略

这一做法的意义在于，主链依赖的是结构化工作流，而不是一段超长提示词。

#### 4.2.2 Mirofish 多 Agent 实践

Mirofish 的实践经历了从基础 Router 到专家节点，再到协作节点、聚合节点和重规划逻辑的逐步演进：

1. **Phase 0**：Router + 单专家节点响应
2. **Phase 1**：11 专家注册 + 工具调用
3. **Phase 2**：`collaboration_node`（922 行）实现 5 种协作模式
4. **Phase 3**：`aggregator_node` 统一结果融合 + `reset_collaboration_node` 审核反馈环

**Aggregator 节点职责**：收集所有 Agent 的 tool_calls → 去重 + 排序后统一执行 → 支持 parallel/debate/delegation 结果融合 → 智能生成最终响应草稿。

系统在专家注册层显式定义角色边界，在工作流层区分协作模式，在聚合层负责统一结果输出。这意味着 Mirofish 不是"多起几个模型实例"，而是一个具备角色管理、协作模式和结果整合的专门框架。

#### 4.2.3 OpenClaw 集成实践

OpenClaw 的接入按 **Phase 0 到 Phase 4** 分阶段推进：

- **Phase 0**（路由层）：`ExecutionRouter` 实现 HUMAN_ONLY（运动/付款/密码等不可自动化任务）和 AGENT_ELIGIBLE（PLANNING/SOCIAL/OCR 等可委派任务）分类
- **Phase 1**（意图层）：`ExecutionIntent` SQLAlchemy 模型，包含 execution_mode、target_env、trust_level、policy 完整字段
- **Phase 2**（翻译层）：`IntentTranslator` 将 ExecutionIntent 翻译为 OpenClaw 请求格式
- **Phase 3**（执行层）：OpenClaw HTTP/WS 客户端（execute、resolve_approval、cancel_run、health_check、list_nodes、invoke_node），配合 `TrustEngine` 三级信任评估
- **Phase 4**（摄取层）：`ExecutionIngestor` 结果摄取 + `ExecutionLearningService` 学习服务 + 知识图谱更新

这种逐阶段推进方式使系统更容易被验证，也使比赛文档可以清晰呈现技术演进脉络。每个 Phase 都有独立的测试文件（`test_openclaw_phase0/1/2/3/4.py`）。

#### 4.2.4 图推理与 GraphRAG 实践

星火通过三层架构维护知识图结构：

1. **持久层**：Apache AGE 图数据库（`AgeClient`，394 行）—— Cypher 查询构建器、asyncpg 异步连接池、自动 SQL 注入防护
2. **推理层**：NetworkX 内存图（`GraphReasoningService`，436 行）—— Dijkstra 变体路径生成、循环检测、个性化权重
3. **缓存层**：Redis（pickle protocol 5，TTL 300s）—— 热加载、节点/边变更时自动失效

**GraphRAG 检索流程**：向量语义检索 → 图结构检索 → 用户兴趣节点融合 → `RetrievalTrace` 全程记录 → 结果排序与返回

知识星图、剧场和报告系统都建立在这条基础设施之上，形成知识组织的统一底座。

#### 4.2.5 反馈与体验系统实践

学习报告、知识剧场、学习模拟、成就系统与多感官反馈并非后期装饰，而是从一开始就被视为主链的反馈层：

- **学习报告**：`LearningReportAgent` 使用 5 个工具（掌握度分析、错题模式、学习时间线、学习者访谈、对话推断），生成多维度分析结果，Flutter 端 `MasteryRadarChart` 雷达图可视化
- **知识剧场**：`PredictionTheaterService` 基于知识图谱推理生成多条路径预测，`PredictionAccuracyTracker` 持续追踪预测准确度
- **学习模拟**：`SimulationEngine` 支持 8 种场景模板，每个 `AgentParticipant` 独立记忆/策略/立场，会话持久化 Redis TTL 6h
- **Mirofish 桥接**：Chat → Theater / Simulation / Report 无缝跳转，通过 WebSocket metadata 的 `open_theater / open_simulation / open_report` flag 实现

技术实践中，这些模块与聊天、图谱、任务、执行结果共享状态与上下文，保证用户在不同页面间看到的是同一条成长链。
