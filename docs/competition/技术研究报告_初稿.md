## 1 问题聚焦

### 1.1 问题描述

传统 AI 学习工具通常只能完成局部任务：要么回答问题，要么安排时间，要么记录笔记。但大学生真实学习过程是一个连续系统，用户的意图、状态、知识盲区、执行能力和反馈信息会不断变化。如果系统不能同时理解这些变化，就很难在长链路中持续有效。

星火面对的核心问题不是“如何让模型回答更像老师”，而是“如何构建一套既理解用户状态，又能把学习目标持续推进下去的 AI 学习系统”。

### 1.2 问题抽象

从技术角度看，这个问题可以被抽象为四个子问题：

1. 如何稳定感知用户当前的任务背景、知识状态和认知偏好。
2. 如何把自然语言目标拆解成可执行计划，并根据执行结果持续修正。
3. 如何让知识检索不仅返回相似文本，还能体现知识结构和学习路径。
4. 如何让系统在复杂协作和外部执行中保持安全、可解释和可追踪。

### 1.3 问题定位

现有方案大致有三类局限。

第一类是“纯聊天型”方案，长于自然语言生成，短于连续执行。

第二类是“纯工具型”方案，长于任务管理，短于认知理解与个性化。

第三类是“纯内容型”方案，长于资源供给，短于状态感知和任务闭环。

星火的定位是把这三类能力整合成一套面向大学生的 AI 学习成长系统，通过架构、编排和数据流把它们真正打通。

### 1.4 问题评估

在大学学习场景中，用户面对的不确定性很高：学习任务常常目标大、时间碎片化、知识关联强、情绪波动大。如果系统只在局部节点发挥作用，整体体验就会断裂。因此，星火必须是一套“能连续工作”的系统，而不能只是功能集合。

本项目的技术评估重点不在单个模块是否先进，而在整条学习主链是否可解释、可扩展、可验证。

### 1.5 问题分解

围绕上述问题，星火把系统分解为以下几条技术主线：

1. 三层异构架构：Flutter、Go Gateway、Python AI Engine。
2. 双核编排：认知核与执行核协同。
3. 多 Agent 协作系统：面向复杂学习问题的专家分工。
4. GraphRAG 与知识星图：面向学习路径与知识结构的检索增强。
5. OpenClaw 执行闭环：让 AI 进入真实执行阶段。
6. 报告、剧场、模拟与多感官体验：把结果反馈做成持续产品能力。

## 2 相关工作

### 2.1 多 Agent 编排相关工作

近年来，大模型应用逐步从单轮问答走向 Agent 工作流，但很多实现仍停留在“多个角色共用同一个上下文”的浅层协作。星火在此基础上进一步强调：

1. 专家注册表与节点级分工。
2. 串行、并行、辩论、委派等协作模式。
3. 规划图与执行图分离，避免规划阶段误触工具。

这使得多 Agent 不只是展示形式，而真正成为复杂学习任务的组织方式。

### 2.2 检索增强相关工作

传统 RAG 更擅长从大规模文本中寻找语义相似片段，但教育场景除了“像不像”，还非常依赖“前置关系、递进关系和路径顺序”。星火因此采用 GraphRAG 与知识星图结合的方式，把向量检索和图结构推理放入同一条主链。

### 2.3 外部执行相关工作

很多学习型产品在生成计划后就停下了，真正执行仍由用户手动承担。星火引入 OpenClaw 作为外部 AI 执行引擎，把部分数字世界任务委派给外部执行器，同时通过结构化协议、审批策略和信任评估确保系统安全。这使得“学习系统”第一次具备了更接近实际行动的闭环推进能力。

## 3 技术方案

### 3.1 技术方向

星火的技术方向不是“把若干 AI 功能塞进 App”，而是构建一套 AI-native 的学习成长系统。为此，我们选择了“异构架构 + 双核编排 + 多 Agent 协作 + GraphRAG + 外部执行闭环”的组合路线。

### 3.2 技术选择

#### 3.2.1 三层异构架构

星火使用 Flutter 作为移动端表现层，Go Gateway 作为高并发接入层，Python AI Engine 作为智能层。这样做的原因是：

1. Flutter 适合统一多平台 UI 与沉浸式交互体验。
2. Go 更适合处理长连接、鉴权、协议转换与高并发 IO。
3. Python 在 AI 编排、模型接入、知识处理和实验迭代方面效率更高。

这种分层使每一层都能做自己最擅长的事情，并为后续扩展提供清晰边界。

#### 3.2.2 双核编排与主编排器

星火采用认知核与执行核协作的方式组织能力。认知核关注用户画像、记忆、认知节奏和情绪动机；执行核关注充分性检查、计划生成、工具调用、审批确认和结果回流。Python 侧的 `ChatOrchestrator` 负责把这些能力串成统一主链。

#### 3.2.3 Mirofish 多 Agent 系统

针对学习问题经常跨知识解释、时间规划、错误分析和策略建议等多个维度的特点，星火选择以 LangGraph StateGraph 构建多 Agent 协作图，让不同专家节点各自承担专门任务，再由聚合节点统一输出。

#### 3.2.4 GraphRAG 与知识星图

GraphRAG 负责语义相似和关系推理双路检索，知识星图负责把节点、关系和掌握度可视化。用户因此不只是获得“答案”，还获得“结构化路径和下一步建议”。

#### 3.2.5 OpenClaw 执行闭环

OpenClaw 被定义为星火的外部 AI 执行引擎。系统通过 `ExecutionIntent` 对任务进行结构化描述，再由 `ExecutionRouter` 判断哪些任务适合交给外部执行器，最后使用 `TrustEngine` 对执行结果进行信任等级评估。这样既保留了执行能力，又避免不受控的旁路写入。

### 3.3 结果期望

星火对技术方案的期望主要体现在四个方面：

1. 形成稳定的学习主链，不再停留在单轮问答。
2. 在复杂学习场景中实现更强的可解释性和协作能力。
3. 在知识检索与路径规划上明显优于纯文本检索方案。
4. 在移动端保持可用、可感、可演示的产品体验。

## 4 技术实践

### 4.1 使用的开发框架及依赖的库

星火当前技术栈以以下组合为核心：

1. Flutter + Riverpod：移动端状态管理与 UI 架构。
2. Go + Gin + Gorilla WebSocket：接入层、实时通信与 API 网关。
3. Python + gRPC + LangGraph：智能编排与服务逻辑。
4. PostgreSQL + pgvector + Redis + MinIO：结构化、向量化、缓存与对象存储。
5. Prometheus + OpenTelemetry：可观测性与链路追踪。

### 4.2 技术实践过程

#### 4.2.1 主链编排的实践

系统在 Python 侧形成了以 `ChatOrchestrator` 为中心的主编排器，将上下文、路由、验证、会话、执行、持久化、可观测性组合成统一工作流。这保证了系统不是靠“单个大 prompt”运转，而是靠稳定的编排结构运转。

#### 4.2.2 多 Agent 协作的实践

星火把学习任务按专家分工组织进 StateGraph。规划阶段与执行阶段分离，协作过程中既支持单专家快速响应，也支持多专家串并行协作与聚合。这使系统能够在不同复杂度问题之间灵活切换。

#### 4.2.3 OpenClaw 闭环的实践

OpenClaw 集成并不是一次性接通，而是按 Phase 0 到 Phase 4 逐步推进，先做路由，再做协议，再做翻译，再做执行，再做结果回流与信任评估。这种阶段式推进方式提高了可验证性，也便于在比赛中清晰讲述技术演进逻辑。

#### 4.2.4 知识图谱与图推理的实践

星火通过 GraphReasoningService、AgeClient 和图结构缓存机制，在数据库与内存之间维护学习路径所需的数据结构。它既支撑剧场、报告、路径推理等高层能力，也服务于知识星图的日常交互。
