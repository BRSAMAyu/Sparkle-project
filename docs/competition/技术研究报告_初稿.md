## 1 问题聚焦

### 1.1 问题描述

星火要解决的问题，不是“如何把一个聊天机器人包装成学习助手”，而是“如何构建一套能够持续理解大学生学习状态、组织知识结构、规划行动路径、推动任务执行并把结果沉淀回成长主链的 AI 学习成长系统”。

在中国大陆高校场景中，学生已经拥有大量数字化工具：课程平台可以提供课件与作业入口，搜题和 AI 问答产品可以提供即时解释，专注和待办产品可以提供时间管理。但这些工具大多分工明确、彼此割裂。学生常常一边在课程平台找资料，一边在 AI 工具里提问，一边在待办或专注工具里记录计划，最后仍然会遇到三个核心问题：

1. 学习目标跨度大，系统很难把“补完一门课”“准备一场比赛”“完成一个项目”稳定拆成可执行路径。
2. 学习过程结构性强，系统不仅要回答问题，还要理解前置关系、掌握度变化和路径依赖。
3. 成长反馈周期慢，系统必须把一次次局部行为重新组织回长期状态，而不是让每一次交互都彼此孤立。

因此，星火面对的是一个典型的系统级问题，而不是单一算法问题。

### 1.2 问题抽象

从技术视角看，星火需要同时解决五层连续问题：

1. 感知层问题：系统如何识别用户当前目标、上下文、偏好、学习节奏和知识薄弱点。
2. 规划层问题：系统如何把模糊目标规范化，并转化为阶段计划、任务清单和下一步动作。
3. 知识层问题：系统如何把学习内容组织成可检索、可解释、可推理的结构，而不是散落在聊天记录中。
4. 协作层问题：系统如何在复杂任务下调度多个专家角色，并保证协作结果可聚合、可重规划。
5. 执行层问题：系统如何在可治理前提下把建议推进到执行，并把结果可信地回流到主链。

这五层并不是独立模块的简单串联，而是强依赖关系：状态理解失真，规划就会失真；知识结构不成立，路径推荐和薄弱点判断就会失真；执行回流做不好，前面的理解与规划就无法形成长期闭环。

### 1.3 问题定位

从研究对象上看，星火位于教育科技、AI-native 应用、知识组织系统与 Agent 系统交叉地带；从工程形态上看，它不是单一脚本或单端原型，而是一套由 Flutter 移动端、Go 接入层和 Python 智能层共同支撑的异构系统。

当前项目的真实工程规模如下：

| 工程维度 | 当前规模 |

| Python AI Engine 代码文件 | 728 个 |
| Python 测试文件 | 260 个 |

这决定了本项目的技术研究不能停留在“某个模型选型是否先进”，而必须回答以下问题：为什么要采用异构架构、为什么需要图谱与 GraphRAG、为什么复杂任务要用多 Agent、为什么执行能力必须带治理边界、以及这些设计为什么值得工程化实现。

### 1.4 问题评估

综合业务特征与工程形态，星火的技术问题具有以下五个突出特征：

#### 长链路特征

一个真实的学习目标常常跨越多轮对话、多次任务、多段页面操作和多天行为记录。系统不能只在单轮问答里聪明，而必须在长链路中保持状态一致性。

#### 强结构特征

学习问题不仅涉及语义相关性，还涉及前置依赖、层级关系、掌握度变化和路径分叉。这意味着单纯依赖向量相似度不足以支撑完整的学习路径问题。

#### 强耦合特征

状态感知、计划生成、图谱检索、多 Agent 协作、执行回流之间存在明显的前后依赖。任何一层过于粗糙，都会降低整条主链的可靠性。

#### 治理约束特征

一旦系统从“回答问题”进入“推动执行”，就必须处理执行边界、权限、可信度、回滚与人工接管问题。这使得星火不能直接套用通用 Agent 的激进方案。

#### 工程复杂度特征

项目既要照顾移动端交互体验，又要保证网关层高并发接入，还要承载 AI 编排、图谱、协作、执行和多感官反馈等复杂能力，因此对架构拆分、协议边界和测试体系都有较高要求。

### 1.5 问题分解

根据问题规模和实际工程复杂度，星火将整体问题进一步拆分为 20 个相互依赖的子问题。每个子问题都需要独立处理，又必须在主链中共同成立。

| 子问题 | 主要目标 | 技术难点 | 难度等级 | 前置依赖 | 对应模块 |
|------|------|------|------|------|------|
| 用户意图识别 | 判断当前输入属于问答、规划、图谱、协作或执行场景 | 用户表达自然、歧义高、场景切换频繁 | 中 | 无 | AI 对话与主链编排 |
| 用户状态建模 | 识别用户目标、学科、节奏、偏好和当前状态 | 状态来源分散且动态变化 | 高 | 无 | AI 对话与主链编排 |
| 长短期记忆管理 | 在多轮会话中保留必要上下文并抑制噪声 | 上下文膨胀、记忆漂移、成本控制 | 高 | 用户状态建模 | AI 对话与主链编排 |
| 信息充分性检查与澄清 | 判断信息是否足够生成可靠结果 | 追问过多会打断体验，追问过少会导致结果失真 | 高 | 用户状态建模 | AI 对话与主链编排 |

| 阶段计划生成 | 形成阶段目标、里程碑和计划节点 | 计划既要合理又要可落地 | 高 | 目标规范化 | 学习规划与任务执行 |
| 任务拆解与粒度控制 | 把计划拆成足够细且不失真 的执行任务 | 粒度过粗难执行，粒度过细会增加负担 | 高 | 阶段计划生成 | 学习规划与任务执行 |
| 任务状态追踪与回流 | 让执行结果能持续影响计划与反馈 | 状态来源多、回流时机复杂 | 中 | 任务拆解 | 学习规划与任务执行 |
| 知识节点抽取 | 从资料、对话和学习行为中抽取知识单元 | 节点定义不稳定，学科差异大 | 高 | 用户状态建模 | 知识星图与 GraphRAG |
| 知识关系构建与演化 | 建立前置、并列、应用、迁移等关系并动态更新 | 关系类型复杂且会持续变化 | 高 | 知识节点抽取 | 知识星图与 GraphRAG |
| GraphRAG 混合召回 | 融合向量检索与图关系检索 | 需要兼顾语义相关性与结构可解释性 | 高 | 节点与关系构建 | 知识星图与 GraphRAG |
| 路径推理与掌握度估计 | 计算推荐路径、薄弱点和掌握状态 | 需要同时建模用户状态、图关系和历史行为 | 高 | GraphRAG 混合召回 | 知识星图与 GraphRAG |
| 多 Agent 触发判定 | 决定问题是否值得进入协作链路 | 误触发会增加成本，不触发又会损失深度 | 中 | 意图识别、充分性检查 | Mirofish 多 Agent 协作 |
| 专家路由与协作模式选择 | 为问题选择合适专家和协作方式 | 问题复杂度高、模式选择空间大 | 高 | 多 Agent 触发判定 | Mirofish 多 Agent 协作 |
| 聚合、冲突消解与重规划 | 合并多专家结果并处理分歧 | 输出冲突、顺序依赖和重规划触发条件复杂 | 高 | 专家路由 | Mirofish 多 Agent 协作 |
| ExecutionIntent 结构化表达 | 把任务表达成可执行、可治理的协议对象 | 既要表达动作，也要表达边界、风险和策略 | 高 | 任务拆解 | OpenClaw 执行闭环 |

| 跨端协议与异构系统协同 | 让移动端、网关和 AI 引擎稳定配合 | 协议转换、状态一致性和链路追踪复杂 | 中 | 无 | AI 对话与主链编排 / 网关层 |
| 多感官反馈编排与端侧体验协调 | 让音频、触觉、通知与主链状态协同 | 设备能力差异、路由切换和降级策略复杂 | 中 | 任务回流、成长反馈 | 成就契约与成长反馈 / BGM 与多感官体验 |

## 2 相关工作

### 2.1 GraphRAG 与图增强检索路线（2024）

2024 年以来，GraphRAG 路线逐步受到重视，其核心思想是把文档与知识点组织成图结构，在检索阶段同时利用语义相似与关系推理能力。相比只做向量召回的传统 RAG，GraphRAG 更适合处理“前置关系”“路径选择”“全局摘要”这类结构性任务。

这一技术路线对星火的重要性在于：学习问题天然带有前置依赖和路径关系。如果系统只会“找到相似内容”，就很难稳定支持路径推荐、薄弱点定位和知识星图可视化。因此，星火吸收 GraphRAG 路线的核心思想，但把它进一步落到学习图谱、掌握度和路径生成上。

### 2.2 LangGraph / Agentic Workflow 路线（2024-2025）

近两年，LangGraph 和各类 agentic workflow 框架逐步把 Agent 系统从“单次工具调用”推进到“有状态工作流编排”。这类方案强调状态机、节点图、检查点、回溯与多步骤决策，使复杂任务不再依赖单段提示词硬撑。

这一路线对星火非常关键，因为星火的复杂度不在某个单点能力，而在多条能力链需要长期协同。Mirofish 多 Agent、主链编排、执行回流都更适合建立在显式工作流之上，而不是建立在不可控的提示词堆叠之上。

### 2.3 Socratic Tutoring 与学习对话增强路线（2025）

以 ChatGPT Study Mode、Khanmigo 为代表的路线，强调通过启发式提问、分步讲解、因材施教式引导来改善学习体验。它们证明了一个重要事实：相比直接给答案，AI 如果能够引导学生思考，学习体验和理解深度会更好。

不过，这类路线的核心单元仍然通常是“对话回合”。它能把“怎么解释”做得很好，却不天然等于“怎么形成长期成长系统”。星火吸收这一路线中的澄清、引导和分步解释思路，但把问题继续向长期状态、知识结构与执行推进推进。

### 2.4 中国大陆 AI 辅学与搜题路线（2024-2026）

国内近三年非常活跃的一条路线，是围绕搜题、答疑、作业辅导、学习资料处理和学习机能力展开的 AI 辅学系统。夸克、作业帮、小猿搜题、有道小P、科大讯飞 AI 学习机、学而思学习机等产品，都在即时答疑、错因分析、题目讲解、学情反馈或个性化辅学方面积累了大量实践。

这一路线的重要意义在于，它证明了学生对“低门槛获得帮助”和“更快纠错”的强需求；但它也暴露出明显边界：多数方案仍然围绕“问题求解”或“单次学习支持”，较少处理跨周、跨模块、跨目标的长期学习成长系统。星火的设计重点，正是把这种局部强能力继续组织为完整主链。

### 2.5 执行型 Agent 与可信治理路线（2024-2026）

随着 Agent 逐步具备调用工具、发起操作、执行流程的能力，执行型 Agent 路线开始快速发展。但在教育场景中，执行能力越强，治理要求也越高。若系统不能判断执行边界、不能保留审批与拒绝机制、不能评价结果可信度，能力增强就可能直接转化为风险增强。

因此，星火没有简单复用“会调工具的 Agent”方案，而是在接入 OpenClaw 时增加了 `ExecutionIntent`、执行路由、`TrustEngine`、人工接管与结果回流机制，形成一条更适合学习场景的保守型执行路线。

## 3 技术方案

### 3.1 技术方向

针对上述问题，星火选择的不是“更换一个更强的大模型”这类单点思路，而是采用以下总体技术方向：

1. 以异构架构解决不同层级的职责冲突，用 Flutter 负责端侧体验，用 Go 负责高并发接入，用 Python 负责 AI 编排和复杂推理。
2. 以显式主链解决学习过程连续性问题，而不是让能力散落在独立页面和独立服务中。
3. 以知识星图和 GraphRAG 解决结构化学习问题，而不是只做语义检索。
4. 以 Mirofish 多 Agent 解决复杂任务处理问题，而不是把所有复杂度都压给单个模型。
5. 以 OpenClaw 治理化执行闭环解决“建议无法落地”的问题，而不是停留在说明层。

### 3.2 技术选择

围绕上述方向，星火形成了如下关键技术选择：

| 问题类型 | 备选思路 | 最终选择 | 选择原因 |
|------|------|------|------|
| 移动端交互与体验 | Web 单页 / 原生双端 / Flutter | Flutter | 更适合快速构建统一体验，并承载图谱、多感官和动画交互 |
| 高并发接入与协议桥接 | Python 直连 / Node.js 网关 / Go 网关 | Go Gateway | 更适合长连接、协议管理、鉴权和高并发接入 |
| AI 编排核心 | 单体接口层 / Python AI Engine | Python AI Engine | 更适合 LLM 调度、图推理、Agent 编排和异步任务 |
| 知识组织 | 纯向量库 / 文本缓存 / 图谱 + 向量混合 | 知识星图 + pgvector + GraphRAG | 同时兼顾语义召回与结构关系 |
| 复杂问题处理 | 单模型直接回答 | Mirofish 多 Agent | 更适合复杂任务拆解、协作和聚合 |
| 执行推进 | 普通工具调用 | OpenClaw + ExecutionIntent + TrustEngine | 具备边界治理、可信评估和结果回流能力 |
| 多端状态一致性 | 页面级局部状态 | 主链状态 + 统一协议 | 便于计划、任务、图谱、执行与反馈联动 |

### 3.3 结果期望

本项目采用上述技术方案后的预期结果，应当是合理、可行、可逐步验证的，而不是脱离现实的理想化承诺。

| 期望类型 | 合理预期 |
|------|------|
| 功能期望 | 在同一系统内打通“对话澄清 -> 计划生成 -> 任务拆解 -> 知识组织 -> 执行回流 -> 成长反馈”的完整主链 |
| 技术期望 | 形成知识星图、GraphRAG、Mirofish、OpenClaw 四条关键能力链，并使它们在主链中发生协同 |
| 工程期望 | 在本地完整环境中达到可稳定演示、可专项回归、可持续扩展的状态，而不是停留在单次演示脚本 |
| 性能期望 | 在当前阈值体系下，主链入口、充分性检查、路由和主要检索能力满足比赛演示所需的响应要求，不出现明显卡顿或失控 |
| 质量期望 | 关键模块具备测试、验收或专项回归材料支撑，对仍待补强的真机能力保持诚实口径 |

进一步说，本项目的技术目标不是“一次性把所有能力做到工业化量产水平”，而是“让关键主链真实成立，让创新模块真实落地，让工程证据真实可信”。对于学生团队参赛项目而言，这样的预期既可实现，也更符合评审对技术成熟度的判断标准。

## 4 技术实践

### 4.1 使用的开发框架及依赖的库

| 层级 | 主要技术栈 | 主要职责 |
|------|------|------|
| 移动端 | Flutter、Riverpod、Dio、音频/动效相关组件 | UI、状态管理、多感官反馈、页面交互 |
| 接入层 | Go、Gin、Gorilla WebSocket、gRPC | 鉴权、长连接管理、协议转换、实时接入 |
| 智能层 | Python、FastAPI、gRPC、LangGraph、Celery | 主链编排、图推理、多 Agent、执行闭环 |
| 数据层 | PostgreSQL、pgvector、Redis、MinIO | 关系数据、向量检索、缓存、对象存储 |

### 4.2 技术实践过程

星火的技术实践不是一次性完成的，而是沿着“先主链、再结构、后增强、最后收口”的顺序逐步推进：

1. 第一阶段先打通 Flutter、Go Gateway、Python AI Engine 的异构主链，解决消息链路和协议边界问题。
2. 第二阶段补齐计划、任务、知识节点、知识关系和主链回流，解决学习过程不再停留在聊天记录中的问题。
3. 第三阶段接入 Mirofish 多 Agent 和 OpenClaw 执行闭环，解决复杂任务分析与建议落地问题。
4. 第四阶段补齐学习报告、知识剧场、学习模拟、成就契约和多感官体验，让系统从“会做事”进一步走向“会陪伴成长”。
5. 第五阶段围绕 benchmark、测试、验收、from-zero rebuild 和演示链路进行收口，保证项目不仅能开发出来，也能稳定展示和验证。

技术实践中的关键决策有三点：

1. 对关键能力采取显式建模，而不是让复杂行为全部藏在提示词中。
2. 对复杂链路采取分阶段落地和分阶段测试，降低调试成本。
3. 对执行能力和端侧体验保留清晰边界，不用夸张演示替代真实稳定性。

## 5 结果验证

### 5.1 性能验证数据

当前项目已经建立一套偏保守的性能阈值验证方式。其目标不是追求脱离场景的极限分数，而是确保比赛展示链路足够稳定、主要交互环节没有明显阻塞。

| 验证项 | 当前口径 |
|------|------|
| 高频意图识别 | 已建立 `P50 < 10ms、P95 < 25ms` 的阈值型测试口径 |
| 充分性检查 | 已建立 `P50 < 50ms` 的阈值型口径 |
| 路由与吞吐 | 已建立 `P95 < 100ms` 以及吞吐 benchmark 口径 |
| 向量 / 图相关能力 | 已有专项 benchmark 和性能脚本用于回归 |

这些数据的意义不在于“分数多漂亮”，而在于证明星火的关键入口和关键链路已经形成可重复验证的性能边界。

### 5.2 测试覆盖验证

项目当前的测试覆盖已经不只针对“聊天能否跑通”，而是覆盖了多条创新主链：

1. Python 侧已有 260 个测试文件，覆盖编排、图谱、执行、报告等关键逻辑。
2. Go 侧已有 30 个测试文件，覆盖接入层、数据库与性能相关链路。
3. Flutter 侧已有 110 个测试文件，覆盖组件、体验和关键页面回归。
4. 另有 29 个 benchmark / 性能相关文件，用于专项性能验证。

这说明星火不是依赖单次演示脚本的概念原型，而是已经具备一定工程回归能力的真实系统。

### 5.3 工程稳定性验证

除功能与性能外，项目还保留了多类系统级稳定性证据：

1. from-zero rebuild、fresh build、env-check、smoke 等工程闸门文档已经存在。
2. OpenClaw、Mirofish、Theater、Simulation、Learning Report 等专项能力已有独立验收或专项测试材料。
3. Flutter、Go Gateway 和 Python AI Engine 已形成相对稳定的接口边界和职责分层。
4. 数据库 schema、模块文档、开发文档和测试文档之间已经能形成交叉印证。

### 5.4 当前仍需补强的部分

为保证技术结论诚实，当前仍需补强的部分单列如下：

1. 真机音频、触觉、通知、系统分享和前后台恢复仍需进一步统一签收。
2. 个别高级多 Agent 场景仍可继续优化演示脚本和评审呈现方式。
3. 若总决赛需要更强的学术支撑，可在保持正文简洁的前提下补充尾注、论文与官方资料来源。
