## 1 项目概述

### 1.1 项目背景

随着生成式 AI 的普及，大学生获得信息和学习建议的门槛被大幅降低，但"知道怎么做"和"真正做下去"之间的鸿沟并没有自动消失。大量学习工具把注意力放在内容回答、资料组织或任务记录上，却很难真正帮助用户建立从目标、到路径、到执行、到反馈、再到长期成长沉淀的连续闭环。

中国在校大学生约 4400 万，在线教育市场 2025 年预测超过 6000 亿元，个性化 AI 学习赛道处于快速增长早期，竞争格局尚未定型。在这一背景下，星火选择从"学习成长系统"这一差异化方向切入，而非在搜题、资料加工等已趋饱和的方向上竞争。

星火希望解决的不是单一道题、单一页面或单一功能的优化问题，而是学习过程中的连续性问题：目标如何拆解，知识如何组织，执行如何推进，结果如何回流，成长如何可见。

### 1.2 项目定位

#### 1.2.1 应用场景

星火主要面向大学生日常自主学习场景，包括但不限于：

1. **期末复习与课程冲刺**：快速梳理知识结构，定位薄弱环节，生成针对性复习计划。
2. **竞赛准备与项目学习**：跨知识域任务拆解，多 Agent 协作深度分析，执行进度追踪。
3. **长周期知识体系构建**：知识星图渐进式点亮，遗忘曲线可视化，结构化学习路径推荐。
4. **日常专注学习与计划执行**：Sprint 冲刺模式，BGM 沉浸式环境，触觉反馈激励。
5. **错题复盘、路径梳理与成长回顾**：错题本模式识别，学习报告多维度分析，知识剧场路径推演。

这些场景的共同点在于：目标都不是一次性交付，学习过程普遍具有路径依赖、执行成本和反馈滞后等特征。

#### 1.2.2 目标人群

项目的核心目标用户为大学生，具体可分为以下三类：

1. **有目标但执行不稳定型**：知道要学什么，但难以持续推进，需要系统帮助拆解和追踪。
2. **有积累但缺结构型**：学了很多内容，却缺少知识关系和复盘机制，需要知识图谱和路径推理。
3. **有意愿但缺系统型**：希望借助 AI 建立长期学习系统，而不是只解决眼前题目。

潜在拓展人群包括：考研备考者、职场学习者、终身学习爱好者，以及企业培训场景中的知识管理与执行闭环需求。

#### 1.2.3 定位说明

星火对外统一定位为**"面向大学生的 AI 学习成长系统"**。这一定位刻意避免把系统简化成"聊天助手""搜题工具"或"待办应用"。其核心含义是：星火围绕成长主链组织产品和技术，让用户的状态理解、知识组织、执行推进和反馈沉淀彼此连通。

### 1.3 项目方案

星火采用**"移动端体验层 + 高并发接入层 + AI 智能层"**的三层异构架构，在产品层以对话作为统一入口，在系统层把目标澄清、计划生成、任务拆解、知识星图、学习剧场、学习模拟、学习报告、OpenClaw 执行闭环与多感官成长反馈串成一条主链。

从问题空间到解空间的映射关系如下：

| 核心问题 | 对应模块/链路 | 预期输出 |
|---------|-------------|---------|
| 目标太大、难以启动 | 对话澄清 + 计划生成 + 任务拆解 | 可执行的下一步行动 |
| 知识碎片化 | 知识星图 + GraphRAG + 路径推理 | 结构化学习路径与掌握度 |
| 反馈滞后 | 学习报告 + 剧场 + 成就系统 | 可见的成长反馈 |
| 执行断裂 | Mirofish + OpenClaw 闭环 | 可推进、可回流的执行链路 |

### 1.4 项目目标

本项目当前阶段的目标如下：

1. 打通"对话 → 规划 → 任务 → 执行 → 反馈 → 成长沉淀"的学习主链。
2. 让知识状态可以被可视化、可推理、可回顾，而不是只留在聊天记录中。
3. 用多 Agent 协作、GraphRAG 和 OpenClaw 执行闭环体现技术创新度与系统深度。
4. 在移动端形成有温度、低打扰、可持续使用的成长体验。
5. 通过测试、验收、benchmark 和工程闸门证明项目不是概念原型，而是可验证的系统工程。

### 1.5 项目价值

星火的项目价值主要体现在三个层面：

**对用户的价值**：把"抽象学习目标"转化为"可推进、可追踪、可复盘"的具体行动链。通过知识星图让成长可见，通过成就系统让坚持有感，通过多感官反馈让学习过程本身变得更有温度。

**对教育类 AI 产品形态的价值**：探索从"答疑工具"走向"成长系统"的路径——让学习产品不再只解决当下问题，而是帮助用户长期建立自己的学习结构与行动节奏。这是一个当前市场中尚未被充分验证的产品方向。

**对工程实践的价值**：将异构架构、双核编排、多 Agent、知识图谱、GraphRAG、外部执行闭环和多感官反馈整合进同一系统，形成约 67.5 万行代码规模的复杂 AI-native 产品工程样本。

**社会效益**：帮助更多学生以更低门槛获得个性化支持、长期反馈和可持续成长体验，降低学习过程中的盲目性与挫败感。特别是对于缺乏优质教育资源的地区学生，AI 学习系统有望起到教育公平化的补充作用。

### 2.1 最终呈现形式

1. **移动端主链演示**：对话、知识星图、学习报告、剧场、模拟等关键页面的完整交互流程。

### 2.3 运行环境

**移动端**：Flutter 构建，支持 iOS 与 Android，最低版本 iOS 14 / Android API 24。

**后端基础设施**（Docker Compose 编排）：

| 服务 | 版本 | 职责 |
|------|------|------|
| PostgreSQL | 16+ with pgvector | 关系型存储 + 向量检索 |
| Redis | 7+ | 缓存、检查点、事件总线、任务队列 |
| MinIO | Latest | 对象存储（文件上传、头像） |
| Go Gateway | Go 1.24 | 接入层、鉴权、WebSocket |
| Python AI Engine | Python 3.11 | 智能编排、gRPC 服务 |
| Celery Worker | Python 3.11 | 异步任务队列 |

前后端主要通过 WebSocket（实时聊天/状态同步）、HTTPS REST（认证/资源访问）和 gRPC（Gateway ↔ Python Engine）完成通信。

当前开发与演示环境强调"本地完整拉起能力"（`make dev-all`），保证系统可以在统一依赖环境中完成联调、回归和比赛展示。

### 2.4 验收标准

当前版本的核心验收标准：

1. 主链场景可从对话一路跑通到计划、任务、反馈与成长沉淀。
2. 从零复建（from-zero rebuild）、核心容器健康、移动端 fresh build 与本地 smoke 全部通过。
3. Mirofish、OpenClaw、Theater、Simulation、Learning Report 等关键创新模块具有专项验证材料。
4. 移动端核心页面和关键交互在模拟器环境下可稳定演示。
5. 对高风险或仍未完全签收的能力保持明确边界说明，不虚构完成度。

### 2.5 关键问题

| 关键问题 | 风险等级 | 对策 |
|---------|---------|------|
| 大模型调用延迟/成本/稳定性 | 高 | LLM 路由分层策略 + 熔断机制 + 缓存复用 |
| 多 Agent 协作链路解释性与复杂度 | 中 | 显式协作模式 + Aggregator 统一输出 + 审核反馈环 |
| GraphRAG 维护复杂度与缓存一致性 | 中 | Redis 缓存 TTL + 自动失效 + 图结构序列化 |
| OpenClaw 外部执行边界控制与安全性 | 高 | TrustEngine 三级信任 + HUMAN_ONLY 硬分类 + 敏感字段过滤 |
| 真机音频/触觉/通知等移动端能力 | 中 | 分层降级策略 + 模拟器优先保证核心演示 |

## 3 可行性分析

### 3.1 技术可行性分析

星火采用的关键技术栈都拥有成熟生态：Flutter（Google 维护，Stars 165K+）、Go（Google 维护，高并发标杆）、Python（AI/ML 生态最丰富）、LangGraph（LangChain 团队出品）、PostgreSQL（全球最先进开源关系数据库）、pgvector（HNSW 索引性能优秀）、Redis（缓存/消息标杆）。

项目的难点主要来自**组合复杂度**而非底层技术不可达。从当前代码规模（67.5 万行）、模块划分（16+ 完整模块）、测试资产（100+ 测试文件）和验收记录来看，核心技术路线已经进入真实落地阶段。

### 3.2 资源可行性分析

团队具备移动端、后端、AI 编排和产品统筹等方面的分工基础，并已沉淀较完整的开发文档、模块文档、测试材料与验收记录。现有仓库中 Python、Go、Flutter 三侧的模块规模均表明系统具备持续迭代能力。

项目当前最大的优势不是"概念新"，而是**"工程积累已经形成"**——已有主链、有模块、有测试、有验收、有可重建环境。

### 3.3 市场可行性分析

大学生学习中的执行失败、知识碎片化和反馈滞后是高频且普遍存在的问题。当前主流产品虽然已经覆盖学习问答（ChatGPT Study Mode）、作业辅助（StudyX/Gauth）、资料整理（Quizlet）中的部分场景，但"长期状态理解 + 知识结构化 + 执行闭环 + 成长沉淀"的组合能力仍然稀缺。

**付费意愿分析**：核心用户群体（备考/提升）付费意愿强，可采用 Freemium 模式——基础功能免费，高级 AI 功能（多 Agent 协作、执行闭环、深度报告）按月订阅。参考 Duolingo（MAU 1 亿+、付费率约 8%）和 Notion（个人版免费 + Pro 版 $10/月）的成功路径。

#### 4.1.4 数据采集

1. **用户主动输入**：文本消息、图片、资料上传、交互选择（计划确认/审批决策）。
2. **学习过程行为**：任务完成、反馈提交、路径浏览、剧场/模拟参与、Sprint 冲刺记录。
3. **知识组织过程**：图谱节点更新、掌握度变化、推荐路径生成、遗忘衰减计算。
4. **外部执行回流**：OpenClaw 执行结果、审批状态、信任评估、结果摄取记录。
5. **系统观察数据**：RunLedger 追踪日志、Prometheus 指标、OpenTelemetry trace、WebSocket 延迟。

## 5 概要设计

### 5.1 处理流程

用户从移动端输入学习目标后，系统处理流程如下：

```
用户输入 → Flutter WebSocket 发送
  → Go Gateway 鉴权 + 协议桥接
    → gRPC 调用 Python AI Engine
      → 上下文构建（ContextBuilderMixin）
      → 意图识别（UnifiedIntentRouter + BERT）
      → 充分性检查（SufficiencyChecker）
      → 双核路由（认知核 OR 执行核）
      → 计划/任务生成 OR 多 Agent 协作 OR 外部执行
      → 结果汇总 + 持久化（PersistenceLayerMixin）
      → 可观测性记录（ObservabilityMixin）
    ← gRPC 流式回传
  ← Go Gateway WebSocket 推送
← Flutter 流式渲染 + 状态更新
```

在这一过程中，系统会将结果继续回写到任务、计划、知识状态、反馈记录和成长资产中，保证每一轮交互都能影响下一轮服务。

### 5.2 总体结构设计

系统整体采用三层异构架构：

| 层 | 技术栈 | 职责 |
|---|-------|------|
| Flutter | Riverpod + Design System V2 + GLSL | UI、状态展示、多感官反馈、跨平台体验 |
| Go Gateway | Gin + Gorilla WS + sqlc + CQRS | 高并发接入、鉴权、WebSocket、REST、gRPC 桥接 |
| Python Engine | gRPC + LangGraph + Celery | 认知建模、主编排器、图推理、多 Agent、OpenClaw |

4. OpenClaw 执行结果 → 影响后续任务、计划与反馈（TrustEngine 评估后回流）

### 5.8 错误/异常处理设计

| 异常场景 | 处理策略 |
|---------|---------|
| LLM 模型不可用 | LLMRouter 多模型 fallback + 用户友好提示 |
| 外部服务超时 | 超时控制 + 熔断（CircuitBreaker）+ 降级响应 |

### 5.11 跨端应用架构设计

虽然当前主形态是移动端 App，但系统后端能力天然具备跨端服务化特征。Gateway 的 REST/WebSocket/gRPC 接口可直接被 Web 端或桌面端复用。未来若拓展到 Web、桌面端或其他终端，可继续复用 Gateway、AI Engine、GraphRAG、执行闭环和成长反馈的后端能力。

## 8 详细设计

### 8.1 AI 对话与编排模块

#### 8.1.1 功能描述

该模块是系统入口和主链核心，负责需求理解、上下文构建、意图识别、充分性检查、路由决策、计划生成、工具调用、结果汇总和流式响应。主编排器 `ChatOrchestrator`（1619 行）采用 8 个 Mixin 模块化组合。

#### 8.1.2 性能描述

要求在常规学习对话场景下提供 < 2s 首 Token 的流式反馈，在复杂规划或多 Agent 场景下提供明确状态提示，并具备异常情况下的可解释降级能力。

#### 8.1.3 输入

用户消息、会话上下文（ContextBuilder 构建）、历史记录、画像信息（PersistentBayesianLearner）、计划状态、任务状态、知识状态（GraphRAG 检索结果）。

#### 8.1.4 输出

流式文本（打字机效果）、结构化卡片（计划卡片/任务卡片）、计划结果、任务建议、状态更新、桥接跳转标志（open_theater / open_simulation / open_report）、ExecutionIntent（当需要外部执行时）。

#### 8.1.5 程序逻辑

```
上下文构建（ContextBuilderMixin）
  → 意图识别（UnifiedIntentRouter 快路径 + BERT 分类器）
  → 充分性检查（SufficiencyChecker：required / clarify_if_missing / can_infer）
  → 双核路由（DualCoreRouter → 认知核 OR 执行核）
  → 计划/执行决策（LangGraphPlanner → ExecutablePlan）
  → 多 Agent 协作（可选，Mirofish collaboration_node）
  → 结果汇总（ResponseBuilderMixin）
  → 持久化与回流（PersistenceLayerMixin → DB + Redis）
  → 可观测性记录（ObservabilityMixin → RunLedger + Prometheus）
```

#### 8.1.6 限制条件

依赖模型可用性（通过 LLMRouter 多模型 fallback 缓解）、上下文质量（通过 ContextPruner 剪枝优化）、知识结构完整性（通过 free_mode 降级保底）和实时链路稳定性（通过 CircuitBreaker 熔断保护）。

### 8.2 知识星图与图推理模块

#### 8.2.1 功能描述

负责知识结构组织、掌握度跟踪、学习路径生成和图谱可视化，是系统形成长期结构感和成长反馈的关键基础设施。

#### 8.2.2 性能描述

向量检索 1000 次 < 100ms（HNSW 索引）；图结构 Redis 缓存 TTL 300s，节点变更自动失效；路径生成基于 Dijkstra 变体算法融合掌握度权重。

#### 8.2.3 输入

用户查询、知识主题、当前掌握度数据、关系图谱、用户兴趣节点。

#### 8.2.4 输出

结构化学习路径、掌握度分析、相关知识节点推荐、RetrievalTrace 检索追踪记录、星图可视化数据（6+1 星域分布）。

#### 8.2.5 程序逻辑

```
查询接收
  → GraphRAG 双模检索（pgvector 向量检索 + AGE 图检索）
  → 结果融合 + 用户兴趣节点加权
  → GraphReasoningService 路径推理（Dijkstra 变体）
  → 循环检测 + 个性化权重计算
  → RetrievalTrace 全程记录
  → 返回结构化路径 + 掌握度更新
```

#### 8.2.6 限制条件

依赖知识图谱数据完整性（节点和关系覆盖度）；图结构规模增长时需关注推理时间；缓存策略需保证一致性。

### 8.3 多 Agent 与 OpenClaw 执行模块

#### 8.3.1 功能描述

负责复杂任务协作（Mirofish 11 专家 × 5 协作模式）、任务委派、执行协议翻译（IntentTranslator）、审批确认、结果摄取和信任评估（TrustEngine 三级），是当前版本最具代表性的高级能力。

#### 8.3.2 性能描述

Mirofish 桥接链路 < 12s（Theater/Simulation）、< 25s（Report）；OpenClaw 执行支持 HTTP 和 WebSocket 双传输模式；TrustEngine 自动晋升需满足 5 次成功 + 85% 成功率 + 质量 ≥ 0.7。

#### 8.3.3 输入

规划结果（ExecutablePlan）、ExecutionIntent、审批上下文、任务状态、外部执行返回结果、专家协作请求（协作模式 + 参与专家列表）。

#### 8.3.4 输出

协作结果（Aggregator 统一输出）、执行请求（OpenClaw 格式）、信任等级（RAW/VALIDATED/TRUSTED）、回流记录（知识图谱更新 + 任务状态更新）、后续策略建议。

#### 8.3.5 程序逻辑

```
Mirofish 协作路径：
  复杂任务识别 → Router 选择专家 → collaboration_node 执行协作
  → aggregator_node 合并结果 → 输出统一响应
  → 如有 modify/reject → reset_collaboration_node 重规划

OpenClaw 执行路径：
  ExecutionRouter 分类（HUMAN_ONLY / AGENT_ELIGIBLE）
  → ExecutionIntent 构建（mode/env/policy）
  → IntentTranslator 翻译为 OpenClaw 请求
  → OpenClaw 执行（HTTP POST 或 WebSocket 双向流）
  → ResultParser 解析执行结果
  → TrustEngine 三级信任评估（RAW → VALIDATED → TRUSTED）
  → ExecutionIngestor 摄取 → 知识图谱更新 + 任务状态回流
```

#### 8.3.6 限制条件

多 Agent 协作依赖工作流稳定性和 LLM 响应质量；外部执行依赖 OpenClaw 服务可用性和网络连通性；TrustEngine 评估依赖执行结果质量（需满足 Schema 验证 + 质量阈值）；审批链路需保证用户可见状态一致性。
