## 1 项目概述

### 1.1 项目背景

随着生成式 AI 的普及，大学生获得信息与建议的门槛显著降低，但“知道怎么做”和“真正做下去”之间仍存在巨大鸿沟。用户往往能在聊天里得到答案，却很难把答案转化为可持续推进的学习行动。

星火希望解决的，不是单一知识问答问题，而是整个学习过程中的连续性问题：目标如何拆解，计划如何推进，知识如何沉淀，错误如何复盘，动力如何维持。

### 1.2 项目定位

#### 1.2.1 应用场景

星火主要面向大学生的自主学习场景，包括期末冲刺、课程复习、竞赛准备、长期知识体系构建、日常专注学习与社群共学等。

#### 1.2.2 目标人群

目标用户主要是：

1. 有明确学习目标但执行节奏不稳定的大学生。
2. 学过很多内容但缺少体系、复习和反馈机制的大学生。
3. 希望在 AI 帮助下建立稳定学习闭环的自驱型或半自驱型用户。

#### 1.2.3 定位说明

星火对外统一定位为“面向大学生的 AI 学习成长系统”。这里的“成长系统”强调它不仅回答问题，还持续参与目标拆解、任务推进、知识组织和反馈沉淀；相比“学习操作系统”这样的表述，这一定位更容易被评委快速理解。

### 1.3 项目方案

星火采用“移动端体验 + 高并发接入 + 智能编排引擎”的三层异构架构。产品层面以 AI 对话为入口，串联计划、任务、知识星图、学习报告、学习模拟、知识剧场、成就系统与外部执行闭环，形成持续学习系统。

### 1.4 项目目标

本项目的阶段性目标是：

1. 打通“对话 -> 规划 -> 任务 -> 执行 -> 反馈”的学习主链。
2. 用知识星图与报告系统让成长可视化。
3. 用多 Agent 协作和 OpenClaw 执行闭环提升系统的技术创新度与实际推进能力。
4. 在移动端形成有温度、低打扰、可持续使用的学习体验。

### 1.5 项目价值

星火的价值主要体现在三个方面：

1. 对用户而言，帮助大学生把抽象学习目标转化为可执行行动。
2. 对产品形态而言，探索 AI 学习系统从“答疑”走向“闭环成长”的路径。
3. 对工程实践而言，提供一个异构架构、多 Agent、GraphRAG、外部执行闭环相结合的复杂系统样本。

## 2 开发计划

### 2.1 最终呈现形式

当前项目以移动端 App 为核心表现形态，后端以 API 服务和 AI 引擎形式支撑。比赛展示中将以移动端核心页面、后端编排能力和关键闭环演示为主。

### 2.2 主要功能描述

当前版本重点功能包括：

1. AI 对话与需求澄清。
2. 计划生成、任务拆解与执行反馈。
3. 知识星图与学习路径。
4. 学习报告、知识剧场与学习模拟。
5. 多 Agent 协作系统。
6. OpenClaw 执行闭环。
7. 成就、契约、BGM 与多感官体验。

### 2.3 运行环境

移动端采用 Flutter 构建，支持 iOS 与 Android。  
后端采用 Docker Compose 组织 PostgreSQL、Redis、MinIO、Gateway、Python AI Engine 与 Celery 等依赖服务。  
系统通过 WebSocket、HTTP 和 gRPC 完成前后端实时通信与服务间调用。

### 2.4 验收标准

当前版本的验收标准主要包括：

1. 核心用户主链可完整跑通。
2. 从零复建、核心容器健康、移动端 fresh build 可通过。
3. Mirofish、OpenClaw、Theater、Simulation、Learning Report 等关键创新模块具备专项测试或回归证据。
4. 关键移动端体验在模拟器环境可稳定运行。

### 2.5 关键问题

1. 大模型调用延迟与成本控制。
2. 多 Agent 协作链路的稳定性与解释性。
3. OpenClaw 外部执行过程的安全性与可控性。
4. 知识图谱与向量检索融合后的性能与维护复杂度。

### 2.6 进度安排

项目已完成从基础架构、核心 AI 主链到多 Agent、OpenClaw、Mirofish 相关功能的多阶段迭代。当前处于“本地后端主链通过、专项回归通过、等待进一步人工签收与真机补证”的状态。

### 2.7 开发预算

当前预算重点集中在：

1. 云服务器与基础依赖服务。
2. 大模型 API 调用成本。
3. 移动端构建、测试与真机调试成本。

## 3 可行性分析

### 3.1 技术可行性分析

星火当前采用的关键技术均已有成熟生态支撑：Flutter、Go、Python、LangGraph、PostgreSQL、pgvector、Redis、OpenTelemetry 等都具备稳定的工程基础。项目难点主要在组合复杂度，而不是底层技术不可达。

从当前代码和测试资产来看，项目核心技术路线已经进入真实落地阶段，而非停留在原型验证阶段。

### 3.2 资源可行性分析

团队在客户端、后端、AI 编排和产品统筹上具有明确分工，且项目已沉淀大量工程文档、测试材料和验收记录。现有代码规模、模块划分与测试资产都说明项目已具备持续迭代基础。

### 3.3 市场可行性分析

星火面向的是大学生普遍存在的学习执行和成长管理问题，场景天然存在且频繁发生。虽然当前还缺少正式的访谈与量化调研数据，但从需求普遍性、产品落点和使用频率来看，项目具备明显的校园应用潜力与后续扩展空间。

## 4 需求分析

### 4.1 数据需求

#### 4.1.1 静态数据

包括知识节点、学科分类、部分种子知识结构、系统配置和视觉/音频资源等。

#### 4.1.2 动态数据

包括用户对话、任务记录、计划版本、掌握度变化、学习反馈、执行记录、模拟会话、剧场预测结果、成就事件等。

#### 4.1.3 数据词典

当前系统中的关键数据结构包括：KnowledgeNode、Task、Plan、ExecutionIntent、ChatSession、ChatMessage、Achievement、LearningReport 等。

#### 4.1.4 数据采集

系统主要通过用户主动输入、学习执行过程、错误记录、图谱更新、外部执行结果回流等方式积累数据，并结合缓存与日志系统形成可观测链路。

### 4.2 功能需求

#### 4.2.1 核心功能模块

1. 对话与需求理解模块。
2. 计划与任务模块。
3. 知识星图与图推理模块。
4. 学习报告模块。
5. 学习模拟与知识剧场模块。
6. 多 Agent 协作模块。
7. OpenClaw 执行闭环模块。
8. 成就、契约与感官体验模块。

### 4.3 性能需求

#### 4.3.1 时间特性

系统需要满足移动端实时聊天、流式输出、任务反馈、剧场和模拟等场景的交互可接受性。对于需要较长推演的场景，系统应提供明确状态反馈与降级策略。

#### 4.3.2 适应性

系统需要兼容不同终端性能与不同网络状态，支持弱网、缓存、降级与重试策略。

### 4.4 界面需求

界面应兼顾清晰信息结构、低打扰体验和成长感反馈。知识星图、报告、剧场、成就等页面既要有科技感，也要易于在比赛场景中快速理解。

### 4.5 接口需求

#### 4.5.1 硬件接口

移动端依赖设备的网络、音频、触觉与系统通知能力。

#### 4.5.2 软件接口

系统对外和对内主要依赖 WebSocket、REST 和 gRPC 协议，并通过 Protobuf 维持跨语言契约一致性。

### 4.6 其他需求

系统需要具备可观测性、可回滚性、权限控制、异常处理与可验证的工程过程。

## 5 概要设计

### 5.1 处理流程

用户从移动端发起请求后，Go Gateway 负责鉴权、协议转换与连接管理，再通过 gRPC 把请求转给 Python AI Engine。Python 侧编排器构建上下文、进行路由和验证，按需要触发多 Agent、知识检索、计划生成、报告或外部执行，并将结果流式回传前端。

### 5.2 总体结构设计

系统整体采用三层异构架构：

1. Flutter：承载 UI、状态展示、多感官体验。
2. Go Gateway：承载实时连接、鉴权、API 网关与工程治理。
3. Python AI Engine：承载认知、规划、执行、Agent 协作和知识处理。

### 5.3 功能设计

功能设计围绕学习主链组织，而不是围绕孤立页面组织。对话是入口，计划和任务是推进器，知识星图是结构层，报告/模拟/剧场是反馈和洞察层，OpenClaw 是执行增强层。

### 5.4 数据流转设计

对话、任务、计划、知识节点、执行记录和学习报告之间存在持续回流关系。系统不仅“产生结果”，还会把结果继续写回到用户状态、知识状态和后续策略中。

### 5.5 用户界面设计

移动端采用 Feature-First 架构与 Design System V2，强调统一视觉语言、沉浸式氛围和重点场景差异化表达。

### 5.6 数据结构设计

当前版本中最关键的数据结构包括：

1. `ExecutionIntent`：面向外部执行器的结构化任务协议。
2. `KnowledgeNode`：知识节点基础结构。
3. `SparkleState`：多 Agent 和编排链路中的状态载体。

### 5.7 接口设计

#### 5.7.1 外部接口

面向移动端的接口主要为 REST 和 WebSocket，覆盖认证、任务、计划、知识星图、报告、模拟、执行记录等能力。

#### 5.7.2 内部接口

Gateway 与 Python AI Engine 通过 gRPC 双向流与 Protobuf 契约协同。

### 5.8 错误/异常处理设计

系统通过路由降级、超时控制、信任评估、审批确认、熔断与可观测性机制减少异常对用户体验的破坏，并确保关键问题可追踪、可定位。

### 5.9 系统配置策略

配置通过环境变量、Compose 编排和服务级配置集中管理，避免硬编码敏感信息。

### 5.10 系统部署方案

开发与演示环境以 Docker Compose 为主，便于本地快速拉起完整服务链；后续可迁移至更复杂的生产部署形态。

### 5.11 跨端应用架构设计

当前主形态为移动端 App，后端能力天然具备跨平台服务化特征，为后续多端扩展保留了空间。

### 5.12 其他相关技术与方案

OpenTelemetry、Prometheus、BGM 路由服务、GraphRAG、剧场与模拟等共同构成了星火的差异化工程栈。

## 8 详细设计

### 8.1 AI 对话与编排模块

#### 8.1.1 功能描述

作为系统入口，负责用户需求理解、上下文构建、路由决策、计划生成、工具执行和流式响应。

#### 8.1.2 性能描述

要求在常规对话场景下保持稳定流式反馈，并支持复杂场景下的可解释降级。

#### 8.1.3 输入

用户消息、会话上下文、画像、历史记录、任务/计划状态。

#### 8.1.4 输出

流式文本、结构化卡片、执行计划、工具结果、状态更新。

#### 8.1.5 程序逻辑

上下文构建 -> 充分性检查 -> 双核路由 -> 规划/执行 -> 结果汇总 -> 持久化。

#### 8.1.6 限制条件

依赖模型可用性、知识数据完整性和实时链路稳定性。

### 8.2 知识星图与图推理模块

负责知识结构组织、掌握度跟踪、学习路径生成和可视化反馈。

### 8.3 多 Agent 与 OpenClaw 执行模块

负责复杂任务协作、任务委派、执行协议翻译、审批与结果信任评估，是当前版本最具代表性的高级能力之一。
