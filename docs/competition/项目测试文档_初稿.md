## 1 测试计划

### 1.1 测试策略与目标

星火采用“单元测试 + 集成测试 + 专项回归 + 工程闸门 + 人工验收”组合策略。测试目标不是只证明代码能跑，而是证明学习主链、关键创新模块与比赛展示链路具备真实可验证性。

本项目当前测试特别强调以下几点：

1. 对 AI 主链和多 Agent 系统进行专项回归。
2. 对 OpenClaw 执行闭环进行分阶段测试。
3. 对移动端关键创新页面进行 widget 级回归。
4. 对从零复建、容器健康、环境检查与 smoke 链路进行工程验证。

### 1.2 测试范围

本轮测试覆盖以下核心范围：

1. 后端 AI 对话主链。
2. Mirofish 多 Agent 与桥接能力。
3. OpenClaw Phase 0 至 Phase 4 执行闭环。
4. Learning Report、Knowledge Theater、Simulation 等关键创新能力。
5. Flutter 侧 BGM、Mirofish、Learning Insights 等关键页面与组件。
6. 工程环境、容器、构建、健康检查与 smoke 链路。

### 1.3 测试环境

后端测试环境基于 Python 3.11、pytest、真实 PostgreSQL 与本地完整依赖。  
Gateway 测试基于 Go 工程测试框架。  
移动端测试基于 Flutter test。  
环境联调依赖 Docker Compose 提供 PostgreSQL、Redis、MinIO、Gateway、Python AI Engine、Celery 等基础服务。

## 2 单元测试

### 2.1 OpenClaw 执行闭环模块

#### 2.1.1 测试用例与结果分析

OpenClaw 已按 Phase 0 到 Phase 4 进行分阶段测试：

1. Phase 0：执行路由决策。
2. Phase 1：ExecutionIntent 构建。
3. Phase 2：意图翻译与请求生成。
4. Phase 3：执行状态流转与信任评估。
5. Phase 4：结果摄取与闭环回流。

当前仓库已有以下专项测试文件：

- `test_openclaw_phase0.py`
- `test_openclaw_phase1.py`
- `test_openclaw_phase2.py`
- `test_openclaw_phase3.py`
- `test_openclaw_phase4.py`
- `test_openclaw_gateway_ws.py`
- `test_openclaw_admin_api.py`

根据当前验收记录，上述链路已完成专项回归并通过。

#### 2.1.2 测试结果综合分析及建议

OpenClaw 模块当前最大的优势是测试分层清晰、阶段边界明确。后续建议继续补充更适合比赛展示的状态流转截图和执行回流示意图。

#### 2.1.3 测试经验总结

对于带外部执行器的复杂系统，按阶段拆分测试比一次性做大而全 E2E 更利于定位问题，也更适合向评委说明系统设计的严谨性。

### 2.2 Mirofish 多 Agent 模块

#### 2.2.1 测试用例与结果分析

当前仓库中已有：

- `test_mirofish_phase0_acceptance.py`
- `test_mirofish_wiring_finish.py`
- `test_theater_seed_and_accuracy.py`
- `test_session_feedback_adaptation.py`
- `test_sufficiency_checker_llm_fallback.py`
- `test_unified_intent_router_fast_path.py`
- `test_unified_intent_router_routing.py`

这些测试覆盖了多 Agent wiring、Knowledge Theater、会话反馈、充分性检查与意图路由等关键环节。

#### 2.2.2 测试结果综合分析及建议

Mirofish 相关测试说明系统不是“单一聊天 UI”，而是具备真实协作链路。后续建议继续强化多 Agent 复杂协作模式下的端到端展示证据。

#### 2.2.3 测试经验总结

复杂智能系统必须把“协作结构”本身纳入测试对象，而不是只测试最终输出文本。

## 3 功能测试

### 3.1 AI 对话主链功能

#### 3.1.1 测试用例与结果分析

根据当前本地发布前验收记录，曾执行以下链路验证：

- `tests/unit/test_response_feedback_service.py`
- `tests/integration/test_websocket_full_stack.py`

相关结果记录为 `19 passed`，说明 AI 对话 WebSocket 主链、反馈闭环和部分全栈交互能力已经形成可重复验证基础。

#### 3.1.2 测试结果综合分析及建议

AI 主链当前已经具备较强的技术可信度。后续建议把一条比赛展示主链整理成更适合截图和录屏的标准化验收脚本。

#### 3.1.3 测试经验总结

对话系统最重要的不只是回答正确，而是流式体验、状态回流和多轮连续性是否稳定。

### 3.2 Mirofish 桥接功能

#### 3.2.1 测试用例与结果分析

当前验收记录显示以下能力已有专项回归：

1. Theater free mode、seed、accuracy、what-if、adopt、chat bridge preview。
2. Simulation 交互继续、推荐 seeds、checkpoint fallback。
3. Learning Report cold start、structured dashboard、ready update、缓存复用。

#### 3.2.2 测试结果综合分析及建议

这说明 Mirofish 不只是概念模块，而已经进入具体产品页面与桥接流程。后续建议把最容易打动评委的两到三条桥接链路固定为演示重点。

#### 3.2.3 测试经验总结

桥接类功能最容易出现“页面有了但链不断”的假成熟状态，因此必须用真实跳转和结果回流去验证。

### 3.3 Flutter 关键页面与组件

#### 3.3.1 测试用例与结果分析

当前本地验收记录显示已执行并通过的移动端专项测试包括：

- `mirofish_wiring_finish_test.dart`
- `insights_frontend_smoke_test.dart`
- `learning_insights_navigation_test.dart`
- `simulation_interaction_continue_test.dart`
- `theater_phase2_widget_test.dart`
- `unified_settings_bgm_test.dart`
- `bgm_service_test.dart`

对应结果记录为 `18 passed`。

#### 3.3.2 测试结果综合分析及建议

移动端关键创新页面已具备一定 widget 级验证能力。后续建议补充核心页面截图作为比赛文档中的辅助证据。

#### 3.3.3 测试经验总结

对于比赛文档，移动端测试不能只写“页面完成”，而应强调页面链路、交互和状态更新已被验证。
