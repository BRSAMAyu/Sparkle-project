## 1 测试计划

### 1.1 测试策略与目标

星火采用“单元测试 + 功能测试 + 系统测试 + benchmark + 工程闸门 + 人工验收”的组合测试策略。测试工作的目标，不是证明某段代码在本地偶然可运行，而是证明 10 个核心功能模块能够共同支撑一条完整、稳定、可回归的学习成长主链。

测试策略重点遵循以下原则：

1. 全模块覆盖：项目开发文档 `4.2` 中定义的 10 个功能模块全部进入单元测试和功能测试范围。
2. 闭环验证：重点验证输入、处理、回流、反馈四个关键环节是否真正衔接，尤其关注数据反馈闭环、功能闭环与体验闭环是否成立。
3. 创新能力重点覆盖：OpenClaw、Mirofish、知识星图、GraphRAG、学习报告、剧场、模拟、BGM 与多感官体验均纳入专项验证范围。
4. 系统级可信：除模块级测试外，保留构建、smoke、from-zero rebuild、性能阈值和剩余边界等系统级证据。
5. 结果表达真实：明确区分“已验证能力”和“仍在统一签收中的边界”，不以包装替代验证。

[图 Q1] 星火测试体系图（单元测试 -> 功能测试 -> 系统测试 -> 验收）

### 1.2 测试范围

测试范围按照“模块逻辑 -> 用户场景 -> 系统级稳定性”三层展开，既覆盖开发文档 `4.2` 中的全部功能模块，也覆盖最容易影响整体闭环质量的系统级环节。

| 范围层级 | 覆盖对象 |
|------|------|
| 单元测试 | 10 个功能模块的核心逻辑、状态流转、关键接口、规则判断 |
| 功能测试 | 10 个功能模块在用户视角下的主要交互场景和关键结果 |
| 系统测试 | 环境与工程闸门、性能阈值、混沌/弹性验证、剩余边界 |
| 验收补充 | 真机体验、演示脚本、专项回归和系统级快照 |

### 1.3 测试环境

测试环境遵循“与真实工程保持一致，同时便于重复回归”的原则。除自动化测试环境外，也保留了联调环境和真机环境，用于验证多感官体验、弱网场景和系统级边界。

| 环境 | 配置 |
|------|------|
| Python 测试环境 | Python 3.11 + pytest + PostgreSQL + Redis |
| Go 测试环境 | Go 运行环境 + 标准测试框架 + benchmark |
| Flutter 测试环境 | Flutter test + widget / integration / performance 级回归 |
| 联调环境 | PostgreSQL + Redis + MinIO + Go Gateway + Python AI Engine + Flutter 客户端 |

| 测试对象 | 关键验证点 | 结果 |
|------|------|------|

| 信息充分性检查 | 是否能判断当前信息是否需要继续澄清 | 通过 |

#### 2.1.3 测试经验总结

主链类模块最容易因为上下文丢失或状态判断失真而带来连锁问题，因此必须把澄清、分流和状态读取一起测，而不能拆开孤立测试。

#### 2.2.3 测试经验总结

计划模块的单元测试不能只验证输出内容，还要验证任务粒度是否合理、是否能够接回主链。

3. 端侧真机能力部分（音频、触觉、通知）允许在文档中诚实标注“已具备基础，部分场景仍待统一签收”，但不得将未完成项包装为已完成。

### 4.3 混沌测试与弹性验证

1. 后端依赖波动时主链是否仍能给出可理解的降级说明。

5. 页面快速切换、前后台切换或弱网环境下，状态是否能保持基本一致。
