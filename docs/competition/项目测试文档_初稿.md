## 1 测试计划

### 1.1 测试策略与目标

星火采用**"单元测试 + 集成测试 + 功能回归 + benchmark + 工程闸门 + 混沌测试 + 人工验收"**组合策略。测试重点不是证明某段代码能跑，而是证明学习成长主链、关键创新模块和比赛展示路径在真实环境下具备可验证性、可复现性和可解释性。

本项目测试策略特别强调以下四点：

1. **创新模块专项回归**：对 OpenClaw（Phase 0-4）、Mirofish（11 专家 × 5 协作模式）、GraphRAG、Theater、Simulation、Learning Report 等关键创新模块建立专项回归，而不是只测试聊天主链。
2. **分阶段链路测试**：对复杂能力采用分阶段测试和链路测试结合的方式，确保问题可定位、逻辑可审查。例如 OpenClaw 按 Phase 0-4 逐阶段验证，Mirofish 从 Router → Expert → Collaboration → Aggregator 逐层验证。
3. **系统级工程闸门**：对工程环境、构建、容器健康和 smoke 链路建立系统级验证，避免"代码存在但环境不可演示"的风险。
4. **诚实边界管理**：对尚未完全收口的真机能力保留诚实边界，不将未完成部分包装为已全部验收通过。

**发布目标**：在本地完整环境中，核心学习主链和关键创新模块达到"可稳定演示、可专项回归、可解释说明"的质量等级。

## 2 单元测试

### 2.1 OpenClaw 执行闭环模块

#### 2.1.1 测试用例与结果分析

OpenClaw 相关能力按 Phase 0 到 Phase 4 建立了明确分层，让执行闭环不是一个模糊的"大功能"，而是一系列可独立验证、也可串联验证的工程环节。

**测试文件清单**：

| 测试文件 | Phase | 核心验证点 |
|---------|-------|----------|
| `test_openclaw_phase0.py` | 0 | ExecutionRouter 路由决策——HUMAN_ONLY（运动/付款/密码）和 AGENT_ELIGIBLE（PLANNING/SOCIAL/OCR）正确分类 |
| `test_openclaw_phase1.py` | 1 | ExecutionIntent 构建——execution_mode、target_env、policy 字段正确设置与完整性 |
| `test_openclaw_phase2.py` | 2 | IntentTranslator 翻译——translate_to_openclaw_request 正确生成 OpenClaw 请求格式 |
| `test_openclaw_phase3.py` | 3 | 执行生命周期与信任评估——status 状态流转（DRAFT→...→SUCCEEDED/FAILED）、TrustEngine 三级晋升 |
| `test_openclaw_phase4.py` | 4 | 结果摄取——ExecutionIngestor 正确解析执行结果、知识图谱更新、后续任务触发 |
| `test_openclaw_gateway_ws.py` | — | Gateway WebSocket 侧链路——消息格式、事件推送、审批回传 |
| `test_openclaw_admin_api.py` | — | 管理控制接口——执行记录查询、状态管理 |

**关键验证点详解**：

1. **路由正确性**：运动、付款、密码修改等任务必须被分流到 HUMAN_ONLY，不允许进入自动执行；PLANNING、SOCIAL、OCR 等任务才可进入 AGENT_ELIGIBLE 路由。
2. **意图完整性**：结构化执行意图必须包含目标环境（BROWSER/SHELL/API/DOCUMENT/HUMAN）、执行模式（HUMAN/AGENT/HYBRID）和策略（允许域名/工具/审批/质量）。
3. **信任晋升条件**：自动晋升到 TRUSTED 需同时满足 5 次成功执行 + 85% 成功率 + 质量分数 ≥ 0.7。
4. **敏感字段过滤**：TrustEngine 自动过滤 password、secret、api_key、token 等敏感字段，防止执行结果中泄露敏感信息。
5. **闭环回流**：执行结果必须通过 ExecutionIngestor 正确摄取后，才能触发知识图谱更新和后续任务状态变更。

#### 2.1.2 测试结果综合分析及建议

OpenClaw 模块当前最大的工程优势，是把"外部执行"拆成多个边界清晰的阶段来做测试，而不是一上来就用一个笼统的 E2E 用例覆盖全部逻辑。这样既提高了定位效率，也更便于在比赛文档中展示系统设计的严谨性。

**Phase 覆盖矩阵**：

| 验证点 | Phase 0 | Phase 1 | Phase 2 | Phase 3 | Phase 4 |
|-------|---------|---------|---------|---------|---------|
| 路由决策 | ✓ | | | | |
| 意图构建 | | ✓ | | | |
| 请求翻译 | | | ✓ | | |
| 状态流转 | | | | ✓ | |
| 信任评估 | | | | ✓ | ✓ |
| 结果回流 | | | | | ✓ |

后续建议：补充更适合评委展示的状态流转截图，以及典型任务从"计划生成 → 进入执行 → 回流到任务与知识状态"的完整示例。

#### 2.1.3 测试经验总结

对于带有外部执行引擎的复杂系统，**分阶段测试优于一次性黑盒测试**。只有先证明路由、意图、翻译、执行、回流各阶段都清晰可控，整条闭环才真正可信。这一测试策略本身也体现了项目的工程成熟度。

### 2.2 Mirofish 多 Agent 模块

#### 2.2.1 测试用例与结果分析

Mirofish 多 Agent 相关测试覆盖的重点不是"最终回答像不像"，而是"协作结构是否真实存在并稳定运行"。

**测试文件清单**：

| 测试文件 | 核心验证点 |
|---------|----------|
| `test_mirofish_phase0_acceptance.py` | 多 Agent 基础验收——Router 分发、专家节点响应、工具调用 |
| `test_mirofish_wiring_finish.py` | 专家连线完整性——11 个专家全部正确注册并可路由 |
| `test_theater_seed_and_accuracy.py` | 剧场路径预测——种子话题命中率、PredictionAccuracyTracker 追踪 |
| `test_session_feedback_adaptation.py` | 会话反馈适应——SessionFeedbackSignal 检测/应用/计数/置信度 |
| `test_sufficiency_checker_llm_fallback.py` | 充分性检查降级——LLM 不可用时的 fallback 策略 |
| `test_unified_intent_router_fast_path.py` | 快路径意图识别——高频意图快速分类（无需 LLM） |
| `test_unified_intent_router_routing.py` | 统一路由测试——意图到专家节点的正确映射 |

**关键验证逻辑**：

1. **协作结构真实性**：测试不是只验证输出文本，而是验证 Router 是否正确选择了专家、collaboration_node 是否按指定模式（single/sequential/parallel/debate/delegation）执行、aggregator_node 是否正确合并了多个专家的结果。
2. **桥接完整性**：Theater free_mode / seed / accuracy / what-if / adopt / chat bridge preview 全部有专项回归。
3. **反馈闭环**：SessionFeedbackSignal 的检测结果是否真正影响了后续会话策略。
4. **降级策略**：当 LLM 不可用时，SufficiencyChecker 的 fallback 是否能保证主链不中断。

#### 2.2.2 测试结果综合分析及建议

Mirofish 模块当前的亮点在于：测试对象不仅包括单个专家节点，也包括**协作结构本身**——桥接触发、路由转发、剧场路径预测和用户反馈适应。这比只做输出文本校验更接近真实质量要求。

后续建议固定两到三条最能打动评委的典型协作用例：
- "知识解释 + 路径规划"（galaxy_guide + time_tutor 协作）
- "错题分析 + 复习建议"（error_analyst + study_buddy 协作）
- "剧场推演 + 报告回流"（Theater → Report 桥接完整链路）

#### 2.2.3 测试经验总结

复杂智能系统的测试重点不应该只落在"结果像不像人写的"，还必须落在**"结构是否真实、链路是否稳定、状态是否可回流"**。Mirofish 的测试策略证明了多 Agent 系统可以被结构化地验证。

## 3 功能测试

### 3.1 AI 对话主链功能

#### 3.1.1 测试用例与结果分析

AI 对话主链是系统最核心的入口，也是最容易被评委直接感知的一条链路。

**测试文件清单**：

| 测试文件 | 核心验证点 |
|---------|----------|
| `test_response_feedback_service.py` | 反馈闭环——用户反馈是否正确影响后续策略 |
| `test_websocket_full_stack.py` | WebSocket 全栈——消息发送/接收/流式输出/状态同步 |

**验收结果**：19 passed，说明 AI 对话 WebSocket 主链、反馈闭环和全栈交互能力已具备可复用验证基础。

**功能测试覆盖的关键问题**：

1. **流式稳定性**：用户消息能否稳定进入实时链路并获得流式响应（打字机效果连续、无断流）。
2. **多轮一致性**：系统是否能在多轮交互中维持状态一致性（上下文不丢失、画像持续更新）。
3. **反馈回流**：用户反馈是否真正影响后续会话和策略（SessionFeedbackSignal 应用后可观测到变化）。
4. **结构化触发**：计划、任务和结构化结果是否能从对话中被正确触发（LangGraphPlanner 生成 ExecutablePlan）。

#### 3.1.2 测试结果综合分析及建议

当前 AI 对话主链的测试可信度较高，原因在于它不是只校验接口返回，而是已经结合了 WebSocket、反馈服务与全栈链路材料。这条主链可以作为比赛展示的**最核心"可信主路径"**。

后续建议将一条标准化展示剧本沉淀为固定脚本，包含：用户输入目标 → 系统澄清 → 生成计划 → 拆分任务 → 进入知识星图 → 触发剧场/模拟 → 查看报告 → 成就解锁。

#### 3.1.3 测试经验总结

学习系统中的聊天链路最重要的不只是"回答正确"，还包括**状态回流、结构化输出和多轮连续性**是否稳定。只有这几点成立，对话才真正是主链入口，而不是孤立窗口。

| Chat → Simulation | 交互继续、推荐 seeds、checkpoint fallback | 通过 |

#### 3.2.3 测试经验总结

对于以成长闭环为核心的产品，**桥接能力本身就是测试对象**。如果聊天到报告、聊天到剧场、聊天到模拟不能成立，那么系统就很难说服评委它是一个完整成长系统。

### 4.3 混沌测试与弹性验证

系统已开始关注异常场景和服务弹性，仓库中存在 `tests/chaos/test_service_resilience.py`，验证系统在异常条件下的表现。

**混沌测试覆盖的关键场景**：

| 场景 | 预期行为 | 保护机制 |
|------|---------|---------|
| Python Engine 无响应 | Gateway 返回"服务繁忙" | CircuitBreaker 熔断 |
| LLM 模型调用超时 | 自动切换备用模型 | LLMRouter 多模型 fallback |
| Redis 连接中断 | 降级到直接 DB 查询 | 缓存失效降级策略 |
| 外部执行结果异常 | TrustEngine 拒绝回流 | 信任评估 + HANDED_BACK |
| WebSocket 连接断开 | 客户端自动重连 | Flutter 重连机制 |

对星火这类高复杂度系统而言，混沌测试尤为重要。一旦涉及多 Agent、外部执行、图检索和多服务协作，问题往往不是"平时能不能跑"，而是"出问题时会不会整体崩掉、能不能被定位、能不能优雅降级"。
