# 前端改进对齐文档

日期：2026-03-22  
范围：Sparkle Flutter 前端体验层 Phase 6 ~ Phase 13  
目标：统一本轮前端改进的设计意图、实现边界、验收口径与后续延展方式，避免后续新增页面或组件重新回到“局部最优、全局不一致”。

---

## 1. 文档目的

这份文档解决四个问题：

1. 当前前端体验层到底已经改到了什么程度。
2. 哪些能力属于共享底座，后续页面必须复用，不能再各写一套。
3. 哪些改动已经通过自动化验收，哪些仍属于真机签收范围。
4. 后续继续扩展时，什么是允许的，什么是不允许的。

---

## 2. 总体设计目标

本轮前端改进不是单纯“加动画”或“加音效”，而是要把 Sparkle 前端收口成一套统一体验系统。

统一目标如下：

- 高频主链优先：优先提升 `Dashboard -> Chat -> Task -> Focus -> Achievement -> Community` 这条真实用户主路径。
- 体验语义统一：同类行为应触发同类反馈，不允许不同页面对同一动作给出完全不同的触感/声音/动效。
- 共享层优先：优先改共享组件、共享服务、共享 token，而不是逐页堆特例。
- 无障碍可退化：`reduceMotion`、大字体、深浅色模式下必须优雅降级。
- 性能可控：所有多感官和动效增强都必须接受预算约束，不能以掉帧、音频爆音、粒子失控为代价。

## 4. 共享底座能力

以下能力现在属于前端共享底座。后续新增页面或重构页面时，默认必须复用，不应绕开。

### 4.1 体验语义层

核心文件：

- [experience_profile.dart](/Users/brsama/code/GitHub/Sparkle-project/mobile/lib/core/experience/experience_profile.dart)
- [scene_audio_policy.dart](/Users/brsama/code/GitHub/Sparkle-project/mobile/lib/core/services/scene_audio_policy.dart)
- [scene_audio_scope.dart](/Users/brsama/code/GitHub/Sparkle-project/mobile/lib/core/widgets/scene_audio_scope.dart)

职责：

- 为页面定义统一体验语义，如 `dashboard / assistant / focus / social / celebration`
- 统一 route 级 BGM、ambient、场景优先级
- 避免页面各自直接操作音频服务造成冲突

约束：

- 页面级音频接入默认通过 `SceneAudioScope`
- 不允许页面绕过策略直接硬切 BGM，除非是明确的临时演示页或实验页

### 4.2 动效原语

核心文件：

- [sparkle_motion_primitives.dart](/Users/brsama/code/GitHub/Sparkle-project/mobile/lib/core/design/widgets/sparkle_motion_primitives.dart)
- [design_system.dart](/Users/brsama/code/GitHub/Sparkle-project/mobile/lib/core/design/design_system.dart)

已提供：

- `SparkleStaggerItem`
- `SparkleStaggerList`
- `SparkleStaggerGrid`
- `SparkleStaggerWrap`
- `SparkleAttentionPulse`
- `SparkleExitTransition`

约束：

- 新增进场/退场动效优先用上述 primitives
- 不再新增散落的硬编码 `Duration(milliseconds: ...) + Curves.xxx`
- 动效时长应优先走 `DS.motionDuration(token)`
- 动效曲线应优先走 `DS.motionCurve(token)`

### 4.3 感官反馈层

核心文件：

- [sensory_feedback_service.dart](/Users/brsama/code/GitHub/Sparkle-project/mobile/lib/core/services/sensory_feedback_service.dart)
- [bgm_service.dart](/Users/brsama/code/GitHub/Sparkle-project/mobile/lib/core/services/bgm_service.dart)

已提供：

- 统一语义事件：`tap / selection / confirm / success / warning / error / streak / starUnlock / achievement*`
- SFX、haptic、ambient 的统一调用入口
- BGM 模式：`adaptive / focusOnly / silent`
- 全局感官预算 `SensoryBudget`
- ambient fade in/out
- BGM 预加载与生命周期恢复

约束：

- 页面和组件不要直接写平台 haptic 或零散音效逻辑，优先发语义事件
- 连续动作不应绕开预算层强行触发多次反馈
- 音频场景切换不应再硬停硬起

### 4.4 庆祝与粒子预算

核心文件：

- [sparkle_confetti.dart](/Users/brsama/code/GitHub/Sparkle-project/mobile/lib/core/design/widgets/sparkle_confetti.dart)
- [global_particle_counter.dart](/Users/brsama/code/GitHub/Sparkle-project/mobile/lib/core/design/widgets/global_particle_counter.dart)
- [rarity_visual_wrapper.dart](/Users/brsama/code/GitHub/Sparkle-project/mobile/lib/core/design/widgets/rarity_visual_wrapper.dart)

- 小/中/大型庆祝强度
- 稀有度对应的 glow 与反馈强度

约束：

- 新增粒子类视觉效果时必须接入 `GlobalParticleCounter`
- 大面积庆祝效果必须加 `RepaintBoundary`

## 7. 当前一致性规则

后续前端开发必须遵守以下规则：

### 7.1 动效规则

- 进入类列表优先 `SparkleStagger*`
- 注意力吸附优先 `SparkleAttentionPulse`
- 退出类隐藏优先 `SparkleExitTransition`
- 非必要不新增独立 `AnimationController`
- 如必须使用 `AnimationController`，必须显式兼容 `context.reduceMotion`

### 7.2 声音规则

- route 级音频统一通过 `SceneAudioScope`
- 组件级反馈优先发语义事件，不直接控制原始 player
- 不允许为低价值动作叠加过重音效或高频 haptic

### 7.3 无障碍规则

- `reduceMotion` 打开后，所有错峰、pulse、shimmer、parallax 应可接受退化
- 所有关键状态页至少应具备基本 `Semantics`
- 大字体下不能依赖固定高度截断信息

### 7.4 性能规则

- 大面积粒子/庆祝/复杂 CustomPaint 默认加预算与 `RepaintBoundary`
- 不允许把庆祝型视觉效果直接铺满日常高频列表项
- 真机出现卡顿时，优先削减粒子、glow、实时模糊和重复动画，而不是牺牲主链可用性

## 8. 后续推荐动作

如果继续推进前端体验，推荐按这个顺序：

1. 真机录屏验收 `Splash -> Auth -> Onboarding -> Dashboard -> Chat -> Task -> Focus -> Achievement -> Community -> Settings`
2. 在中端 Android 上做 Galaxy、Achievement、Dashboard 三个重页面的帧率抽样
3. 针对真机发现的具体“刺点”做最后一轮定向打磨，而不是再大面积铺新动画

不建议的做法：

- 继续横向给低频后台页堆更多特效
- 在没有真机验证前继续增加更复杂的音频层
- 为单个页面写绕开共享系统的特殊动画基建

---

## 9. 当前结论

当前前端已经从“功能型应用界面”进入“有统一体验系统的产品界面”阶段。

关键变化不在于某一个页面更炫，而在于：

- 高频主链体验已经统一
- 次级页面不再明显掉队
- 共享底座已经形成
- 无障碍和性能约束已经进入系统层

后续工作重点不再是“继续铺更多效果”，而是：

- 用真机验证已有系统
- 用少量精准修正把它打磨到发布质量
