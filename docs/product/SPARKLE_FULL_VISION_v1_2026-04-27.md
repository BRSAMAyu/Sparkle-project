# 0. 最终一句话

Sparkle 是一个以 Aurora 为认知内核、以知识星图为用户世界模型、以任务卡为执行协议、以 Causal Control Spine 为因果控制主脊柱、以社群为共调节层、以 Skill Extraction 为持续学习机制的 AI-native 目标实现操作系统。

它不是一个更会聊天的 AI。

它最终应该像这样存在：

用户把自己的目标、材料、限制、情绪、时间、关系、社群、失败和反馈交给 Sparkle。
Sparkle 持续理解这些信息，并以可解释、可纠正、可验证的方式改变自己如何帮助用户。
用户不需要会写 prompt，不需要自己管理上下文，不需要自己判断资料优先级，不需要自己从失败中归因。
Sparkle 会把用户散落的人生片段编译成行动路径。

最终体验口号：

> Sparkle 不是替你回答问题。Sparkle 是和你一起把事情做成。

# 1. 完全体 Sparkle 的根本身份

## 1.1 Sparkle 不是这些东西

Sparkle 不是：

```text
聊天机器人
知识库
RAG 工具
学习计划生成器
任务清单
知识图谱展示页
成就系统
打卡社区
时间管理 App
AI 助手皮肤
```

这些都只是局部能力。

## 1.2 Sparkle 是什么

Sparkle 是：

```text
目标建模系统
+ 用户理解系统
+ 资料理解系统
+ 知识状态系统
+ 任务执行系统
+ 情绪/能量/时间感知系统
+ Aurora 认知控制系统
+ 自适应 Context / Harness Engineering 系统
+ 因果反馈学习系统
+ 社群共调节系统
+ 长期成长档案系统
```

更准确地说：

> Sparkle 是一个能持续把"用户想成为什么"转化成"今天具体该做什么"的系统。

## 1.3 Sparkle 的终局价值

普通 AI 的价值是：

> 你问得好，它答得好。

Sparkle 的价值是：

> 即使你问得乱、说不清、状态差、资料多、目标远、执行不稳，
> Sparkle 也能帮助你逐渐把事情推进到现实。

它解决的是：

```text
目标模糊
资料混乱
状态不稳
行动断裂
反馈缺失
长期坚持困难
失败归因错误
自我理解不足
```

# 2. 完全体用户体验：从第一次打开到长期成长

下面先从用户视角描述完整体验。

## 2.1 第一次打开：不是注册流程，而是相遇

用户第一次打开 Sparkle，不应该感觉进入了一个工具。

他应该感觉：

> 有一个系统正在认真、克制、聪明地理解我。

首页不是冷冰冰的表单，而是一个轻量入口：

```text
你现在最想推进什么？
[考试冲刺]
[长期学习]
[项目交付]
[自我成长]
[日常混乱整理]
[我也说不清]
```

用户选择或直接输入：

```text
我 7 天后计网考试，基本没学，想先别挂。
```

Sparkle 立即给出 First Minute Aha：

```text
明白。你现在不是"正常学习计网"，而是"7 天先过线抢救"。

这意味着普通复习计划会害你，因为它会把时间平均分给所有章节。

我们要先找：
1. 高频；
2. 可训练；
3. 最可能转成分数；
4. 现在还来得及补的部分。

现在不用填完整问卷。
你可以先上传课件/往年题，或者做一个 12 分钟诊断。
```

用户在 60 秒内获得一个明确感受：

> 它不是让我填表。它已经理解了我的处境。

## 2.2 冷启动建模：不是问卷，而是建立工作关系

Sparkle 的冷启动不是一次性"收集信息"。

它是一种协作关系的建立。

系统会分层收集：

**必须信息**

```text
目标是什么
截止时间
当前基础
可用时间
材料情况
用户想要的最低验收标准
```

**高价值信息**

```text
最害怕的部分
过去为什么失败
老师出题风格
用户习惯的学习方式
当前情绪压力
是否需要强提醒
是否接受直接指出问题
```

**可后续推断信息**

```text
执行稳定性
任务颗粒度偏好
错因类型
资料适配性
情绪波动规律
关系边界
```

关键原则：

> 不要为了建模而建模。
> 每个问题都要让用户感觉"问这个是为了更好帮我"。

## 2.3 用户上传资料：资料立刻变成世界的一部分

用户上传：

```text
计网课件
往年题
作业
老师复习提纲
错题截图
```

Sparkle 不只是存文件。

它会显示：

```text
我已经开始解析这些资料。

目前识别到：
- 传输层：TCP / UDP / 拥塞控制
- 网络层：IP / 子网划分 / 路由
- 应用层：DNS / HTTP
- 往年题中 TCP 窗口题出现频率较高

这些资料会接入你的计网知识星图，不会默认全部塞进每次回答。
我会按任务需要选择使用，避免污染上下文。
```

用户感受到：

> 我上传的东西不是附件，而是 Sparkle 世界模型的一部分。

## 2.4 知识星图：不是图，而是用户当前世界模型

完全体知识星图不只是可视化。

它是用户目标世界的可计算结构。

例如计网星图中每个节点都有：

```text
掌握度
考试权重
出现频率
难度
可训练性
前置依赖
关联资料
关联错因
关联任务卡
最近练习时间
推荐动作
社群共性错因
```

用户看到的不是一张漂亮图，而是：

```text
TCP 拥塞控制
掌握度：偏低
考试权重：高
当前错因：cwnd/ssthresh 混淆
关联资料：课件第 4 章 p32-p45
推荐动作：worked example → 2 道变式 → 小测
```

图谱能够回答：

```text
我为什么今天要学这个？
为什么不学那个？
为什么这份课件被用上？
为什么这一题错了会影响明天计划？
```

## 2.5 标准对话：用户感觉在和一个懂自己目标的人说话

完全体中，用户大多数时候仍然在标准对话层交流。

但每句话都受 Aurora 轻量控制。

用户问：

```text
TCP 拥塞控制是什么？
```

普通 AI 可能开始长篇解释。

Sparkle 会根据当前状态决定：

```text
你现在问这个，不是为了完整理解协议设计，而是为了能做窗口变化题。

我先用考试版本讲：
拥塞控制核心是根据网络拥塞情况调整 cwnd。

你现在最容易错的是：
1. 超时后 ssthresh 怎么变；
2. 三次重复 ACK 后 cwnd 怎么变；
3. 慢启动和拥塞避免什么时候切换。

我先给你一个 worked example，然后再让你做 2 道变式。
```

用户感受到：

> 它不是在讲知识点，它知道我为什么问这个知识点。

## 2.6 任务卡：执行世界的最小协议

完全体任务卡不是 todo。

每张任务卡都像一个小型学习协议。

例如：

```text
任务：25 分钟修复 TCP 拥塞控制窗口题

为什么做：
这是当前最高收益薄弱点。你最近 3 次都错在窗口变化判断。

目标：
做完后你能判断：
- 慢启动阶段 cwnd 怎么变；
- 超时后 ssthresh 和 cwnd 怎么变；
- 三次重复 ACK 后如何调整。

材料：
- 课件第 4 章 p32-p45
- 2023 期末 Q4
- 你的最近两道错题

步骤：
1. 5 分钟看压缩规则；
2. 8 分钟跟做 worked example；
3. 8 分钟做 2 道变式；
4. 4 分钟小测和错因标记。

卡住时：
不要重看完整课件。
点"我卡住了"，Sparkle 只调取当前题和相关规则。

完成后更新：
- TCP 拥塞控制掌握度
- 窗口变化错因状态
- 当前任务颗粒度判断
- 后续计划策略
```

用户不会觉得"我要完成一个任务"。

他会觉得：

> 我知道现在为什么做这个，做到什么程度算完成，卡住怎么办，做完会影响什么。

## 2.7 执行过程：系统持续感知，但不打扰

用户开始任务后，Sparkle 进入任务执行态。

它会感知：

```text
任务是否开始
是否超时
是否频繁求助
是否卡在某一步
是否跳过小测
是否多次要求重讲
是否切换资料
是否打开社群讨论
是否暂停太久
```

但它不会每分钟打扰用户。

它只在关键时刻介入：

```text
你已经在第 2 步停留了 11 分钟。
这一步原本只需要 8 分钟。
我先不催你。
我判断你可能卡在窗口变量变化。
要不要我用一个更小的例题带你走一遍？
```

这种介入不是监督，而是陪跑。

## 2.8 用户失败时：不责备，先归因

用户任务没完成。

普通任务系统：

```text
任务未完成。
```

Sparkle：

```text
这张任务没完成，不先算失败。

我需要判断原因：
A. 今天没有真实时间；
B. 任务排大了；
C. 资料看不懂；
D. 题型迁移卡住；
E. 你状态太差，不适合硬推。

你选一个，或者直接解释。
```

用户选择：

```text
不是没时间，是我不会做。
```

Sparkle：

```text
明白，那我收回"任务颗粒度偏大"的判断。
我现在改判为：主要问题是知识瓶颈，不是时间安排。
下一张任务我会保留短时长，但改成 worked example，不再直接让你刷题。
```

这是完全体 Sparkle 的关键体验：

> 用户的纠正会立即改变系统状态和后续行动。

## 2.9 Aurora 显性介入：像认知核心，而不是第二个聊天窗口

大多数时候 Aurora 在后台。

但当系统发现关键冲突时，Aurora 会显性出现。

例如：

```text
Aurora · 需要重新校准一个判断
```

用户点开。

Aurora：

```text
我发现一个冲突。
你一开始说每天能学 2 小时，
但最近两张任务都明显超时。

我现在有两个可能判断：
1. 我把任务排大了；
2. 你这两天临时有事；
3. 不是时间问题，而是知识点没建立起来。

这个判断会影响今晚计划，所以我不想继续猜。
你觉得更接近哪一个？

[确实排大了]
[只是这两天忙]
[不是任务大，是我不会]
[都不对，我解释一下]
```

用户选择后，Aurora 更新状态：

```text
收到。我把主要原因从"任务颗粒度偏大"改成"知识瓶颈更强"。

我会做三个调整：
1. 今晚任务仍控制在 30 分钟以内；
2. 不推进新章节；
3. 先用 worked example 修 TCP 窗口变化。

Aurora 先退回后台。
标准层会接着陪你完成任务。
```

这就是完全体 Aurora 的感觉：

- 会观察
- 会承认不确定
- 会提出假设
- 会让用户纠正
- 会改变系统
- 会退回后台

# 3. 完全体系统主脊柱：Causal Control Spine

完全体 Sparkle 的一切系统都要围绕这条链：

```text
Raw Event
→ Actionable Signal
→ Signal Ranking & Conflict
→ State Patch
→ Actionable State Register
→ Policy Arbitration
→ Aurora Control Signal
→ Directives
→ Actuation
→ Directive Audit
→ User-visible Receipt
→ Outcome
→ Causal Attribution
→ Model Update
→ Skill Extraction
```

## 3.1 Raw Event：事实

所有系统事件都先作为事实进入。

例如：

```text
用户完成任务
用户超时
用户错题
用户上传资料
用户纠正系统判断
用户打开社群资料
用户连续 7 天完成
用户 24 小时未回来
伙伴提醒用户
```

Raw Event 不做解释。

## 3.2 Actionable Signal：解释

系统把事件解释成可能有行动意义的信号。

例如：

```text
任务超时
→ 可能任务太大
→ 可能用户真实时间不足
→ 可能知识点太难
→ 可能资料不适合
```

每个信号带：

```text
claim
confidence
scope
ttl
evidence
counter_evidence
alternative_explanations
possible_effects
```

## 3.3 Signal Ranking & Conflict：排序与冲突

信号不是越多越好。

系统要判断：

```text
哪些信号最影响当前目标？
哪些信号会改变下一步？
哪些信号冲突？
哪些需要用户确认？
哪些可以静默处理？
```

例如：

```text
七连胜 → 可以提高挑战
焦虑高 → 不宜提高压力
考前 24h → 不开新章节
用户要求冲高分 → 可能需要增加难度
```

Aurora 必须仲裁。

## 3.4 Actionable State Register：可行动状态寄存器

它不是大画像。

它只存会影响行动的状态。

例如：

```text
goal_mode = exam_rescue
deadline_pressure = high
task_granularity_fit = too_large
knowledge_bottleneck = tcp_congestion_control
transfer_failure = true
retrieval_risk = medium
strategy_confidence = low
relationship_stance = direct_but_careful
```

每个状态都有：

```text
value
confidence
scope
ttl
evidence
counter_evidence
can_affect
user_visible
requires_confirmation_if_high_impact
```

## 3.5 Policy Arbitration：策略仲裁

这是完全体最关键的智能层之一。

它决定：

```text
主策略是什么
副策略是什么
哪些约束是硬的
哪些只是倾向
是否需要资料
是否需要 Aurora 显性介入
是否需要用户确认
是否需要重规划
是否需要召回
是否需要写入模型
```

例如：

```text
当前策略：
恢复可完成节奏 + 修复 TCP 瓶颈

硬约束：
- 今晚任务 <= 25 分钟
- 不推进新章节

软倾向：
- worked example 优先
- 语气直接但不施压
```

## 3.6 Directives：系统行动指令

Aurora 不只是写 prompt。

它输出不同类型的 directive：

```text
ResponseDirective
ExecutionDirective
PlanDirective
RetrievalDirective
ModelWriteDirective
NotificationDirective
UXDirective
SkillDirective
CommunityDirective
```

每类 directive 由下游模块结构化消费。

## 3.7 Actuation & Audit：执行与审计

每个模块执行后必须回报：

```text
我是否应用 directive？
应用了哪些约束？
哪些被覆盖？
为什么覆盖？
输出是否符合要求？
```

例如任务生成器：

```text
Directive: max_task_duration <= 25
生成任务: 23 分钟
Audit: applied=true
```

如果生成 40 分钟，必须 fail 或说明 override。

## 3.8 User-visible Receipt：用户可见回执

用户应该感受到：

> 因为我做了 X，Sparkle 改变了 Y。

例如：

```text
我把今晚任务压到 25 分钟。
原因是最近两次长任务都超时。
目标不是少学，而是先恢复可完成节奏。
```

这不是每次都长篇解释，而是在关键变化时给出短回执。

## 3.9 Outcome & Causal Attribution：结果与因果归因

系统要知道干预是否有效。

例如：

```text
缩短任务后用户完成了
→ 短任务可能适配当前状态

缩短任务后用户仍未完成，并反馈"不会做"
→ 问题可能不是时长，而是知识讲解方式
```

系统不会过度自信说"证明有效"，但会更新假设。

## 3.10 Skill Extraction：技能沉淀

当某种策略多次有效，Sparkle 提取为 skill。

例如：

```text
对于 7 天计网先过用户，
TCP 拥塞控制连续错时，
先 worked example，再 2 道变式，
比重看完整课件更有效。
```

Skill 分三类：

- Personal Skill
- Cohort Skill
- System Skill

最终 Sparkle 会越来越懂：

> 什么人在什么状态下，用什么策略更容易成功。

# 4. 完全体 Aurora

## 4.1 Aurora 的最终身份

Aurora 是 Sparkle 的认知内核。

它负责：

```text
感知状态
管理时间
裁决冲突
控制上下文
决定是否用资料
决定是否主动介入
决定如何表达
决定是否写入模型
决定是否重规划
决定是否生成任务
决定是否召回
决定是否唤醒完整 Aurora Core
```

Aurora 不是一个角色皮肤。

Aurora 是：

```text
状态系统
+ 决策系统
+ 控制系统
+ 自我修正系统
+ 用户协商系统
```

## 4.2 Aurora 的自我模型

完全体 Aurora 必须建模自己。

它会问自己：

```text
我现在对用户最重要的判断是什么？
哪些判断置信度不足？
用户有没有纠正过我？
我上次策略有没有起效？
我是不是任务排大了？
我是不是资料调用过多？
我是不是说话太像催促？
我是否需要主动找用户确认？
```

示例：

```json
{
  "aurora_self_state": {
    "current_primary_hypothesis": "用户卡点是题型迁移失败，而非概念完全空白",
    "confidence": 0.74,
    "open_questions": [
      "今晚真实可用时间是否只有 45 分钟",
      "用户是否仍以先过线为目标"
    ],
    "recent_self_correction": {
      "claim": "之前任务粒度可能偏大",
      "confidence": 0.68
    },
    "relationship_stance": "direct_but_careful",
    "next_best_confirmation": "确认任务颗粒度是否排大"
  }
}
```

这会让 Aurora 像"有连续思考"。

## 4.3 Aurora 的四种存在方式

### L0：规则感知层

不调用模型。

负责：

```text
时间
deadline
任务状态
静默事件
基本阈值
勿扰规则
```

### L1：轻量 Aurora

每轮对话都参与。

负责：

```text
意图判断
上下文选择
资料是否调用
```

# 5. 时间感知：Sparkle 活在时间里

完全体 Sparkle 必须有强时间感。

用户离开后，系统世界不会冻结。

## 5.1 返回体验

用户开始 45 分钟任务后离开 2 小时再回来。

Sparkle：

```text
你离开了大约 2 小时。
上一张 TCP 任务卡原本预计 45 分钟结束，但我还没有收到完成反馈。

先不用重新开始。
你现在是哪种情况？

[做完了，补记录]
[做了一半，卡住了]
[没开始]
[换个小任务]
```

这很重要。

普通 AI 没有时间连续性。
Sparkle 必须有。

## 5.2 Deadline Phase

考试目标中，时间阶段会自动改变策略。

```text
D-7 到 D-5：建立最小通过路径
D-4 到 D-3：主瓶颈训练
D-2：高频题型与错因修复
D-1：不学新章节，只做高收益复盘
D-0：保持状态，避免过载
```

用户 D-1 说想学新章节。

Sparkle：

```text
如果目标是先过线，现在不建议开新章节。

不是因为它不重要，而是因为还剩 24 小时，
新章节的理解成本高、转分不确定。

现在最划算的是：
1. 高频错因；
2. 公式和流程；
3. 短模拟；
4. 睡前错题摘要。
```

# 9. 主动召回：有价值的回来理由

|------|------|
| Activation Recall | 启动第一步 |
| Recovery Recall | 从失败恢复 |

召回不是：


而是：

> 现在回来做这个低成本动作，对你的目标很划算。

# 21. 最终铁律

完全体所有实现必须遵守这些铁律。

**铁律 1**：没有行动的理解不算理解

Sparkle 说"我懂你"没有意义。它必须因此改变下一步。

**铁律 2**：没有审计的智能是幻觉

Aurora 判断必须能追踪到事件、状态、directive、输出和结果。

**铁律 3**：用户永远有纠正权

所有高影响判断都必须可反驳。

**铁律 4**：资料不能污染上下文

上传资料不等于每轮使用资料。

**铁律 5**：任务卡不是待办

任务卡是策略执行协议。

**铁律 6**：社群不是广场

社群是共调节层和资源质量层。

**铁律 7**：成就不是糖果

成就是成长信号来源。

**铁律 8**：Aurora 不常驻

轻量 Aurora 常在，Full Aurora 稀缺而有仪式感。

**铁律 9**：系统必须会承认自己错了

SparkleSelfModel 是核心，不是附属。

**铁律 10**：最终目标不是好看，而是推进现实

所有 UI、动画、图谱、社群、成就，都必须服务用户目标推进。

# 22. 最终结语

完全体 Sparkle 的理想状态不是"功能非常多"。

而是：

> 每一个功能都接在同一条因果控制主脊柱上。
> 每一个数据都可能成为用户下一步更好的理由。
> 每一次失败都不是终点，而是模型更新。
> 每一次坚持都不只是徽章，而是系统重新理解用户的证据。
> 每一份资料都不只是文件，而是用户世界模型的一部分。
> 每一次对话都不只是回复，而是目标推进的一步。

最后用一句话收束：

> Sparkle 是一个能把用户的目标、资料、行动、失败、反馈和社群支持，持续编译成更好下一步的 AI-native 目标实现操作系统。

这就是完全体。
