## 0. Why This Document Exists

We have already built:

- the five bridges
- the soul/runtime substrate
- residual diagnosis
- decision policy
- experience actuation
- a first experience-phase evaluator

That is a major milestone.

It is still not the final product.

Sparkle is not being built to demonstrate that we can design sophisticated AI architecture.
Sparkle is being built to become:

> **an AI-native growth operating system that truly helps a person become who they want to become**

This document exists to define the next top-layer phases after bridge construction:

1. stronger live acceptance
2. UX polish on visible adaptation
3. manual and human evaluation of the north-star journey
4. system-level integration so Sparkle behaves more like one living organism than many disconnected subsystems

This is the shift from:

- “can the architecture support the vision?”

to:

- “does the product actually fulfill the vision for a real user?”

## 1. The Core Reminder

The highest rule does not change:

> **If a change does not improve user outcomes, it is not progress.**

Sparkle must not optimize for:

- architectural theater
- prompt cleverness
- number of agents
- number of models
- dashboard density
- internal sophistication that users cannot feel

Sparkle must optimize for:

- real helpfulness
- correct diagnosis of what matters now
- real changes to the system when the user needs them
- trustworthy continuity over time
- user-specific adaptation
- long-term flourishing, not just short-term task completion

## 4. The Five-Layer Configuration System Status

We previously aligned on a multi-layer configuration / self-modification model.

That model remains correct.

### 4.1 The Five Layers

1. `Constitutional layer`
   What cannot silently change.

2. `Session layer`
   Immediate, reversible turn-level adjustments.

3. `Episode layer`
   Short-term persistence for the current goal, stress period, exam week, or recovery window.

4. `Profile layer`
   Cross-session learned user tendencies that require repeated evidence.

5. `System layer`
   Which pipelines, capabilities, models, feature mixes, and orchestration styles Sparkle may use.

### 4.2 Current Status

| Layer | Status | Notes |
|---|---|---|
| Constitutional | Mostly built | Constitution and identity kernel exist; drift rules exist |
| Session | Built v1 | Companion and strategy session writes exist |
| Episode | Partially built | Promotion paths exist, but live behavior proof is still limited |
| Profile | Partially built | Learned tendencies exist, but validation and conflict resolution remain immature |
| System | Mostly future | Sparkle does not yet truly operate the whole body/config surface |

### 4.3 Strategic Meaning

This means:

- the five-layer idea was right
- it is not fully realized yet
- we should not pretend the system layer is already complete

The next phases should strengthen:

- live reliability of session/episode/profile learning
- design of the future system layer
- body awareness so Sparkle can know what capabilities it actually has

## 5. What the Next Chapter Must Accomplish

The next chapter is not “more architecture.”

It is:

> **turning the current architecture into a live product that feels coherent, adaptive, and genuinely helpful**

This chapter has four goals:

1. prove the live system works through stronger acceptance
2. make adaptation visible and emotionally legible in the user experience
3. establish real human evaluation loops
4. begin unifying Sparkle’s many subsystems into one AI-operable body

---

## 6. Phase A: System-Safe Live Acceptance

### 6.1 Goal

Upgrade acceptance from controlled proof to trustworthy product proof.

### 6.2 Why This Matters

Right now, the biggest remaining gap is proof quality.

We have component proof.
We have orchestrator-backed proof.
We still do not have final confidence that the live stack wins the real scenario under realistic constraints.

### 6.3 Build Targets

1. Finish walking the backend suite with `--maxfail=1` until the primary orchestration and growth paths are system-safe.
2. Make every shadow path non-fatal:
   - card protocol dual-write
   - shadow projections
   - weighted fallbacks
   - optional sidecar systems
3. Strengthen acceptance tests so the live orchestrator path is minimally stubbed.
4. Build a scenario matrix beyond one happy-path thermodynamics test.

### 6.4 Required Acceptance Matrix

At minimum, acceptance must cover:

- `R_e` cognitive repair with user materials
- `R_c` overload and immediate load-shedding
- `R_c` recovery into mobilization
- `R_n` normative decision support
- `R_i` identity-fragile moment with evidence-based reframe
- multi-session continuity after a real adaptation

### 6.5 Deliverables

- stronger live orchestrator acceptance tests
- fewer import/logic stubs in north-star acceptance
- explicit “shadow path must not poison core flow” regressions
- a release-style acceptance checklist for experience-phase runtime

### 6.6 Done When

- the main backend suite is no longer blocked by known integration failures in the growth path
- live acceptance covers all four residual families
- the north-star journey is proven on the real primary orchestration path with only necessary external stubs

## 7. Phase B: UX Polish on Visible Adaptation

### 7.1 Goal

Make Sparkle’s intelligence something the user can actually feel, not just something the backend computes.

### 7.2 Core Principle

Every important internal change should become one of:

- a sentence
- a question
- a card
- a visible shift in guidance
- a visible shift in plan or workload

### 7.3 Product Areas to Polish

#### Chat Experience

- opening language after system updates
- “I adjusted this because...” messages
- follow-up feedback questions that feel light, warm, and natural
- clearer evidence-grounded phrasing when user materials are used
- continuity callbacks to earlier struggles and recoveries

#### Home Experience

- growth narrative before dashboard mechanics
- clearer explanation of what changed since yesterday / this week
- visible “what Sparkle noticed” card
- visible “why this is the next move” card

#### Adaptation Transparency

- show when strategy changes were applied
- show what changed:
  - difficulty
  - load
  - pacing
  - explanation mode
  - session mode
- show reversibility:
  - “we can change this again if it doesn’t help”

### 7.4 Interaction Doctrine

The user should repeatedly feel:

- Sparkle saw the real issue
- Sparkle changed something real
- Sparkle did not overreact
- Sparkle stayed honest
- Sparkle remembers the trajectory

### 7.5 Deliverables

- backend language templates / prompt polish for visible adaptation
- mobile chat polish on system updates and feedback moments
- home screen growth narrative polish
- product language review for residual-specific response styles

### 7.6 Done When

- a user can point to at least one concrete visible adaptation per meaningful struggle cycle
- the UI no longer hides core intelligence behind generic task surfaces
- adaptation feels calm, truthful, and personal rather than theatrical

## 8. Phase C: Manual and Human Evaluation of the North-Star Journey

### 8.1 Goal

Create a real evaluation loop with humans, not just automated tests.

### 8.2 Why This Matters

This product cannot be validated only by unit tests and integration tests.

Sparkle’s success depends on:

- whether the user felt understood
- whether the intervention timing felt right
- whether the adaptation was trusted
- whether the guidance actually improved outcomes

### 8.3 North-Star Evaluation Scenario

Use the thermodynamics-in-14-days journey as the first formal human evaluation protocol.

Baseline scenario:

- user uploads textbook, PPTs, homework, and notes
- user has real misconceptions
- user experiences overload in the middle of the journey
- Sparkle must diagnose, ground, adjust, and recover momentum

### 8.4 Human Evaluation Dimensions

#### Outcome

- did understanding improve?
- did execution improve?
- did the user make it further than without Sparkle?

#### Experience

- did the user feel accurately seen?
- did they feel the timing was right?
- did they notice real change?
- did trust increase across days?

#### Intelligence

- was the residual diagnosed correctly?
- was the loop selected correctly?
- was grounding appropriate?
- was the intervention reversible and non-manipulative?

### 8.5 Evaluation Methods

1. guided internal founder walkthroughs
2. scripted pilot users with structured debrief
3. transcript review using a rubric
4. outcome comparison before/after intervention cycles

### 8.6 Required Artifacts

- evaluator rubric
- tester runbook
- transcript review template
- scenario score sheet
- issue triage tags:
  - diagnosis wrong
  - timing wrong
  - adaptation invisible
  - grounding weak
  - continuity weak
  - tone drift

### 8.7 Done When

- at least one north-star scenario can be run repeatedly by humans with a stable rubric
- findings from human review feed back into implementation priorities
- product decisions are no longer based only on engineering intuition

## 9. Phase D: Body Awareness and Organic System Integration

### 9.1 Goal

Begin turning Sparkle from “many available systems” into “one AI-operable body.”

### 9.2 Why This Matters

Sparkle already has:

- multiple models
- many agents
- OpenClaw pipeline
- routing and prediction
- feedback systems
- community systems
- galaxy systems
- achievement systems
- visual and environmental systems

These are valuable only if the AI can understand:

- what they are
- what they are for
- when they should be used
- what they cost
- what state they are currently in

### 9.3 The Required New Layer

Sparkle now needs a `body map` and `capability registry`.

This is not a giant prompt.
It is a structured runtime map of:

- available organs / subsystems
- readable state
- writable state
- costs
- risks
- permissions
- typical use cases
- current availability

### 9.4 Output of This Phase

Sparkle should increasingly be able to answer, internally:

- What can I do right now?
- What part of my body should I use?
- What evidence do I still need?
- What will this action cost?
- What should remain unchanged?

### 9.5 Scope Boundary

This phase should begin as a design and substrate phase.
It should not delay Phases A-C.

User value still comes first.
Body-awareness work should be tied to live benefit, not abstract AGI excitement.

### 9.6 Deliverables

- capability registry spec
- body-map runtime artifact
- subsystem health and availability model
- model/agent role map
- system-layer configuration design for future bounded AI operation

### 9.7 Done When

- Sparkle can reason over its own tools, models, and subsystems as a coherent capability surface
- new orchestration decisions are based on structured body knowledge, not scattered prompt hints

## 10. Recommended Execution Order

### 10.1 Immediate Order

1. Finish system-safe backend hardening via full-suite `--maxfail=1`
2. Complete stronger live acceptance
3. Polish visible adaptation on chat and home
4. Formalize manual/human evaluation of the thermodynamics journey
5. Design the body-awareness / capability-registry layer

### 10.2 Why This Order

Because:

- trust requires system safety
- UX polish without reliable runtime is theater
- human evaluation without a reasonably stable product wastes signal
- body-awareness design is important, but should not outrun real user value

## 12. What We Must Not Lose

As we move from architecture into live product work, we must not lose the original vision:

- Sparkle is a growth system, not a generic assistant
- each user has their own Sparkle
- Sparkle should be allowed bounded growth and self-definition
- the companion relationship matters
- the AI should increasingly know its own body
- every subsystem should eventually become part of one coherent organism

But we must also not lose the other side of the consensus:

- the user benefit is the judge
- truth matters
- safety matters
- reversibility matters
- no internal sophistication counts if the user cannot feel the help

Short version:

> **Build the organic system. Judge it by real human benefit.**
