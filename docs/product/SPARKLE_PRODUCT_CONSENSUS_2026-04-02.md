## 2. 最终定义: Sparkle 到底是什么

### 2.1 最终产品定义

Sparkle 从现在开始，统一定义为:

`AI 学习成长系统`

这一定义高于“助手”，也高于“教练”。

- 它不是 AI 学习助手。
- 它不是 AI 教练产品。
- “教练”最多只是系统在某些场景下采用的一种交互角色。
- “助手”最多只是系统在某些任务上的局部能力表现。

Sparkle 的本质不是回答问题，也不是陪聊，更不是做一个功能很多的学习 App。

Sparkle 的本质是:

`帮助用户跨越“理想中的自己”和“现实中的自己”之间鸿沟的 AI 学习成长系统。`

### 2.2 为什么是“学习成长系统”

创始人的核心愿景已经很清楚:

- 学习只是人成长的一部分，不是全部。
- 真正的需求不是“学会某个知识点”，而是“成为更好的自己”。
- 用户长期痛苦，不只是不会学，而是明明知道自己想成为什么样的人，却总在现实里走不动、走偏、走断。

因此，Sparkle 的目标不是单点提高效率，而是帮助用户完成:

- 从当前状态到目标状态的路径设计
- 在路径中不断前进
- 在走偏时及时被发现并被拉回
- 在一次次反馈中真正形成成长

### 2.3 产品一句话口径

推荐统一口径:

`Sparkle 是一个围绕学习场景构建、帮助用户持续走向更好自己的 AI 学习成长系统。`

内部更完整的版本:

`Sparkle 是一个通过感知、诊断、干预、验证和再优化，帮助用户跨越理想与现实落差的 AI 学习成长系统。`

## 3. 我们服务的根本需求是什么

### 3.1 最高层需求

Sparkle 最终满足的不是“完成任务”或“获得答案”，而是更高层次的需求:

`自我实现`

但产品不能直接从“自我实现”这四个字出发，因为它太抽象、太宏大、太难落地。

所以必须拆成层次化需求结构。

### 3.2 需求层级

从底到高，Sparkle 面对的是五层需求:

| 层级 | 需求 | 用户内心表达 |
|------|------|--------------|
| 第 1 层 | 行为发生 | 我今天真的做了 |
| 第 2 层 | 卡点可见 | 我终于知道自己卡在哪里 |
| 第 3 层 | 路径清晰 | 我知道接下来该怎么走 |
| 第 4 层 | 自我效能 | 我知道自己是能做到的 |
| 第 5 层 | 自我实现 | 我正在成为更好的自己 |

当前共识是:

- 第 5 层是北极星，不是第一天就能直接交付的体验。
- 第 4 层“自我效能感”是产品最核心的长期体验结果。
- 第 2 层“卡点可见”是当前最关键的中枢层。
- 第 1 层“行为发生”是用户愿意留下来的最低保证。

### 3.3 用户的真实痛苦

大学生或年轻用户使用 Sparkle 时，真实需求大致分为三类:

| 类型 | 需求 | 当前共识 |
|------|------|----------|
| 执行型 | 我知道要做什么，但做不到 | Sparkle 相对较强 |
| 方向型 | 我有目标，但不知道如何拆 | Sparkle 有雏形但体验偏硬 |
| 认知型 | 我学了但没真正懂，不知道自己哪里没懂 | Sparkle 当前最薄弱 |

专家讨论中反复确认:

`类型 C，也就是“认知型需求”，是最痛、最被忽视、也最能形成产品壁垒的需求。`

## 4. Sparkle 要解决的核心矛盾

创始人的描述中最关键的一点，是“红宫”问题:

`人的理想预期和现实实现之间存在巨大的落差。`

用户会反复经历这样的过程:

1. 我想变得更好。
2. 我相信自己应该能做到。
3. 我开始了。
4. 我因为拖延、理解障碍、意志不稳、环境干扰、时间不足而中断。
5. 我开始怀疑自己。
6. 我痛苦，不是因为目标不重要，而是因为我觉得自己不配做到。

因此，Sparkle 不是简单地帮助用户“执行任务”，而是要帮助用户解决这个更深的矛盾:

`如何让一个想成为更好自己的人，不再因为一次次走不动而否定自己。`

这也是为什么 Sparkle 必须是“成长系统”，而不是单纯的工具。

## 5. Sparkle 的核心价值主张

### 5.1 系统真正要做的四件事

Sparkle 的真正价值，不是模块数量，而是持续完成以下四件事:

1. 帮用户看清自己真正想去哪里。
2. 帮用户把目标拆成现在能走的一小段。
3. 在用户走偏、走不动、走假了的时候，比用户更早发现。
4. 用新的证据重写下一步，而不是重复喊加油。

### 5.2 从工具到系统的变化

普通工具只做一小段:

- 给答案
- 给计划
- 给提醒
- 给复习

Sparkle 要做的是整段:

`目标形成 -> 路径生成 -> 执行推进 -> 认知诊断 -> 行为纠偏 -> 干预验证 -> 系统学习`

只有当这条链成立时，Sparkle 才配叫“系统”。

### 5.3 最终闭环定义

经过多轮讨论，最终闭环被修正为:

`发现问题 -> 以用户可接受的方式交付 -> 用户愿意采纳 -> 产生行动 -> 验证有效 -> 更新系统`

这里最重要的修正有两个:

- 不是“发现问题”就算完成。
- 不是“建议用户改变”就算闭环。

少了下面两步，系统在产品上就不成立:

1. 以用户可接受的方式交付
2. 用户愿意采纳

## 6. 当前系统的真实状态

### 6.1 核心判断

当前 Sparkle 不是没有能力，而是能力结构失衡。

系统已经具备大量模块、服务和设计，但整体更像:

`诊断能力强，行动能力不足，验证能力薄弱`

### 6.2 当前能力状态

| 能力层 | 当前状态 | 说明 |
|--------|----------|------|
| 感知/观测 | 较强 | 错题、计划、专注、行为、进度、画像信号已有大量积累 |
| 诊断/分析 | 可用 | 能识别概念混淆、拖延、计划风险、低掌握度等 |
| 处方/行动 | 断裂 | 诊断结果大量停留在分析层，未充分改写真实路径 |
| 验证/回流 | 薄弱 | 系统尚不清楚某次干预是否真的有效 |

### 6.3 当前系统最大的结构性问题

最核心的问题不是“缺功能”，而是:

`模块很多，但没有共同服务于唯一主链路。`

当前系统更像:

- 有计划系统
- 有错题系统
- 有知识星图
- 有报告系统
- 有推送系统
- 有编排系统
- 有情绪和设计系统

但这些系统尚未被强约束到同一个价值中心:

`帮助用户真正发现卡点、接受纠偏、走回路径并形成成长。`

## 7. 对几位专家观点的综合吸收

### 7.1 创始人提供的核心方向

创始人明确给出了最重要的长期愿景:

- 产品不是单纯为学习存在，而是为成长存在。
- 学习场景是切口，但本质是帮助用户成为更好的自己。
- 系统必须具备成长性，必须随着用户状态变化而不断重写路径。
- 系统必须形成全链路反馈闭环，越用越懂用户，越用越有效。
- 设计系统、BGM、动效、成就、社交、伙伴等并非装饰，而是用于支撑用户坚持下去。

这一定义为 Sparkle 提供了最高层的存在意义。

### 7.2 专家一提供的核心修正

专家一指出了当前产品最关键的断裂:

- Sparkle 更会追踪执行，不够会追踪理解。
- 系统能告诉用户“你完成了多少任务”，但不能真正告诉用户“你到底哪里没懂”。
- 错题本、知识星图、掌握度系统的概念方向是对的，但尚未形成真正的理解质量地图。
- 推演、模拟、报告虽然有能力，但更多依赖用户主动触发，而不是系统主动把关键帮助送到面前。

这让整个讨论第一次明确到:

`理解质量追踪` 是最关键的产品缺口。

### 7.3 专家二提供的核心收敛

专家二把讨论从“愿景”收敛到了“系统状态”:

- 系统不是不能诊断，而是“能看到问题，却没有把方向盘接上”。
- 关键问题在于“诊断 -> 行动”没有打通。
- 真正壁垒是“纵向证据链 x 时间积累”。
- 不是单次聪明，而是长期知道用户在哪里卡住、干预了什么、是否真的改善。
- 90 天不该再扩功能，而该接通 6 个断点。

这让团队第一次明确:

`Sparkle 的核心不是多模块，而是一个能被验证的纠偏闭环。`

### 7.4 后续专家补充的关键修正

后续最重要的修正来自一个此前讨论不足的问题:

`用户抗拒力`

也就是:

- 系统可以判断你卡住了
- 系统可以提醒你偏了
- 但用户未必愿意被这样对待

现实中，很多用户面对这类反馈会产生强烈防御:

- “我知道我烂，别提醒我”
- “别再给我增加焦虑了”
- “你谁啊，管我”

因此，Sparkle 的核心不只是更早发现问题，而是:

`更早发现问题，并用用户愿意接受的方式帮助他重新走起来。`

这是本轮讨论中最关键的体验修正。

## 8. 用户抗拒力: 这不是附加问题，而是核心问题

### 8.1 为什么这是关键风险

所有技术闭环都隐含一个前提:

`用户愿意接纳系统的干预。`

如果用户不接受:

- 最好的诊断也只是压迫感
- 最好的预警也只是打扰
- 最好的重规划也只是系统自嗨

因此，Sparkle 的闭环不能只从技术正确出发，必须从用户心理接受度出发。

### 8.2 设计结论

Sparkle 的干预方式必须满足:

1. 不审判
2. 不羞辱
3. 不替用户做道德评价
4. 不先告诉用户“你又失败了”
5. 先建立同侧关系，再提出改动建议
6. 优先引发好奇和重新启动，而不是制造羞耻和焦虑

### 8.3 团队统一体验原则

这句原则必须成为所有产品和文案决策的最高约束:

`Sparkle 不是指出你不行，而是帮助你重新变得能走。`

进一步展开就是:

`Sparkle 不是来证明用户做得不够好，而是来帮助用户在不否定自己的前提下重新启动。`

## 9. 为什么用户不用 ChatGPT、Claude、DeepSeek 或传统学习软件

### 9.1 通用 AI 的强项

ChatGPT、Claude、DeepSeek 的强项是:

- 单次回答质量高
- 即问即答快
- 推理和表达能力强
- 覆盖面广

如果 Sparkle 只是一个“更像学习场景的聊天机器人”，那没有胜算。

### 9.2 传统学习工具的强项

Anki、Quizlet 等传统工具的强项是:

- 学习动作简单直接
- 低摩擦
- 复习结构稳定
- 高度聚焦单一任务

如果 Sparkle 只是错题本、提醒器或复习器，也很难胜。

### 9.3 Sparkle 必须赢的地方

Sparkle 必须赢在三件事上:

1. 不只是回答，而是修正路径
2. 不只是记忆，而是诊断卡点
3. 不只是响应，而是主动发现问题并帮助用户接受改变

一句话概括:

`别人回答问题，Sparkle 纠正轨迹。`

## 10. Sparkle 的真正壁垒

### 10.1 短期壁垒: 执行层嵌入深度

短期最现实的壁垒不是“系统多懂你”，而是:

`系统真能嵌入你的日常执行过程。`

包括:

- 专注计时
- 环境陪伴
- 不中断推进
- 错题沉淀
- 计划和任务联动
- 学习过程中的即时反馈

用户不会因为“长期壁垒”而第一天留下来，但会因为“今天真的被帮到了”而留下来。

### 10.2 中期壁垒: 纠偏能力

系统能够:

- 比用户更早发现问题
- 比用户更早发现这不是意志力问题，而是概念、节奏、负荷或路径问题
- 用用户愿意接受的方式推动他重新启动

### 10.3 长期壁垒: 纵向因果证据闭环

长期真正不可复刻的壁垒，是:

`用户成长过程中的纵向因果证据链`

也就是系统长期知道:

1. 你在哪类目标上最容易中断
2. 你在什么情境下最容易拖延、放弃或自我怀疑
3. 什么干预对你有效，什么无效
4. 什么进步是真正内化的，什么只是表面完成

壁垒演进路径:

`短期靠执行层嵌入留住用户 -> 中期靠纠偏能力建立差异 -> 长期靠证据闭环形成壁垒`

## 11. 当前最关键的产品断裂点

经过综合讨论，当前最重要的不是功能缺失，而是核心链路断裂。

### 11.1 六个主要技术断点

1. `adaptive_replanner` 已能产生调整，但未真正写回计划执行
2. 错题分析结果更多更新画像信号，而未充分回写知识节点掌握度
3. `plan health = critical` 等高风险状态没有稳定转化为事件和行动
4. 推送/干预更多是时间驱动，而不是行为驱动
5. `cognitive_adjustments` 更偏 prompt 层，未充分改变实际参数和策略
6. 干预后缺少系统化效果验证与回流

### 11.2 但它们并非同等优先级

最终共识是:

最优先的不只是“把断点接上”，而是:

`让断点接上后，用户愿意被这样对待。`

因此，真正的优先级应该是:

第一梯队:

1. 干预交付方式和语言体系
2. `adaptive_replanner -> 计划执行`
3. 错题分析 -> 知识节点掌握度

第二梯队:

4. 风险事件触发
5. 行为触发推送
6. 参数级调整

第三梯队:

7. 干预效果验证与回流

注意:

第 1 项不是传统意义上的“技术断点”，但它决定了其他断点接通后的用户体验生死。

## 12. 未来 90 天的唯一主题

### 12.1 总原则

未来 90 天不再以“多做功能”为目标，而以“跑通一个真实可验证的成长闭环”为目标。

原则如下:

1. 暂停大多数非核心新功能开发
2. 所有研发资源优先服务于主链路
3. 所有体验打磨优先服务于主链路
4. 所有演示、复赛叙事必须建立在真实闭环之上

### 12.2 90 天路线图

#### 0-20 天: 接通核心数据与计划执行

目标:

- 错题分析回写知识节点掌握度
- `adaptive_replanner` 真正写回计划
- 梳理干预语言体系与文案框架

成功标准:

- 系统不只是知道用户卡住了
- 系统真的会改后续路径

#### 21-50 天: 接通主动预警与行为干预

目标:

- `plan health = critical` 等风险状态稳定转化为事件
- 推送系统支持行为触发
- 干预语言 A/B 测试

成功标准:

- 系统开始主动而不是被动
- 系统的干预不只是能发出，而是更容易被接受

#### 51-70 天: 接通参数层与效果回流

目标:

- 让 `cognitive_adjustments` 改变实际参数
- 建立干预后效果验证和回流机制

成功标准:

- 系统开始学习“什么方法对这个用户有效”

#### 71-90 天: 打磨单一端到端主场景

目标:

- 完成一个稳定可演示、可验证、可复用的主链路闭环
- 用于复赛、答辩和真实用户测试

成功标准:

- 不只是模块能跑
- 而是用户结果真的被改变

## 13. 指标体系: 分阶段，不冒进

### 13.1 为什么不能一开始就只看最终指标

“7 日关键卡点解决率”方向是对的，但它高度依赖系统已经具备稳定的卡点识别和干预能力。

在能力尚未成熟时，直接用它作为当下唯一主指标，会导致失真。

因此，共识是采用分阶段指标体系。

### 13.2 分阶段主指标

| 阶段 | 主指标 | 含义 |
|------|--------|------|
| 0-30 天 | 关键链路完成率 | 用户从“我有目标”到“今天完成一个具体动作”的比例 |
| 30-60 天 | 主动纠偏采纳率 | 系统发出干预后，用户接受并执行的比例 |
| 60-90 天 | 7 日关键卡点解决率 | 被识别出的关键卡点在 7 天内真实改善的比例 |

### 13.3 长期北极星

长期北极星仍然定义为:

`7 日关键卡点解决率`

建议长期定义:

被系统识别为高优先级卡点的用户，在 7 天内满足以下条件中的至少两项:

- 同类错误复发率下降
- 关联节点掌握度提升
- 计划健康度恢复到安全区间

### 13.4 衡量“系统比用户更早发现问题”

统一公式:

`主动纠偏有效率 = 预警命中率 x 用户采纳率 x 干预后改善率`

### 13.5 护栏指标

必须同时观察:

- 7 日留存
- 关键链路完成率
- 干预打扰率
- 干预关闭率

这组指标的作用是防止系统变成“更智能的骚扰器”。

## 14. 复赛与对外展示: 只证明一件事

复赛不应该证明:

- 我们有多少服务
- 我们有多少模块
- 我们有多复杂的架构
- 我们有多少表

复赛只需要证明一个最小闭环:

`用户快失败了 -> 系统发现真正卡点 -> 用不引发防御的方式让用户采纳 -> 用户行为真的改变 -> 系统记住这种方法有效`

### 推荐主场景

热力学复习场景被一致认为是最佳主场景之一:

1. 用户说: “我热力学完全不会，考试两周后”
2. 系统澄清后，生成可执行的两周路径
3. 用户执行到第 3 天，在“热力学过程分类”上连续卡住
4. 系统发现: 不是单纯偷懒，而是概念混淆
5. 系统不用“你已经错了三次”来交付，而用更低防御、更高接受度的方式:
   “我发现一个有趣的现象，你在可逆和不可逆过程之间总是更容易选前者，我们来试个东西？”
6. 用户愿意花 20 分钟补一个关键概念
7. 后面的任务推进明显变顺
8. 系统记录: 这种引导方式对该用户有效

这一个场景跑通，远比 26 个模块都做到 80 分更有价值。

## 15. 我们现在不该做什么

未来 90 天的战略取舍必须足够残酷。

### 不该做的事

1. 不扩新场景
   身材管理、技能成长、作品创作等可以是长期方向，但现在先不扩。

2. 不追求大而全模块建设
   不是功能越多越像系统，而是闭环越完整越像系统。

3. 不做全面 UI 抛光
   当前 UI 只打磨主链路关键时刻。

4. 不做孤立的炫技 Demo
   不以“看起来很厉害”为目标，而以“真的改变用户下一步行为”为目标。

5. 不把知识星图继续做成展示中心
   它首先是证据界面，不是视觉主角。

### 必须始终记住的判断

- 情绪价值是启动器，不是壁垒。
- 视觉体验是放大器，不是核心。
- 知识星图是证据界面，不是价值本身。
- 真正的核心，是诊断、纠偏、验证。

## 16. 设计系统、情绪价值与社交的真正位置

这部分不是外围，而是必须重新理解。

### 16.1 情绪价值不是“锦上添花”

情绪价值不只存在于:

- BGM
- 触感
- 动效
- 成就弹窗

更关键的是存在于:

`系统指出你可能不行的时候，如何不让你立刻防御。`

因此，真正关键的情绪设计场景不是“庆祝成功”，而是“系统在你快失败时如何和你说话”。

### 16.2 社交、伙伴和分享的作用

社交、责任伙伴、分享系统的本质，不是单纯做社区。

它们服务于三件事:

1. 让用户获得关系中的力量
2. 让用户在成长中感到被看见
3. 用外部连接降低放弃率

它们应当是成长系统的增强层，而不是独立的热闹模块。

## 17. Sparkle 的长期演化方向

虽然当前聚焦学习场景，但长期系统形态已经基本明确。

### 17.1 从学习切入，到成长扩展

路线应当是:

1. 先在学习场景跑通最小闭环
2. 再把这套“目标 -> 路径 -> 卡点 -> 干预 -> 验证”的底层能力抽象出来
3. 未来扩展到其他成长类目标场景

### 17.2 系统真正会成长的标志

Sparkle 未来不是因为“功能更多”而变成成长系统，而是因为它开始具备这些能力:

- 真的越来越懂同一个用户
- 真的知道什么方法对这个用户有用
- 真的能随着用户变化而重写路径
- 真的能帮助用户形成长期自我效能

这才叫“系统会成长”。

## 18. 最终共识摘要

如果只保留最重要的结论，统一如下:

1. Sparkle 的最终定义是 `AI 学习成长系统`，不再以“助手”或“教练”作为产品定义。
2. 学习是切口，不是终点；真正服务的是“成为更好的自己”。
3. 当前最核心的中枢问题不是执行，而是“卡点可见”和“纠偏有效”。
4. 当前系统的问题不是缺功能，而是没有足够集中地服务唯一主链路。
5. 真正闭环不是“诊断 -> 行动 -> 验证”，而是“发现 -> 可接受交付 -> 愿意采纳 -> 行动 -> 验证 -> 更新系统”。
6. 最大风险不是技术做不到，而是用户不愿意被这样对待。
7. 短期靠执行层嵌入留住用户，中期靠纠偏能力建立差异，长期靠证据闭环形成壁垒。
8. 未来 90 天应暂停大多数新功能开发，集中跑通一个真实闭环。
9. 分阶段指标比一步到位的最终指标更现实。
10. 复赛只证明一个主场景，不证明全部系统。

## 19. 这份文档之后怎么用

从现在开始，以下场景都必须回看这份文档:

- 新功能立项前

4. 它是否增强了 Sparkle 作为“学习成长系统”的闭环能力？

如果答案是否定的，那它就不是当前阶段的核心工作。
