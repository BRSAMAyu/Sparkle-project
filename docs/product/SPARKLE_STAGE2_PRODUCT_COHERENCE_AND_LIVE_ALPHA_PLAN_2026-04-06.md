## 0. Why This Document Exists

We have now completed and frozen the design of the five implementation phases:

- Phase A: User Insight Engine
- Phase B: Planning Engine
- Phase C: Feedback and Growth Engine
- Phase D: Body Awareness and Capability Governance
- Phase E: Five-Layer Learning System

This is a major milestone.

It is **not** the same as product truth.

The system now has enough architecture, enough bridges, enough state, and enough runtime intelligence that the main question has changed.

The old question was:

> Can Sparkle be designed as a serious AI-native growth system?

The new question is:

> Can Sparkle run as one coherent product organism, help a real user in a way they can feel, and prove it better than raw AI use?

This document defines that next chapter.

It is not another foundation plan.

It is the plan for moving Sparkle from:

> **improved internal system**

to:

> **living, runnable, judgeable product**

---

## 1. Honest Current State

### 1.1 What Is Now Real

Sparkle now has a serious operating substrate:

- understanding state compilation
- planning readiness and planning quality control
- feedback binding and validated learning
- body-awareness and capability governance
- five-layer learning and drift-aware governance
- visible adaptation surfaces
- benchmark and evaluation harnesses

This means Sparkle is no longer a vague architecture project.

### 1.2 What Is Still Not Proven

The product is still not yet fully proven in the way that matters most:

- full-stack startup and runnable coherence are not yet treated as the primary truth source
- the real mobile experience is not yet the main judge of progress
- evaluators are still stronger as regression harnesses than as final product truth
- human evaluation exists, but has not yet become the center of the roadmap
- the system is still richer internally than it is proven externally

### 1.3 Bottom-Line Status

Current status should be described as:

> **Architecture-complete enough to stop inventing major new foundation layers**  
> **Product-incomplete enough that we must now shift to runnable coherence, human judgment, and Live Alpha truth**

---

## 2. The Goal of Stage 2

Stage 2 has one core objective:

> **Make Sparkle boot, run, feel coherent, help one user deeply, and prove it.**

This breaks down into four product truths:

1. Sparkle can be run reliably through one real full-stack path.
2. Sparkle can complete the north-star loop as one coherent product.
3. Users can feel visible, truthful adaptation.
4. Human evaluation can judge Sparkle using real transcripts and change the roadmap.

If Stage 2 succeeds, Sparkle reaches a truthful `Live Alpha`.

---

## 3. The Main Strategic Principle

From this point forward, every meaningful change should answer:

> **Does this make Sparkle better at understanding the user, planning for the user, or improving through real feedback?**

If the answer is no, it is not Stage 2 priority.

This means we should now optimize for:

- runnable coherence
- user-visible helpfulness
- plan usefulness
- grounded adaptation
- continuity
- repeated human truth

We should **not** optimize for:

- more architecture for its own sake
- more agents without clear user benefit
- more internal cleverness users cannot feel
- evaluator score inflation
- polishing side systems before the core loop is alive

---

## 4. The Core Loop We Are Now Judging

Stage 2 judges one strict Sparkle loop:

1. user gives a goal
2. Sparkle understands the user and what is still missing
3. Sparkle creates the plan or asks one high-value clarification first
4. user acts, or an execution system acts on the plan
5. Sparkle receives evidence, feedback, and outcome signals
6. Sparkle adapts the next move visibly and helpfully
7. Sparkle preserves continuity across time

This is the main loop.

All major systems must now justify themselves by improving this loop.

If a subsystem does not materially improve this loop in Stage 2, it is not core.

---

## 5. The North-Star Scenario

The practical north-star remains:

### Thermodynamics in 14 Days

A student:

- has a real final exam in 14 days
- uploads slides, textbook excerpts, homework, notes, and prior errors
- does not fully understand what is wrong with their study approach
- becomes overloaded mid-journey
- needs Sparkle to diagnose, plan, ground, adapt, recover momentum, and preserve trust

Stage 2 is successful only if Sparkle can handle this journey:

- on the real product path
- in a way a human evaluator can recognize as good
- with visible adaptation
- with continuity
- with better planning than raw frontier model usage for a comparable non-expert user

## 6. Stage 2 Workstreams

Stage 2 has five workstreams.

These should be executed in order.

### 6.1 Workstream 1: Runnable Golden Path

Goal:

> Build one repeatable full-stack startup and emulator path that lets us inspect the real product.

Why this comes first:

- we cannot judge product truth from internal code state alone
- we cannot judge visible adaptation without the actual app
- we cannot trust architectural confidence if the real stack is not runnable

Deliverables:

- one written bring-up checklist for backend, gateway, mobile, and emulator/simulator
- one verified startup path for local development
- one golden-path smoke test for login/session/chat/home flow
- one known-issues list for startup/runtime blockers

Definition of done:

- backend can start
- gateway can connect
- mobile app can run
- emulator/simulator can open the real product
- founder or implementation Codex can complete one start-to-chat path without guessing missing steps

Non-goals:

- full release automation
- every platform working equally well
- perfect CI before local truth

### 6.2 Workstream 2: Full-Stack North-Star Coherence

Goal:

> Prove the real core product loop works on the full stack, not only inside backend harnesses.

Deliverables:

- one full-stack scripted walkthrough of the 14-day exam journey
- one cold-start plan flow
- one overload and recovery flow
- one continuity follow-up flow
- one real check of adaptation surfaces on chat and home

Definition of done:

- Sparkle asks when readiness is low
- Sparkle plans when readiness is sufficient
- Sparkle uses grounding when user materials matter
- Sparkle visibly changes something real after feedback
- Sparkle carries the thread across turns and at least one later session

Non-goals:

- complete domain coverage
- support for every residual class before the main loop is strong

### 6.3 Workstream 3: Visible Adaptation and Product Legibility

Goal:

> Make Sparkle’s intelligence obvious, calm, and trustworthy in the user experience.

This is not about theatrical language.

It is about making the user able to feel:

- what Sparkle noticed
- what Sparkle changed
- why it changed it
- that the change is reversible if it does not help

Deliverables:

- stable chat adaptation language
- stable home narrative cards for:
  - what changed
  - what matters now
  - next move
- grounded explanation patterns
- continuity language patterns

Definition of done:

- a human evaluator can point to a concrete adaptation Sparkle made
- the user does not have to infer adaptation only from metadata or behavior drift
- adaptation language feels supportive and truthful, not manipulative or overdramatic

### 6.4 Workstream 4: Human Truth Loop

Goal:

> Make human evaluation the real judge of whether Sparkle is helping.

Deliverables:

- at least one real run of the north-star human evaluation protocol
- transcript review with issue tagging
- explicit product findings from real runs
- roadmap updates linked to those findings

Definition of done:

- human evaluation is not just documented, but actually executed
- transcript findings create implementation priorities
- repeated failure modes are visible and named

Non-goals:

- perfect statistical rigor
- waiting for a large-scale study before acting

### 6.5 Workstream 5: Product Simplification and Prioritization

Goal:

> Reduce system sprawl and force Sparkle to feel like one product organism.

This workstream exists because we now have many systems:

- OpenClaw
- Mirofish
- cards
- Knowledge Galaxy
- achievements
- community
- visual systems
- body-awareness
- five-layer learning
- multiple planning and orchestration layers

The danger now is not missing architecture.

The danger is too many organs competing for attention before the main loop is clearly alive.

Deliverables:

- one explicit list of core-now systems
- one explicit list of supporting-now systems
- one explicit list of postponed-now systems
- one product-surface simplification pass driven by the north-star loop

Definition of done:

- there is a clear answer to “what is the product right now?”
- the first-run experience is not diluted by secondary systems
- major decisions are filtered by the two moats:
  - understanding quality
  - plan quality

## 7. Stage 2 Execution Order

The execution order must be:

1. `S2-0 Runnable Golden Path Bring-Up`
2. `S2-1 Full-Stack North-Star Smoke`
3. `S2-2 Visible Adaptation UX Reality Pass`
4. `S2-3 First Human Evaluation Cycle`
5. `S2-4 Product Simplification Decisions`
6. `S2-5 Live Alpha Gate Review`

This order matters.

We should not:

- spend more weeks polishing architecture before the product runs
- broaden subsystem scope before the north-star flow is alive
- claim product superiority from internal harnesses alone

---

## 8. What Must Be Proven in Stage 2

Stage 2 must prove five things.

### 8.1 Product Coherence

The system behaves like one product, not many disconnected modules.

### 8.2 User Understanding

Sparkle asks for missing high-value information and surfaces truths the user recognizes as real.

### 8.3 Planning Superiority

Sparkle gives a better plan and better adaptation path than a non-expert user would typically get from raw frontier-model prompting.

### 8.4 Feedback-Driven Improvement

Sparkle changes future behavior based on real evidence, not just turn-local sentiment.

### 8.5 Trustworthy Experience

Sparkle remains helpful, legible, grounded, and non-manipulative.

---

## 9. What Counts as Truth in Stage 2

We now need a stricter hierarchy of truth sources.

### 9.1 Highest Truth

- real app runs
- real transcripts
- real evaluator judgments
- visible user-facing behavior

### 9.2 Secondary Truth

- orchestrator-backed acceptance tests
- full-stack smoke runs
- benchmark reports
- evaluator harnesses

### 9.3 Useful but Insufficient

- internal architecture quality
- code elegance
- synthetic scorecards
- isolated component correctness

This means:

> **A subsystem is not “done” just because it is implemented. It is only done when it improves the real product loop.**

---

## 10. What To Postpone

Stage 2 should explicitly postpone:

- broad domain expansion
- new major architecture layers
- richer system autonomy beyond current guarded rights
- large decorative dashboard complexity
- community and achievement expansion unless they directly improve the north-star loop
- deeper ambient systems that do not improve understanding or planning right now

This is not abandonment.

It is sequencing discipline.

## 11. The Live Alpha Question

Stage 2 ends with one honest question:

> **Can we truthfully say Sparkle is now a living AI-native growth product for at least one real user journey?**

That sentence is true only if:

- the app runs
- the core loop is coherent
- adaptation is visible
- human evaluation is real
- the product helps enough to be felt

If not, we are still in Stage 2.
