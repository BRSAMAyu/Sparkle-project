`ExperienceEnvelope` 模型 9 个字段中，7 个后端每轮对话都写入、但前端从未渲染：

| 字段 | 类型 | 后端写入 | 前端渲染 |
|------|------|---------|---------|
| `traceId` | String? | 每轮 | **未渲染** |
| `turnId` | String? | 每轮 | **未渲染** |
| `userState` | Map | 每轮 | **未渲染** |
| `profileContext` | Map | 每轮 | **未渲染** |
| `raw` | Map | 每轮 | **未渲染** |
| `structuredCognitiveAdjustments` | List\<Map\> | 每轮 | 仅渲染在 DEAD CODE widget 中 |
| `updatedAt` | DateTime? | 每轮 | **未渲染** |
| `isEmpty` | bool | — | **未渲染** |
| `hasAdjustments` | bool | — | 仅渲染在 DEAD CODE widget 中 |

`chat_provider.dart:1309/1505` 每轮对话都调用 `updateFromMetadata()` 把完整 envelope 数据写入 provider。但这些数据**从未到达用户眼睛**——因为唯一消费它的 `ExperienceEnvelopeIndicator` 没有被集成。

## 7. 根本原因分析

本轮审查揭示了 Sparkle 前端当前的核心问题不是"代码写得不好"——大部分 widget 代码质量不错。问题在于**集成链断裂**：

```
后端计算 → Provider 写入 → Widget 读取 → 屏幕渲染
   ✅           ✅             ❌           ❌
```

两个最关键的 widget（ExperienceEnvelopeIndicator、CommunityStrategyCard）都是**代码已写好但从未被 import**。它们本应承载的后端数据（7 个 envelope 字段、社区策略推荐）就这样沉默了。

这不是能力问题，是**交付流程问题**——"写 widget"和"接入 widget"被当作两个步骤，而第二步被遗漏了。
