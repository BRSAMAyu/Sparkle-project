# QA Round 7: UI 设计深度审计 — 设计系统、视觉层次、组件润色、动效

> **Date**: 2026-05-06 | **Status**: COMPLETE
> **Methodology**: 4 路 Explore Agent 并行 UI 审计 + 亲自 grep 验证关键发现
> **Focus**: 从设计系统一致性、视觉层次、组件润色、动效质量四个维度诊断 UI 问题

---

## Executive Summary

**Round 6 关注的是"用户体验的衔接断裂"，Round 7 关注的是"视觉实现的设计一致性"。**

核心发现：Sparkle 有一个**设计精良的设计系统**（DS tokens, AnimationSystem, TypographySystem, SpacingSystem），但功能代码中**大量绕过它**。这不是"设计系统不好"，是"设计系统没有被充分遵守"。

四个关键断裂点：

1. **设计系统双层身份** — `DS.fontSizeSm` = 14.0 但 `TypographySystem.sizeSm` = 16.0。同一个"Sm"在不同系统中含义不同，全局排版调整不可能。
2. **7 个路由绕过 reduceMotion** — `buildSparkleTransitionPage` 有 reduceMotion 治理，但 7 个 feature 路由直接调用 `buildSharedAxisCompatibleTransition` 跳过了它。
3. **4 个视觉复杂度最高的 widget 零无障碍** — DivineMomentCard、GrowthCard、AchievementMilestoneBadge、RarityBadge — 屏幕阅读器用户完全看不到它们。
4. **32 次 180ms / 30 次 300ms** — 全代码库最常用的两个动画持续时间没有一个是系统令牌。

| 维度 | Round 6 | Round 7 | 变化 |
|------|---------|---------|------|
| 设计系统一致性 | — | **50/100** | DS 存在但遵守率低 |
| 视觉层次 & 布局 | — | **70/100** | 优秀屏幕（Chat/Galaxy）与薄弱屏幕并存 |
| 组件润色 | — | **55/100** | 状态处理不完整，无障碍大面积缺失 |
| 动效 & 运动 | — | **68/100** | reduceMotion 治理 A 级但持续时间碎片化 |
| **总体 UI 健康度** | **70 (UX)** | **61** | — |

> 分数差异来自不同的标尺——UX 关注"功能衔接"，UI 关注"视觉一致性"。这是两个不同维度。

## 1. 设计系统一致性 ★★★★★

### 1.1 双层排版系统冲突

**问题出在哪**:

`DS` 类和 `TypographySystem` 类定义了两套不同的排版尺寸，但标签重叠：

```
DS.fontSizeXs  = 12.0    TypographySystem.sizeXs  = 12.8
DS.fontSizeSm  = 14.0    TypographySystem.sizeSm  = 16.0  ← 冲突!
DS.fontSizeBase = 16.0   TypographySystem.sizeSm  = 16.0
DS.fontSizeLg  = 20.0    TypographySystem.sizeMd  = 20.0
DS.fontSizeXl  = 25.0    TypographySystem.sizeLg  = 25.0
```

`DS.fontSizeSm` (14.0) 和 `TypographySystem.sizeSm` (16.0) 代表不同的字号，但名字一样。开发者在一个地方用 `DS.fontSizeSm`，另一个地方用 `TypographySystem.bodyMedium()`（内部用 `sizeSm` = 16.0），得到的结果差 2px。

**怎么改**:

选项 A（推荐 — 最小改动）: 废弃 `DS.fontSizeSm`，统一到 TypographySystem。在 DS 中标记 `@Deprecated('Use TypographySystem.bodyMedium()')`:

```dart
// design_system.dart
@Deprecated('Use TypographySystem.bodyMedium() instead')
static const double fontSizeSm = TypographySystem.sizeSm; // 14.0 → 16.0
```

选项 B: 合并两个系统。DS 不再定义独立的字体大小，改为引用 TypographySystem：

```dart
static double get fontSizeXs => TypographySystem.sizeXs;
static double get fontSizeSm => TypographySystem.bodyMedium().fontSize!;
static double get fontSizeBase => TypographySystem.sizeSm;
```

文件: `design_system.dart:965-967` + `typography_token.dart:13-14`

### 1.2 goal_detail_page.dart — DS 绕过最严重的屏幕

**问题出在哪**:

`goal_detail_page.dart` 只有 **11 个 DS.token 引用**。对比 `streak_details_screen.dart`（90 个引用），这是 8:1 的差距。

具体违规：

```dart
// goal_detail_page.dart
line 31:   final colorScheme = Theme.of(context).colorScheme;  // 绕过 DS
line 169:  padding: const EdgeInsets.all(18),                   // 硬编码, 应该 DS.spacing18
line 171:  color: colorScheme.surfaceContainerHighest,          // 应该 DS.surfaceHigh
line 172:  borderRadius: BorderRadius.circular(8),              // 硬编码, 应该 DS.borderRadius8 或 12
line 173:  border: Border.all(color: colorScheme.outlineVariant), // 应该 DS.borderSubtle
line 273:  color: colorScheme.primaryContainer,                 // 应该 DS.surfaceSecondary
line 274:  borderRadius: BorderRadius.circular(8),              // 硬编码(第二次)
line 522:  contentPadding: EdgeInsets.zero,                     // 应该 DS.zero 或避免
```

整个屏幕绕过了 DS 的颜色语义层。`colorScheme.surfaceContainerHighest` 和 `DS.surfaceHigh` 在 light theme 下可能碰巧相同，但 dark theme 下就不一定了。

**怎么改**:

替换所有 `colorScheme.*` 为对应的 `DS.*`：

```dart
// Before
final colorScheme = Theme.of(context).colorScheme;
color: colorScheme.surfaceContainerHighest,
borderRadius: BorderRadius.circular(8),
border: Border.all(color: colorScheme.outlineVariant),

// After
color: DS.surfaceHigh,
borderRadius: DS.borderRadius12,  // 或 DS.borderRadius8 — 但 12 才是项目标准
border: DS.borderSubtle,
```

`EdgeInsets.all(18)` → `EdgeInsets.all(DS.spacing18)`（如果 DS.spacing18 不在 8pt 网格上，考虑改用 DS.spacing16 或 DS.spacing20）。

文件: `goal_detail_page.dart`，约 20 处替换。工期: 30 min。

### 1.3 间距系统绕过：~1702 处原始 EdgeInsets

**问题出在哪**:

全代码库 features/ 中有约 1,700 处直接使用 `EdgeInsets.all(16)` / `EdgeInsets.symmetric(horizontal: 12, vertical: 8)` 而不是 `DS.spacing16` / `DS.spacing12` / `DS.spacing8`。

最严重的违规：

```
sprint_review_screen.dart:56:  EdgeInsets.fromLTRB(20, 8, 20, 40)  — 原始 20 和 40
learning_path_dialog.dart:770: EdgeInsets.only(top: 7, right: 8)   — 7px 不在任何网格上
exam_sprint_dashboard_card.dart:861: EdgeInsets.only(top: 1)       — 1px 微调
dashboard_screen.dart:1191:      EdgeInsets.all(14)                — 原始值
goal_detail_page.dart:169:       EdgeInsets.all(18)                — 原始值
goal_detail_page.dart:108:       spacing 22                        — 非 DS token
```

**怎么改**:

不建议批量替换（风险高）。而是在 **P0 屏幕**（goal_detail_page, sprint_review_screen）上逐一替换原始 EdgeInsets 为 DS token。对于非标准值（7, 22），选择最近的 DS token（8, 20 或 24）。

### 1.4 8pt 网格被 DS 自身破坏

**问题出在哪**:

`SpacingSystem` 声明了 8pt 网格（xs=4, sm=8, md=12, lg=16, xl=24, xxl=32, xxxl=48, huge=64）。但 `DS` 类添加了非网格值：

```dart
DS.spacing6  =  6  // 不在 4pt 或 8pt 网格上
DS.spacing10 = 10  // 不在网格上
DS.spacing14 = 14  // 不在网格上
DS.spacing18 = 18  // 不在网格上
```

这些值在实践中被使用（如 goal_detail_page 的 `EdgeInsets.all(18)`），但破坏了 8pt 网格的承诺。

**怎么改**:

不需要删除这些值（它们已被使用），但应该：
1. 在设计系统中标记为 `@Deprecated`，引导开发者改用最近的 8pt 倍数
2. 在 code review checklist 中加一条："新代码不使用 spacing6/10/14/18"

### 1.5 硬编码 Color(0x...) — ~30+ 处绕过 DS 调色板

**问题出在哪**:

虽然 rarity_badge.dart 现在使用 DS 令牌（`DS.rarityRare`, `DS.rarityRareBg` 等），但代码库中仍有 ~30 处直接使用 `Color(0xFF...)`：

```
exam_sprint_dashboard_card.dart:258:  Color(0xFF1A237E), Color(0xFF283593) — 硬编码蓝色
achievement_contract_screen.dart:861: Color(0xFFFFB300), Color(0xFFFFC107) — 硬编码金色
achievement_share_bottom_sheet.dart:504: Color(0xFF07C160) — 硬编码微信绿
memory_settings_screen.dart:422: Color(0xFF71917D) — 孤立绿色
```

这些颜色不会在暗色模式下自动调整，全局品牌色变更也不会传播到它们。

**怎么改**:

每个硬编码颜色要么：
- 已经在 DS 中有等效值 → 替换为 DS token
- 是功能特定的语义颜色 → 添加到 DS 中（如 `DS.shareWechatGreen`）

工期: 扫描 + 逐个替换，约 2h。

## 2. 无障碍：页面转导 reduceMotion 漏洞 ★★★★★

### 2.1 7 个路由绕过 reduceMotion

**问题出在哪**:

`buildSparkleTransitionPage()`（sparkle_route_transition.dart:53-88）有完整的 reduceMotion 治理：
- 当 `disableAnimations` 为 true 时，缩短转导持续时间
- 当 reduceMotion 为 true 时，降到 140ms 淡入转导

但 **7 个 feature 路由文件** 直接调用 `buildSharedAxisCompatibleTransition()`，跳过了这一切：

| 路由文件 | 缺少的治理 |
|---------|-----------|
| `cognitive_routes.dart:16` | 零 reduceMotion 检查 |
| `splash_routes.dart:18` | 零 reduceMotion 检查 + 硬编码 400ms/220ms |
| `auth_routes.dart:16` | 零 reduceMotion 检查 |
| `translation_routes.dart:16` | 零 reduceMotion 检查 |
| `notification_center_routes.dart:16` | 零 reduceMotion 检查 |
| `error_book_routes.dart:20` | 零 reduceMotion 检查 |
| `photon_routes.dart:17` | 零 reduceMotion 检查 |

**对比**: 使用 `buildSparkleTransitionPage` 的路由 — home, insights, theater, tools, achievement, memory, chat, calendar, openclaw, seed_library — 全部安全。

**怎么改**:

每个文件只需改一行。以 cognitive_routes.dart 为例：

```dart
// Before (cognitive_routes.dart:16)
Page<dynamic> _buildTransitionPage({...}) =>
    CustomTransitionPage<void>(
      ...
      transitionsBuilder: (context, animation, secondaryAnimation, child) =>
          buildSharedAxisCompatibleTransition(
        animation: animation,
        type: type,
        child: child,
      ),
    );

// After — 直接用 buildSparkleTransitionPage
// 不需要自定义 _buildTransitionPage，直接用公共 API:
pageBuilder: (context, state) => buildSparkleTransitionPage(
  state: state,
  child: PatternListScreen(highlightId: highlightId),
  type: SharedAxisTransitionType.horizontal,
),
```

每个文件改动 ~10 行。工期: 7 个文件 × 15 min = ~2h。

### 2.2 4 个高视觉复杂度 widget 零 Semantics

**问题出在哪**:

| Widget | 文件 | Semantics 计数 |
|--------|------|---------------|
| DivineMomentCard | divine_moment_card.dart | **0** |
| GrowthCard | growth_card.dart | **0** |
| AchievementMilestoneBadge | achievement_milestone_badge.dart | **0** |
| RarityBadge | rarity_badge.dart | **0** |

这些 widget 都不是简单的文本行 — 它们有图标、动画、多层视觉代码。屏幕阅读器用户对这些 widget 的体验是完全空白。

对比：同级别的 SparkleButton、StreakQualityIndicator、AuroraReceiptChip 都有完整的 Semantics 标签。

**怎么改**:

以 DivineMomentCard 为例：

```dart
// 在 build() 最外层包裹
return Semantics(
  button: onTap != null,
  label: switch (type) {
    DivineMomentType.block => _t('已阻止低收益行为', 'Blocked a low-yield action'),

    DivineMomentType.insight => _t('洞察发现', 'Insight discovered'),
    DivineMomentType.celebration => _t('成就庆祝', 'Achievement celebration'),
  },
  child: AnimatedSlide(...),
);
```

工期: 4 个 widget × 15 min = 1h。

## 3. 组件润色 ★★★★

### 3.1 视觉状态处理不完整

**问题出在哪**:

| 组件 | 缺失的状态 |
|------|-----------|
| CommunityStrategyCard | 无 pressed/disabled/loading/error |
| DivineMomentCard | StatelessWidget — 无任何交互状态 |
| GrowthCard | 无 error/loading/disabled |
| SparkleIconButton | 无 `loading` 属性（SparkleButton 有） |
| SparkleCard | 无 pressed/selected 状态 |

这些不是理论问题——当网络请求失败时，GrowthCard 不会显示错误；当操作进行中时，CommunityStrategyCard 看不出正在处理。

**怎么改**:

1. **SparkleIconButton** — 添加 `loading` 属性（复制 SparkleButton 的模式）:
```dart
// sparkle_button_v2.dart, 在 SparkleIconButton 中添加:
final bool loading;
// 在 build 中:
if (loading) return _LoadingIconButton(size: size, ...);
```

2. **GrowthCard** — 添加 error state:
```dart
final asyncState = ref.watch(growthCardProvider);
asyncState.when(
  data: (growth) => _buildGrowthContent(growth),
  loading: () => const SparkleCardSkeleton(),
  error: (e, _) => CompactErrorCard(message: e.toString()),
);
```

3. **DivineMomentCard** — 转换为 ConsumerStatefulWidget，添加 loading/error wrapper。

工期: 3h。

### 3.2 动画持续时间碎片化

**问题出在哪**:

```bash
$ grep "Duration(milliseconds:" features/ | sort | uniq -c | sort -rn
32  180ms    ← 最常用但不是系统令牌!
30  300ms    ← 第二常用，也不是系统令牌
28  220ms    ← = AnimationSystem.standard ✓
23  200ms    ← 接近 standard 但不是
19  500ms    ← 不是系统令牌
17  100ms    ← AnimationSystem 中没有
15  150ms    ← = AnimationSystem.quick ✓
```

**180ms（32 次）**和 **300ms（30 次）**在全代码库中使用最广泛，但 `AnimationSystem` 中没有定义它们。这意味着无法全局调整所有微交互的持续时间。

**怎么改**:

1. 在 `SparkleMotionToken` 枚举中添加一个新令牌：

```dart
// animation_token.dart
enum SparkleMotionToken {
  instant,     // 0ms (new)
  micro,       // 120ms
  quick,       // 150ms
  responsive,  // 180ms (NEW — 最常用值)
  standard,    // 220ms
  normal,      // 250ms
  deliberate,  // 300ms (NEW — 第二常用值)
  scene,       // 400ms
  slow,        // 400ms
  hero,        // 620ms
}
```

2. 然后逐步将 `Duration(milliseconds: 180)` 替换为 `DS.motionDuration(SparkleMotionToken.responsive, reduceMotion: context.reduceMotion)`。

不需要一次性替换所有。在修改相关文件时逐步迁移。工期: 添加到 DS（10 min）+ 渐进迁移（ongoing）。

### 3.3 PlanReviewCard 呼吸动画 2200ms — 超过 DS 最大值的 3.5 倍

**问题出在哪**:

`plan_review_card.dart:195`:
```dart
duration: const Duration(milliseconds: 2200),
```

DS 的动画持续时间范围是 120ms (micro) 到 620ms (hero)。2200ms 是 hero 的 3.5 倍。这个"呼吸高亮"动画以一个对 UI 反馈来说太慢的周期运行——用户已经读到卡片底部了，高亮还在上半部分呼吸。

**怎么改**:

```dart
// Before
duration: const Duration(milliseconds: 2200),

// After — 使用最长的 DS token 并让它感觉像"呼吸"
duration: DS.motionDuration(SparkleMotionToken.hero), // 620ms
```

如果设计意图是缓慢呼吸，最多用 1200ms（shimmer 周期已有这个值）并添加独立常量：

```dart
static const _breathDuration = Duration(milliseconds: 1200);
```

文件: `plan_review_card.dart:195, 198-200`。工期: 5 min。

### 3.4 曲线使用碎片化

**问题出在哪**:

存在至少 5 种使用 `easeOut` 变体的方式：

```dart
DS.motionCurve(SparkleMotionToken.micro)  → Curves.easeOut
DS.curveEaseOut                            → Curves.easeOut
Curves.easeOut                              → 直接硬编码
Curves.easeOutCubic                         → 成就系统中大量使用
Curves.easeOutQuart                         → 页面转导中使用
```

成就系统完全独立于 DS——`achievement_card.dart:77`、`streak_details_screen.dart:447` 全部硬编码 `Curves.easeOutCubic` 而不是使用 `DS.motionCurve(...)`。

**怎么改**:

1. 在成就系统中，将 `Curves.easeOutCubic` → `DS.motionCurve(SparkleMotionToken.standard)`。
2. 标记 `DS.curveEaseOut` 为 deprecated（与 `DS.motionCurve(micro)` 重复）。

工期: 成就系统替换 30 min。

### 3.5 BorderRadius 不一致

**问题出在哪**:

项目在同一个 UI 层使用了不同的 border radius 值：

```
DivineMomentCard:  BorderRadius.circular(14)  — 不是 DS token
DivineMomentCard:  BorderRadius.circular(6)   — 应该 DS.borderRadius6
DivineMomentCard:  BorderRadius.circular(8)   — 应该 DS.borderRadius8
GrowthCard:        BorderRadius.circular(14)  — 不是 DS token
GrowthCard:        BorderRadius.circular(8)   — 应该 DS.borderRadius8
goal_detail_page:  BorderRadius.circular(8)   — 3 处，应该 DS.borderRadius12
sprint_review:     主卡片 DS.borderRadius20 ✓, 子卡片 DS.borderRadius12 ✓

```

`BorderRadius.circular(14)` 出现了多次，但 DS 中没有 14 的 token。

**怎么改**:

`14` → `DS.borderRadius16`（最接近的 token，视觉差异小）。DivineMomentCard 和 GrowthCard 中约 6 处替换。工期: 15 min。

## 4. 视觉层次 & 布局 ★★★

### 4.1 屏幕之间 DS 遵守率差异悬殊

**问题出在哪**:

| 屏幕 | DS.token 引用 | 评价 |
|------|-------------|------|
| streak_details_screen | **90** | 近乎全 DS |
| dashboard_screen | **~45** | 混合但可接受 |
| chat_screen | **~40** | 混合，但有自己的氛围设计 |
| sprint_review_screen | **~20** | 混合，原始 EdgeInsets |
| **goal_detail_page** | **11** | 几乎完全绕过 DS |

这不是"有些屏幕没用 DS"的问题——是**一个屏幕几乎完全没有用 DS**，而另一个屏幕完全遵守。用户在屏幕之间切换时会感受到视觉语言的不一致。

**怎么改**:

优先修复 goal_detail_page.dart（见 1.2）。然后修复 sprint_review_screen.dart 的原始间距值。

### 4.2 sprint_review_screen 缺乏任何响应式机制

**问题出在哪**:

`sprint_review_screen.dart` 是 6 个关键屏幕中**唯一一个**完全没有使用 `MediaQuery`、`LayoutBuilder`、`ContentConstraint` 或 `ResponsiveSystem` 的屏幕。

在平板上，3 列的 `_StatsRow` 会被拉伸到无法阅读的宽度。在非常小的屏幕上，卡片会过于拥挤。

对比 dashboard_screen 使用了全部 4 种响应式机制。

**怎么改**:

在 `_StatsRow` 外包裹 `LayoutBuilder`，当 `maxWidth < 360` 时堆叠为单列：

```dart
LayoutBuilder(
  builder: (context, constraints) {
    if (constraints.maxWidth < 360) {
      return Column(children: statTiles);
    }
    return Row(children: statTiles.map((t) => Expanded(child: t)).toList());
  },
)
```

文件: `sprint_review_screen.dart:238-247`。工期: 30 min。

### 4.3 图标与文本间距不一致

**问题出在哪**:

`goal_detail_page.dart` 的同一个屏幕内有 **3 个不同的图标-文本间距**：

```
line 199: SizedBox(width: 16)  — GoalHeader
line 285: SizedBox(width: 10)  — TodayStepCard
line 569: SizedBox(width: 10)  — SectionCard
```

`dashboard_screen.dart` 也有这个不一致：

```
line 836: SizedBox(width: DS.spacing8)   — SectionHeader
line 912: SizedBox(width: DS.spacing10)  — EmptyCta
```

这不是功能问题，但破坏了视觉节奏的规律性。

**怎么改**:

统一到一个标准间距（推荐 `DS.spacing8`）:

```dart
// goal_detail_page.dart 各处
SizedBox(width: DS.spacing8)  // 之前是 10 或 16
```

工期: 10 min。

### 4.4 Galaxy/Chat 屏幕 — 视觉设计亮点

**不做什么**:

Galaxy 和 Chat 是当前 UI 质量**最高**的两个屏幕：
- Chat 的双层渐变背景 + 毛玻璃 AppBar + 径向发光叠加 — 设计感一流
- Galaxy 的自适应质量系统（consecutiveSlowFrames 检测 + 自动降级）+ 力引导布局 + 视差星空 — 工程与设计并重

**不修改它们**。这是 UI 质量的基准线，其他屏幕应该向它们看齐。

## 5. 动效质量 ★★★

### 5.1 reduceMotion 治理：A 级（有漏洞）

**做得好的**:

- `DS.motionDuration(token, reduceMotion: true)` → Duration.zero
- `SparkleStaggerItem` — 在 `initState` 和 `build` 中双重检查
- `RarityVisualWrapper` — 停止全部 4 个 controller（shimmer/glow/particle/border）
- `GlobalParticleCounter` — reduceMotion 时返回 `maxParticles = 0`
- `SparkleConfetti` — 三层检查
- 情感模式的 `NoTransitionsBuilder` — 完全禁用页面转导

**漏洞**:

- 7 个路由绕过 reduceMotion（见 2.1）
- `SparkleAttentionPulse` 仅在 `didChangeDependencies` 中捕获 — 无障碍设置在屏幕存续期间变化时不会响应

**怎么改**:

路由修复见 2.1。对于 `SparkleAttentionPulse`：

```dart
// sparkle_motion_primitives.dart:313
@override
void didChangeDependencies() {
  super.didChangeDependencies();
  final newReduceMotion = context.reduceMotion;
  if (_reduceMotion != newReduceMotion) {
    setState(() => _reduceMotion = newReduceMotion);
  }
}
```

工期: 2h（路由修复主导）。

### 5.2 页面转导持续时间与 DS 动效持续时间分歧

**问题出在哪**:

页面转导在 `sparkle_route_transition.dart:57-62` 中定义了自己的持续时间映射：

```
Token    → 转导:    DS.motionDuration():
micro     → 150ms    120ms
standard  → 180ms    220ms
scene     → 210ms    400ms
hero      → 240ms    620ms
```

这是**有意的** —— 页面转导需要比组件内部动效更短的持续时间（用户不想等 400ms 才能进入一个页面）。但这个映射没有文档记录，意味着存在两个并行的持续时间系统。

**怎么改**:

不修改持续时间（它们是正确的）。在 `sparkle_route_transition.dart` 顶部添加注释：

```dart
/// 页面转导持续时间有意短于 [AnimationSystem] 中对应的动效令牌。
/// 页面转导需要在响应性（快速）和流畅性（平滑）之间取得平衡，
/// 偏向响应性。组件内部动效则偏向流畅性。
///
/// 映射:
///   micro    → 150ms (组件: 120ms)
///   standard → 180ms (组件: 220ms)
///   scene    → 210ms (组件: 400ms)
///   hero     → 240ms (组件: 620ms)
```

工期: 5 min。

### 5.3 `_ShimmerWrapper` 被限制在单个文件中

**问题出在哪**:

`skeleton` 微光效果（`loading_indicator.dart:268-285`）的 `_ShimmerWrapper` 是文件私有的。任何其他文件想要添加微光效果到加载状态都需要重新实现。

骨架组件（`SparkleSkeleton`）是 DS 级别的，但微光是文件本地的。

**怎么改**:

提取到 `mobile/lib/core/design/widgets/sparkle_shimmer.dart`：

```dart
class SparkleShimmer extends StatelessWidget {
  const SparkleShimmer({required this.child, ...});
  // 迁移自 loading_indicator.dart 的 _ShimmerWrapper
}
```

工期: 30 min。

## 9. 总体评估

**Sparkle 的 UI 状态**:

- **设计系统**: 80/100 — DS 本身设计得很好（token 系统、语义层、暗色模式），但遵守率低
- **无障碍**: 55/100 — reduceMotion 治理出色，但 4 个核心 widget 零 Semantics，7 个路由有漏洞
- **动效系统**: 75/100 — 原语优秀（交错、粒子、庆祝），但持续时间碎片化
- **组件质量**: 60/100 — 部分组件达到生产级（SparkleButton, StreakQualityIndicator），部分仍处于原型阶段（CommunityStrategyCard）

**最关键的问题**: 设计系统存在但代码不遵守。这不是需要重新设计 DS——是需要强制执行已有的 DS。Goal Detail 屏幕（用户最常看的目标详情）是目前 UI 质量最低的屏幕之一，这直接伤害了产品感知。

**与 Round 6 (UX) 的关系**: Round 6 的修复（Dashboard 信息层级、目标创建庆祝、成就解锁对话框）正在改善用户体验的衔接。本轮发现的问题——如果 Goal Detail 的 UI 质量不提升——用户即使被很好地引导到 Goal Detail 屏幕，面对的也是一个视觉不一致的界面。**UX 把用户带到门口，UI 负责开门后的体验。**
