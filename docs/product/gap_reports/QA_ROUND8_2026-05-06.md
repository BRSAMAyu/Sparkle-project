## 1. CRITICAL: 后端 Bug — 直接影响用户

### BUG-1 (CRITICAL): asyncio.CancelledError 未捕获导致请求崩溃

**问题出在哪**:

`execution_engine.py:1844-1847` — `_execute_graph` 方法调用 `graph_task.exception()` 但不处理 `asyncio.CancelledError`。

Python 3.11 中 `CancelledError` 是 `BaseException` 的子类（不是 `Exception`），所以它**完全绕过** `except Exception as e:` 处理块。当 LangGraph 任务因任何原因被取消（关闭、资源压力、超时），`CancelledError` 未经捕获地传播到整个请求链，导致请求崩溃而不是返回适当的错误响应。

对比：`summarization_worker.py:73` 和 `state_manager.py:426,467` **正确**处理了 `CancelledError`——唯独 `execution_engine.py` 没有。

**用户感受到的**: 聊天突然中断，连接关闭，没有错误解释。相当于"话说到一半被打断"。

**怎么改**:

```python
# execution_engine.py:1844
try:
    graph_exception = graph_task.exception()
except asyncio.CancelledError:
    logger.warning("Graph task cancelled", exc_info=True)
    yield ChatResponse(error=ChatError(
        code=ERROR_CODE_UNAVAILABLE,
        message="Request was cancelled. Please try again.",
    ))
    return
```

文件: `execution_engine.py:1844-1847`。工期: 15 min。

### BUG-2 (CRITICAL): `continue_with_tool_results` 无超时，可永久挂起

**问题出在哪**:

`execution_engine.py:1372-1376` — 调用 `llm_service.continue_with_tool_results()` **没有 `asyncio.wait_for` 超时包装**。

对比：代码库中所有其他 LLM 交互（LangGraph planner 在 2054-2071 行有 10s 超时、GraphRAG 调用等）都包装了超时。`llm_service.py:1120` 的该方法内部也没有超时。

同一个问题存在于 Chat API 层：
- `chat.py:290` — HTTP handler 中的 `continue_with_tool_results()` 无超时
- `chat.py:540` — 同上
- `chat.py:691` — 同上

**用户感受到的**: 工具执行后的聊天回复永久转圈。连接不关闭，服务器资源被消耗。在高负载下，积压的挂起连接会耗尽 worker/线程。

**怎么改**:

```python
# execution_engine.py:1372
try:
    async with asyncio.timeout(30):  # 或从 settings 读取
        result = await llm_service.continue_with_tool_results(
            conversation_history, tool_results
        )
except asyncio.TimeoutError:
    logger.error("Tool continuation timed out")
    yield ChatResponse(error=ChatError(
        code=ERROR_CODE_TIMEOUT,
        message="Tool processing timed out. Please try again.",
    ))
    return
```

文件: `execution_engine.py:1372` + `chat.py:290, 540, 691`。工期: 30 min。

## 2. HIGH: 后端问题 — 间接影响用户/运维

### BUG-3 (HIGH): 工具续接错误被报告为成功

**问题出在哪**:

`orchestrator.py:2958-2980` — 当 `_continue_after_tool_result` 捕获 LLM 错误时，它向用户 yield ERROR 响应并返回。但调用方无条件地设置 `STATE_DONE`、递增 `REQUEST_COUNT` 和 `COLLABORATION_SUCCESS`。错误路径对整个可观测性栈完全不可见。

**影响**: 工具使用失败被记录为成功——仪表板、警报、可靠性指标全部错误。下游消费者（会话摘要、自适应引擎）不知道出错了。

**怎么改**:

在调用方检查 yield 的最后一个消息是否为错误：

```python
# orchestrator.py:2975
last_msg = None
async for msg in self._continue_after_tool_result(...):
    last_msg = msg
    yield msg

if last_msg and last_msg.HasField("error"):
    state.set_state(STATE_FAILED)
    state.increment(METRIC_REQUEST_FAILURE)
else:
    state.set_state(STATE_DONE)
    state.increment(METRIC_REQUEST_COUNT)
    state.increment(METRIC_COLLABORATION_SUCCESS)
```

文件: `orchestrator.py:2958-2980`。工期: 20 min。

### BUG-4 (HIGH): `plan.created` 事件三消费者竞态

**问题出在哪**:

三个独立的消费者组（`plan_task_generation_consumer.py`, `achievement_plan_consumer.py`, `galaxy_plan_consumer.py`）都订阅同一个 `plan.created` 事件，各自独立打开 DB 会话，没有协调。

如果 plan.created 在 plan 的 task/generation 完全持久化之前发布，或在 DB 复制延迟期间，消费者可能读到过期数据、碰撞写锁、或完全错过 plan。

**用户感受到的**: 间歇性问题——创建计划后任务不生成、成就未触发、Galaxy 状态显示"no goals found"。不是每次必现，极其难调试。

**怎么改**:

使用 `event_bus.py` 中的现有延迟分发机制，在 plan.created 发布前添加短暂延迟（100ms），确保 DB 写入已提交：

```python
# 在发布 plan.created 的代码中
await asyncio.sleep(0.1)  # 等待 DB 提交传播
await event_bus.publish(PlanCreated(...))
```

更好的方案：在消费者中添加重试+退避，检查 plan 初始化状态：

```python
# plan_task_generation_consumer.py
for attempt in range(3):
    plan = await db.get_plan(plan_id)
    if plan and plan.tasks:
        break
    await asyncio.sleep(0.1 * (attempt + 1))
```

文件: 3 个 consumer 文件 + plan 发布点。工期: 1h。

### BUG-5 (HIGH): DLQ Admin API 只能访问一个流

**问题出在哪**:

`dlq_admin.py:16-95` — `list_dlq_events` 和 `replay_dlq_events` 仅操作 `CognitiveStreamWorker.DLQ_STREAM`。主 EventBus DLQ（`sparkle_events` 流的 `:dlq` 后缀，在 `event_bus.py:682,804` 处理）从 admin API 完全不可达。

### BUG-8 (MEDIUM): 幂等锁在成功消费后永不释放

**问题出在哪**:

`event_bus.py:1141-1151` — 幂等锁仅在异常路径（line 1150）释放。成功路径设置 `idempotency.set(idempotency_key, {"status": "done"}, ttl=86400)` 但不释放锁。锁持续到 TTL 过期。

**影响**: 如果消息在后续尝试中失败（锁仍被持有），可能无法获取锁，消息保持 pending。高吞吐下泄露的锁累积在 Redis 内存中。

**怎么改**:

在成功路径也释放锁：

```python
try:
    await idempotency.set(idempotency_key, {"status": "done"}, ttl=86400)
except Exception:
    pass
finally:
    await idempotency.unlock(idempotency_key)  # 加入这一行
```

文件: `event_bus.py:1141-1151`。工期: 5 min。

### BUG-9 (MEDIUM): 重试计数在某些解析错误时被重置

**问题出在哪**:

`event_bus.py:839-883` — `_requeue_for_retry` 的 `parsed_data` 是从流字段解析的。如果 `data` 包含非 dict 字段（扁平字符串），原始 `_retry_count` 可能丢失。`_extract_retry_count`（line 706）读到 0，消息永远重试但 `retry_count` 始终为 0，永远不会进入 DLQ。

**影响**: 一个特定解析错误会导致消息无限循环重试——永不升级到 DLQ。导致消费者资源浪费、队列反压、当 Redis stream `maxlen` 驱逐旧消息时可能丢消息。

**怎么改**:

在 requeue 时保留原始 retry_count：

```python
# event_bus.py:855
retry_count = _extract_retry_count(original_message)  # 从原始消息提取
parsed_data["_retry_count"] = retry_count + 1  # 而非从重新解析的数据提取
```

文件: `event_bus.py:839-883`。工期: 20 min。

### BUG-10 (MEDIUM): 消费者任务列表内存泄漏

**问题出在哪**:

`main.py:179-324` — 17 个消费者任务在启动时创建，但 `event_bus.py:1078` 的 `_consumer_tasks` 列表只增不减——任务完成后不会被移除。在长时间运行的进程中，任务引用累积。

另外，`main.py` 的关闭处理程序必须逐个取消 17 个任务。如果任何任务被遗漏，它会泄漏并持有 Redis 连接。重启时，Redis consumer group 中留下死亡成员。

**怎么改**:

1. 在 consumer 停止时从 `_consumer_tasks` 中移除
2. 使用 `asyncio.TaskGroup`（Python 3.11+）统一管理所有 consumer 任务

工期: 30 min。

## 4. N+1 查询风险

**问题出在哪**:

Python SQLAlchemy 模型中有 **36 个 `lazy="dynamic"` 关系**。`lazy="dynamic"` 返回 Query 对象而非预加载的数据——如果在循环中访问，每次迭代触发一次 SQL 查询。

分布:
- `user.py`: 12 个 dynamic 关系（目标、任务、成就、偏好等——用户是最常被查询的模型）
- `task.py`: 7 个 dynamic 关系（聊天消息、反馈、胶囊等）
- `plan.py`: 1 个 dynamic 关系（tasks）

**风险场景**: 仪表板加载用户 → 遍历目标 → 每个目标访问 tasks → 每个 task 访问 messages。如果每个用户有 5 个目标 × 3 个 task × 10 个 message = 150 次额外查询。

**怎么改**:

不是把所有 dynamic 改为 eager（会影响不需要这些关系的查询）。而是：
1. 在已知需要关联数据的热路径（仪表板加载、目标详情、任务详情）中使用 `joinedload()` 或 `selectinload()`
2. 用 SQLAlchemy 的 `nplusone` 库或开启 `sqlalchemy.lazy_load` 日志来检测实际 N+1 模式

文件: `user.py`, `task.py`, `plan.py` 模型定义 + 查询代码。工期: 2h（分析热路径 + 修改查询）。

## 5. DB Schema 问题

### BUG-11 (HIGH): 2 个未合并的 Alembic heads

**问题出在哪**:

`backend/alembic/versions/` 中有 2 个未合并的 migration heads：`c1b2c3d4e5f6` 和 `de30c736266b`。这意味着存在两条独立的 migration 链，通常由两个开发者并行创建 migration 而未 merge 导致。

当前 `alembic heads` 输出两个 head，`alembic upgrade head` 只会应用其中一条链。另一条链的 schema 变更永远不会被应用。

**影响**: 生产环境的 DB schema 可能缺少另一条链中的列/表/约束。Alembic 不会报错——它静默地只应用一条链。

**怎么改**:

```bash
alembic merge c1b2c3d4e5f6 de30c736266b -m "merge_heads_round8"
alembic upgrade head
```

文件: `backend/alembic/versions/`。工期: 15 min。

### BUG-12 (MEDIUM): 113 个 FK 约束没有 ON DELETE 行为

**问题出在哪**:

`backend/gateway/internal/db/schema.sql` 中有 113 个外键约束未指定 `ON DELETE`。例如 `REFERENCES users(id)` 没有 `ON DELETE CASCADE` 或 `ON DELETE SET NULL`。

当父行被删除时，数据库的默认行为（通常是 `RESTRICT` 或 `NO ACTION`）会阻止删除或造成孤儿行。具体行为取决于 DB 配置，导致不一致。

**影响**: 用户删除账户时可能部分失败（某些表拒绝级联）。孤儿行累积，影响数据完整性和查询正确性。

**怎么改**:

审计每个 FK 并明确加上 `ON DELETE`：
```sql
-- 如果删除用户时应保留数据
REFERENCES users(id) ON DELETE SET NULL
-- 如果删除用户时应清理数据
REFERENCES users(id) ON DELETE CASCADE
```

文件: `schema.sql`。工期: 1h（审计 + 决策每列的语义 + 修改）。

### BUG-13 (LOW): `achievementtype` ENUM 有重复值

**问题出在哪**:

`schema.sql` 的 `achievementtype` ENUM 包含 `'planning'` 和 `'PLANNING'` 两个值。大小写不同但语义相同。多数代码检查 `== 'planning'`，但 `'PLANNING'` 的行会被漏掉。

**影响**: 查询可能返回不完整结果（WHERE 条件只匹配一个大小写）。数据迁移/聚合会漏掉数据。

**怎么改**:

统一为一种形式后移除重复值（PostgreSQL 不支持直接删除 ENUM 值，需要 ALTER TYPE + USING + 重命名）:

```sql
-- 先将 PLANNING 行更新为 planning
UPDATE achievements SET type = 'planning' WHERE type = 'PLANNING';
-- （需要完整的 ALTER TYPE 流程来移除枚举值）
```

文件: `schema.sql`。工期: 15 min。

### BUG-14 (LOW): Redis quota Lua 脚本 key 无 TTL

**问题出在哪**:

`backend/gateway/internal/db/scripts/decr_quota.lua` — 递减配额计数器后不设置 TTL。quota key 永不过期，Redis 内存中累积过期的配额数据。

**影响**: 对大多数用户影响小——Redis 的 maxmemory-policy 会驱逐冷数据。但如果用户的 quota key 只在第一天被访问然后永不触碰，它仍然占用内存直到被 LRU 淘汰。

**怎么改**:

在 Lua 脚本末尾添加：
```lua
-- 仅在首次创建时设置 TTL
if new_val == initial_val - 1 then
    redis.call('EXPIRE', key, ttl_seconds)
end
```

文件: `decr_quota.lua`。工期: 5 min。

## 6. 基础设施与部署问题

### BUG-15 (CRITICAL): K8s CD 中 Docker build context 错误

**问题出在哪**:

`.github/workflows/cd_k8s.yml:42,53` — Gateway 和 Backend 的 Docker build 步骤都设置 `context: .`（仓库根目录），但 Dockerfile 位于 `backend/gateway/Dockerfile` 和 `backend/Dockerfile`。

Gateway 的 Dockerfile 执行 `COPY go.mod go.sum ./` 和 `COPY . .`，期望 build context 是 `backend/gateway/`（go.mod 所在目录）。使用 repo root 作为 context 时，`COPY go.mod go.sum ./` 找不到文件（go.mod 在 `backend/gateway/go.mod`，不在 repo root），**构建会直接失败**。

**影响**: K8s CD pipeline 完全无法构建镜像。这个 pipeline 自从 Dockerfile 路径变更后可能从未成功运行过。

**怎么改**:

```yaml
# cd_k8s.yml line 42-47 — Gateway
- name: Build and push Gateway
  uses: docker/build-push-action@v5
  with:
    context: backend/gateway    # 不是 .
    file: backend/gateway/Dockerfile
    ...

# cd_k8s.yml line 50-56 — Backend
- name: Build and push Backend
  uses: docker/build-push-action@v5
  with:
    context: backend            # 不是 .
    file: backend/Dockerfile
    ...
```

文件: `.github/workflows/cd_k8s.yml:42,53`。工期: 5 min。

### BUG-16 (CRITICAL): Celery healthcheck 在 prod 中使用 CMD exec form

**问题出在哪**:

`docker-compose.prod.yml:354,387` — Celery worker 和 GLM batch worker 的 healthcheck 使用 `CMD` exec form：

```yaml
test: ["CMD", "celery", "-A", "app.core.celery_app", "inspect", "ping", "-d", "celery@$$HOSTNAME"]
```

Docker 的 `CMD` exec form 不会展开 shell 变量。`$$HOSTNAME` 被**字面量**传递给 celery 命令。Celery 会尝试 ping 一个名为 `celery@$$HOSTNAME` 的字面量 worker ——它不存在，所以 healthcheck 永远不会成功。

对比：`docker-compose.yml:319`（开发环境）正确使用了 `CMD-SHELL`，变量可以正常展开。

**影响**: 生产环境的 Celery worker 被 Docker 标记为 unhealthy，编排系统可能反复重启它们。影响所有 L4 异步学习 pipeline（6 个 Celery 任务）。

**怎么改**:

```yaml
# docker-compose.prod.yml:354
healthcheck:
  test: ["CMD-SHELL", "celery -A app.core.celery_app inspect ping -d celery@$${HOSTNAME} 2>/dev/null || exit 1"]
```

同样修改 line 387（GLM batch worker）。

文件: `docker-compose.prod.yml:354,387`。工期: 5 min。

### BUG-17 (HIGH): 16 个服务中 15 个无 restart policy

**问题出在哪**:

`docker-compose.yml` — 16 个服务定义中只有 1 个显式设置了 `restart: "no"`（backend-api-dev），其余 15 个完全没有 restart 指令。

没有 restart policy 时，Docker 的默认行为是 `restart: "no"`——服务崩溃后不会自动重启。生产环境中这会导致：
- 凌晨 3 点 OOM kill → 服务永久下线直到人工介入
- Gateway 崩溃 → 所有 WebSocket 连接断开无法恢复
- gRPC server panic → Go↔Python 通信全部中断

**怎么改**:

```yaml
# 核心服务
restart: unless-stopped

# 数据服务
restart: always
```

文件: `docker-compose.yml`（15 个服务）+ `docker-compose.prod.yml`。工期: 10 min。

### BUG-18 (HIGH): Redis 没有 volume 挂载

**问题出在哪**:

`docker-compose.yml:54-70` — Redis 服务没有 `volumes:` 配置。持久化数据（RDB/AOF）、event bus stream 数据、session 缓存全部存储在容器 ephemeral 层。

`docker compose down` 会丢失所有 Redis 数据——包括活跃会话、待消费的 event bus 消息、幂等性锁、DLQ 中的死信事件。

**影响**: 每次重启都会丢失 Redis 状态。Event bus 中的未处理消息（consumer group offset 之后的）永久丢失。用户会话强制中断。

**怎么改**:

```yaml
redis:
  volumes:
    - ./redis_data:/data
```

文件: `docker-compose.yml:54`。工期: 5 min。

### BUG-19 (MEDIUM): Benchmark CI port 冲突

**问题出在哪**:

`.github/workflows/benchmark.yml:323-327` — benchmark workflow 同时启动 service containers（暴露 5432/6379 等端口）并运行 `make dev-all`（也会启动同类服务）。两个 PostgreSQL/Redis 实例争抢相同的 host 端口。

**影响**: Benchmark 结果不可靠——基准测试进程连接到哪个实例是不确定的。可能导致假阳性（连接了非预期实例）或假阴性（连接失败）。

**怎么改**:

在 benchmark CI 中不使用 `make dev-all`，而是仅依赖 service containers:

```yaml
# 移除 make dev-all，仅设置环境变量指向 service containers
env:
  POSTGRES_HOST: localhost
  REDIS_HOST: localhost
```

文件: `.github/workflows/benchmark.yml:323-327`。工期: 15 min。

## 7. 安全问题

### BUG-20 (HIGH): `isDevelopmentEnv()` 在 ENVIRONMENT 未设置时返回 true

**问题出在哪**:

`backend/gateway/internal/handler/websocket_factory.go:64-66`:

```go
func isDevelopmentEnv() bool {
    env := strings.ToLower(os.Getenv("ENVIRONMENT"))
    return env == "" || env == "dev" || env == "development"
}
```

当 `ENVIRONMENT` 环境变量未设置时，函数返回 `true`（开发模式）。这意味着：如果部署时忘了设置 `ENVIRONMENT=production`，系统在完全开放的开发模式下运行。

该函数在 3 个位置被调用：
- `chat_orchestrator.go:215` — 如果 dev 模式，使用 `DefaultUpgrader()`（允许**所有 Cross-Origin WebSocket 连接**，无 origin 验证）
- `chat_orchestrator_chatflow.go:581` — 如果 dev 模式，**跳过每日速率限制**
- `file_events.go:34` — 同 chat_orchestrator.go，WebSocket origin 检查被绕过

**影响**: 一个遗漏的环境变量 → 无 CORS 保护 + 无速率限制。任何网站都可以通过 WebSocket 连接到用户会话。

**怎么改**:

反转默认值——未知环境应默认为安全模式：

```go
func isDevelopmentEnv() bool {
    env := strings.ToLower(os.Getenv("ENVIRONMENT"))
    return env == "dev" || env == "development"
}
```

文件: `websocket_factory.go:65`。工期: 5 min。

### BUG-21 (MEDIUM): CQRS 健康端点未认证且泄露 DB 错误

**问题出在哪**:

`backend/gateway/cmd/server/setup.go` — `/api/v1/health/cqrs` 端点没有认证中间件。当 CQRS 投影或 saga 出错时，原始 DB 错误信息（可能包含表名、列名、查询结构）被直接返回给调用方。

**影响**: 任何人无需凭据即可探测 CQRS 基础设施状态，获取内部 DB schema 信息。

**怎么改**:

1. 添加认证中间件（与 `/api/v1/health` 保持一致）
2. 在返回前脱敏错误信息——将具体 DB 错误替换为通用 "CQRS component unhealthy"

文件: `setup.go`（CQRS 健康端点注册处）。工期: 20 min。

### BUG-22 (MEDIUM): `verify_preference_flow.py` 包含硬编码默认凭据

**问题出在哪**:

`backend/verify_preference_flow.py:18-19` — 包含硬编码的测试用户名和密码作为默认值。虽然是验证脚本，但可能被误用于连接非本地环境。

**怎么改**:

移除默认值，从环境变量读取且不提供 fallback：

```python
TEST_USERNAME = os.environ["SPARKLE_TEST_USERNAME"]
TEST_PASSWORD = os.environ["SPARKLE_TEST_PASSWORD"]
```

文件: `verify_preference_flow.py:18-19`。工期: 5 min。

### BUG-23 (LOW): Go 依赖有已知 CVE

**问题出在哪**:

`backend/gateway/go.mod` — `gin` v1.9.1 有 3 个已知 CVE（HTTP/2 rapid reset、CORS 绕过等）。`pgx` 有 CVE-2025-29693（SQL 注入风险，特定条件下）。

**影响**: 低——Sparkle 在 TLS 终结层（nginx/Caddy）处理后端 HTTP/2，pgx CVE 需要特定的非默认配置。但安全扫描工具会标记，影响合规性。

**怎么改**:

```bash
go get -u github.com/gin-gonic/gin@latest
go get -u github.com/jackc/pgx/v5@latest
go mod tidy
```

文件: `go.mod`。工期: 30 min（含测试验证）。
