### 残留缺陷（新，Major 级）：重启后历史尾部被 stale Redis 缓存遮蔽

- **现象**：杀 app 重启后，历史列表止于 `onboarding_skip`（04:06）；DB 尾部 3 条——ASSISTANT「已跳过初始化流程…」(04:08:23)、USER 北极星 prompt (04:08:26)、ASSISTANT 回复 (04:08:26)——**UI 不可见**（多次滚动+点击恢复卡确认到底，17）。
- **取证**：
  - Postgres `chat_messages`（user `e3322f40`）：13 行，含尾部 3 条；
  - Redis `chat:history:0f3cb241-…`：**恰好 10 条，止于 `_onboarding_skip_`，与 UI 所见逐条一致**；
  - `chat:session_meta:<sid>` 的 `title/last_message_at` 同样 stale（=`_onboarding_skip_` @04:06:52），而恢复卡标题（走 DB sessions 表）已是北极星 prompt——**双元数据源互相矛盾**在同一屏同时出现（16）；
  - 缓存 TTL 848s（≈15min 滚动过期，之后自愈）。
- **根因定性**：网关 `GetMessages`（`backend/gateway/internal/service/chat_history.go:510-530`）**Redis 命中即短路返回**，`getMessagesFromDB` 仅作空缓存 fallback；而缓存 append（同文件 `:295`/`:719` 写点）在 skip 后的 run + 北极星对上出现缺口（WS 主链在线时 append 了 1–10 条，最后 3 条未 append——触发面与 run 收束事件/缓存写入时机相关，待修卡定位）。**缓存 append 缺口 × 命中即返回 × 无一致性校正 = 尾部截断**。
- **影响**：B-01 的「重启可见性」只在缓存与 DB 一致时成立；任何造成 append 缺口的场景（杀 app 时机、断网恢复、收束事件丢失）用户都会看到截断的历史，且最长持续 ~15min。V13 判定面的「历史可见」算**部分达成**。
- **修复建议**（供派卡）：① 读路径合并（Redis 为快照 + DB 补尾部，或按 `last_message_at` 水位决定是否回源）；② 或缓存 append 与引擎落库共享同一事件源（引擎 ack 后 append），并给 `chat:history` 写入加幂等校验；③ `chat:session_meta` 与 DB sessions 表二选一为恢复卡事实源。

## ⑤ 总判定：北极星主链用户面是否闭环

**基本闭环，带一个 Major 残留。**

- **已闭环**：新号注册 → 画像引导（6–8s，无掷硬币）→ 建模访谈（全程有反馈、可取消、断流可见错误+重试）→ 主聊天发北极星 prompt（**发出即见、AI 回复可见、无双发无重复计费**）→ 后端全量落库（session 头+消息）→ 杀 app 重启后会话恢复、恢复卡正确 → 我的页趋势诚实空态 → 光子 1 跳可达。V13 的 Blocker（第一会话断裂）与四 Major 均已修复生效。
- **未闭环的一环**：重启后历史**尾部完整性**不保证（stale Redis 缓存遮蔽 DB 尾部消息，~15min 自愈）——B-01 的「历史可见」打了折扣，判定**部分通过**；以及回归抽查新发现的**重启后社群域 401**（不影响北极星主链，但属于用户面鉴权回归，建议尽快派卡）。
- 一句话：**用户从 0 到北极星主链的用户面旅程已经走通且体验闭环；「杀 app 重启看历史」这一步当前会缺最后几条消息，社群在重启后进不去。**
