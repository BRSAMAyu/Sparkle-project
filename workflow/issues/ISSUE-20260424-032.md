## [Audit] 证据

`_promote_next_queued_intent` 方法（execution_service.py:2363-2384）：

```python
async def _promote_next_queued_intent(self, *, user_id: UUID) -> None:
    active_total = await self._active_execution_count(user_id=user_id, intent_id=UUID(int=0))
    if active_total >= self._config.max_concurrent_runs:
        return
    result = await self._db.execute(
        select(ExecutionIntent)
        .where(...status == ExecutionIntentStatus.QUEUED...)
        .limit(1)
    )
    queued_intent = result.scalar_one_or_none()
    if queued_intent is None:
        return
    await self.dispatch(intent_id=queued_intent.id, user_id=user_id)
```

TOCTOU 问题：
1. `_active_execution_count` 查询时 active < max
2. 在查询和 dispatch 之间，另一个并发终端事件也执行了 `_promote_next_queued_intent`
3. 两个调用都通过 active < max 检查，各自 promote 一个 queued intent
4. 结果：实际运行数超过 `max_concurrent_runs`

此方法在 `confirm_result`、`reject_result`、`cancel`、`handback`、`_mark_intent_failure` 五处被调用，这些操作可能并发发生。

## [Audit] 建议修复方向

1. 使用 `SELECT ... FOR UPDATE` 锁定排队记录
2. 或使用 Redis 分布式锁（`execution_promote:{user_id}`）串行化 promote 操作
3. 或在 dispatch 方法中再次检查并发数并重新入队

## [Audit] 潜在副作用

- `SELECT FOR UPDATE` 需要事务内执行，当前方法未在显式事务中
- Redis 锁增加延迟，但执行操作本身有秒级延迟，影响不大
