# ISSUE-20260424-060 · achievement_photon_visual · P1

## 标题

`get_close_to_unlock_achievements` 对每个未解锁成就执行 `_evaluate_progress`，N+1 查询爆炸

## 证据

**文件**: `backend/app/services/achievement_engine.py`
**行号**: 2047-2131

```python
async def get_close_to_unlock_achievements(self, user_id, threshold=0.8, category=None, locale=None):
    all_achievements = await self._get_all_achievements()
    # ...filter by category...
    unlocked_ids = set(...)  # 1 query for all unlocked

    for achievement in all_achievements:
        if achievement.id in unlocked_ids or await self._is_unlocked(...):
            continue
        if not await self._check_prerequisites(user_id, achievement):  # 1+ queries each
            continue
        progress, current_value, target_value = await self._evaluate_progress(
            user_id, achievement  # 1-3 queries each (some like WEEKEND_WARRIOR: 3 queries)
        )
```

Flutter 端在 `close_to_unlock_provider.dart` 每次触发检查时调用此接口，有 5 分钟节流。

## 问题分析

假设系统有 50 个成就，用户已解锁 20 个：

- `_get_all_achievements()`: 1 query
- unlocked_ids: 1 query
- 循环 30 个未解锁成就:
  - `_is_unlocked`: 30 queries (含缓存短路但首次必穿透)
  - `_check_prerequisites`: 30+ queries
  - `_evaluate_progress`: 30-90 queries（WEEKEND_WARRIOR 每个 3 条）

**总计: 60-120 queries per call**。若 WEEKEND_WARRIOR 在列表中，还叠加 ISSUE-059 的全量加载问题。

此接口在每次专注会话完成后被调用（5 分钟节流），高活跃时段可能频繁触发。

## 修复建议

1. 批量查询用户进度，避免逐成就评估
2. 缓存进度评估结果（5 分钟 TTL 与 Flutter 端节流匹配）
3. 对已知高成本评估（WEEKEND_WARRIOR）单独优化
