# ISSUE-20260424-066 · P2

## Title

NotificationAnalyticsService._get_trends 逐日 N+1 查询，period='all' 可触发数千次 DB 查询

## Slice

11 — calendar_notification

## Evidence

- `backend/app/services/notification_analytics_service.py:365-472`: `_get_trends` 方法对 period 内的每一天执行一个 while 循环，每天执行 6+ 次 DB 查询：
  - `system_sent_stmt` (line 382)
  - `system_viewed_stmt` (line 394)
  - `intervention_notification_sent_stmt` (line 406)
  - `intervention_notification_viewed_stmt` (line 418)
  - `intervention_sent_stmt` (line 430)
  - `intervention_viewed_stmt` (line 441)
  - `_interaction_counts` (line 452)

  当 `period='30d'` 时 ≈ 210 次查询；当 `period='all'`（从 2020-01-01 起）时，超过 14,000 次查询。

- `backend/app/services/notification_analytics_service.py:629-644`: `_get_period_start_date('all')` 返回 `datetime(2020, 1, 1)`，确认无上限。

**预期**: 使用 GROUP BY date 的单次或少量查询聚合每日统计。
**实际**: 逐日循环查询，随时间线性增长。

## Impact

- `period='all'` 的分析请求可能导致 DB 连接池耗尽或超时
- Redis 缓存（1h TTL）缓解首次查询，但冷启动或过期后重复触发

## Suggested Fix

用 `GROUP BY DATE(created_at)` 单次查询替代逐日循环，参考 `_interaction_counts` 的聚合模式。

## 7D Classification

⑤ concurrency/idempotency — 性能缺陷，高并发下可能导致 DB 连接池耗尽
