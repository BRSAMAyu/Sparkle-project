# ISSUE-20260424-068 · P2

## Title

NotificationCenterService._find_notification_for_record 全量加载用户干预通知在 Python 侧遍历匹配

## Slice

11 — calendar_notification

## Evidence

- `backend/app/services/notification_center_service.py:1115-1132`:
  ```python
  async def _find_notification_for_record(self, user_id, record_id):
      result = await self.db.execute(
          select(Notification)
          .where(Notification.user_id == user_id, self._is_intervention_notification())
          .order_by(desc(Notification.created_at))
      )
      target = str(record_id)
      for notification in result.scalars().all():
          if str((notification.data or {}).get("record_id") or "") == target:
              return notification
      return None
  ```

  加载用户**所有**干预通知到 Python 内存，逐个检查 JSON 字段 `data.record_id` 是否匹配。

- 该方法在 `transition_intervention_record` (line 556-605) 中被调用。用户每次对干预记录执行 action（seen/accepted/dismissed），都触发全量加载。

- 对比 `_load_intervention_records_for_notifications` (line 1092-1113) 使用了 `in_(list)` 批量查询，效率更高。

**预期**: 使用 PostgreSQL JSONB 查询（`Notification.data['record_id'].astext == str(record_id)`）或维护显式外键。
**实际**: 全量加载 + Python 侧遍历，O(N) 随通知数量增长。

## Impact

- 长期用户（数千条干预通知）每次交互操作都触发大量 DB 读取和内存分配
- 在高并发场景下（多个干预同时被处理），DB 负载显著增加

## Suggested Fix

使用 SQLAlchemy JSONB filter: `Notification.data.op('->>')('record_id') == str(record_id)` 替代全量加载。或为 `notification_id` 到 `record_id` 建立映射表。

## 7D Classification

⑤ concurrency/idempotency — O(N) 查询随通知积累线性退化
