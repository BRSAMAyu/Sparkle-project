# ISSUE-20260424-073 · P1

## Title

_rate_limit_state 是进程级 in-memory dict，多 worker 部署下限流失效

## Slice

12 — memory_write_lane

## Evidence

- `backend/app/services/memory_inferred_write_lane.py:77`:
  ```python
  _rate_limit_state: dict[str, list[datetime]] = {}
  ```
  类级别属性，每个 Python 进程独立维护。

- `backend/app/services/memory_inferred_write_lane.py:306-315`:
  ```python
  @classmethod
  def _within_rate_limit(cls, user_id: UUID) -> bool:
      now = _utcnow()
      key = str(user_id)
      history = [stamp for stamp in cls._rate_limit_state.get(key, []) if (now - stamp).total_seconds() < 60]
      if len(history) >= 10:
          return False
      ...
  ```
  每个 worker 进程独立检查，N 个 worker = 实际限流 N×10/分钟。

- `backend/app/services/memory_inferred_write_lane.py:599`:
  ```python
  # TRACKED(TD-008): enforce per-session rate limits (1-2 memories) once session tracking is available.
  ```
  TD-008 标注说明当前的限流设计是临时方案，per-session 限流尚未实现。

**预期**: 每用户每分钟最多 10 次推断记忆写入。
**实际**: 在 gunicorn/gevent 多 worker 环境下，每用户的实际限流 = 10 × worker 数量/分钟。

## Impact

- 高并发场景下用户可能在短时间内被写入大量低质量推断记忆
- 与 Rule Y 治理规则中"推断写入必须可限流"的要求不一致

## Suggested Fix

使用 Redis sliding window 替代 in-memory dict（参考 Go Gateway 的 `distributed_rate_limiter.go`），或使用 `cache_service` 的 Redis 实例实现分布式限流。

## 7D Classification

⑤ concurrency/idempotency — 多进程限流失效
