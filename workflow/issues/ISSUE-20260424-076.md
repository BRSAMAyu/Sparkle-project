# ISSUE-20260424-076 · P2

## Title

MemoryPolicyEvaluator 每次写入都查询 UserMemorySettings，无请求级缓存

## Slice

12 — memory_write_lane

## Evidence

- `backend/app/services/memory_policy_evaluator.py:63-70`:
  ```python
  async def _get_settings(self, user_id: UUID) -> UserMemorySettings | None:
      result = await self.db.execute(
          select(UserMemorySettings).where(
              UserMemorySettings.user_id == user_id,
              UserMemorySettings.deleted_at.is_(None),
          )
      )
      return result.scalar_one_or_none()
  ```
  每次调用都执行独立 DB 查询。

- `backend/app/services/memory_service.py:1007-1022`: `_allow_write` 在每次 `upsert_preference`、`create_goal`、`create_episodic_memory` 中被调用，每次都创建新的 `MemoryPolicyEvaluator` 实例并查询。

- `backend/app/services/memory_inferred_write_lane.py:384-396`: `_is_user_disabled` 也独立查询 `UserMemorySettings`，不共享 `MemoryPolicyEvaluator` 的结果。

**预期**: 用户设置在一次请求/会话内不变，应缓存。
**实际**: 单次 chat turn 中如果触发多个记忆写入（preference + episodic），会产生 2-3 次重复的 UserMemorySettings 查询。

## Impact

- 增加不必要的 DB 负载，尤其在 memory write 密集的场景（初次聊天、偏好变更）
- 与其他类似查询（如 `_is_user_disabled`）重复

## Suggested Fix

在 `_allow_write` 或 `MemoryPolicyEvaluator` 中添加请求级缓存（如 `contextvars` 或 per-instance dict with TTL），或复用 `_is_user_disabled` 的查询结果。

## 7D Classification

⑤ concurrency/idempotency — 重复 DB 查询
