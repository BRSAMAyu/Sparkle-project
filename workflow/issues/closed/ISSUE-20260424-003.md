## [Audit] 证据

**问题**: Guest login 限流 `100/15minutes` 极为宽松，且 guest_id 由客户端指定，可被滥用创建大量账号。

**证据 1** — auth.py:798-799:
```python
@router.post("/guest", response_model=Any)
@limiter.limit("100/15minutes")
async def guest_login(request, guest_id: str = None, db):
```
每 IP 每 15 分钟允许 100 次 guest login。对比正常注册 `5/15minutes`（生产），guest 限流是注册的 20 倍。

**证据 2** — auth.py:812-816:
```python
if not guest_id:
    guest_id = 'guest_' + ''.join(random.choices(...))
```
客户端可传入 `guest_id` 参数，且 SELECT 查询 (line 819-822) 使用该参数：
```python
existing_user = await db.execute(
    select(User).where(User.username == guest_id)
)
```

**证据 3** — 每次新 guest 创建会触发 `seed_guest_user_data` (line 842-843)，这是重量级操作（插入演示数据）。

**预期**: Guest login 应有合理限流防止滥用。
**实际**: 100/15min 允许单 IP 每天创建约 9600 个 guest 账号，每个都带完整演示数据种子。

**复现步骤**:
1. 单一 IP 发送 100 次 POST `/auth/guest` 不同 guest_id
2. 100 个 guest 用户被创建，每个带完整演示数据
3. 15 分钟后可继续创建 100 个

## [Audit] 建议修复方向

1. 降低 guest login 限流到 `10/15minutes` 或更低（与注册限流同级别或略宽松）
2. 服务端生成 guest_id（忽略客户端传入值），或至少验证格式（`guest_` 前缀 + 固定长度）
3. 考虑添加 IP 级别的 guest 账号总数限制

## [Audit] 潜在副作用

- 降低限流可能影响高并发真实 guest 体验场景（如展会 demo）
- 可通过配置区分 dev 和 production 限流（与现有 AUTH_RATE_LIMIT 模式一致）
- 需确认 Flutter 端 guestLogin 调用是否依赖自定义 guest_id（从代码看，Flutter 传入的 guest_id 为设备标识，服务端可接管生成）
