## [Audit] 证据

**saveMessage 静默丢弃 Redis 写入失败，用户消息不可恢复丢失**

`chat_orchestrator_feedback.go:67-69`:
```go
if err := h.chatHistory.SaveMessage(ctx, sessionID, data); err != nil {
    log.Printf("Failed to save chat message: %v", err)
}
```

`chat_orchestrator_chatflow.go:224-228` 在发送到 Python gRPC **之前**就调用了 `h.saveMessage`:
```go
if input.SessionID != "" {
    sessionID := input.SessionID
    message := input.Message
    h.saveMessage(userID, sessionID, "user", message, nil)
}
```

**预期**: 用户消息应当持久化。如果 Redis 写入失败，应当至少重试一次或通知客户端消息未保存。
**实际**: 错误只写 log.Printf。如果 Redis 闪断或不可用，用户发送的消息被转发到 Python 处理，但 **Redis 侧的聊天历史不会包含该消息**。重连后历史记录丢失，用户无法看到自己之前发的消息。

复现: 在 Redis 连接闪断时（例如 redis restart），发送聊天消息。消息会被正常处理和回复，但 Redis 历史中缺失这条消息。

## [Audit] 建议修复方向

1. 方案 A：在 `saveMessage` 失败时返回 error，由 `handleChatMessage` 决定是否继续（可能给客户端发一条 "消息已发送但历史保存失败" 的提示）
2. 方案 B：在 `saveMessage` 内加一次简单重试（1 次，短间隔）
3. 方案 C：将 saveMessage 的失败写入 DLQ，由后台 worker 异步补写

## [Audit] 潜在副作用

- `saveMessage` 被 `handleChatMessage` (user message) 和第 668 行 (assistant response) 两处调用
- 如果方案 A 要求 return error，assistant 侧的 saveMessage 也需要处理
- ChatHistoryService.SaveMessage 内部实现可能有自身重试逻辑，需确认

## [Fix] 复核结论

**判定: disputed** — 问题核心观察成立（saveMessage 静默丢弃错误），但严重性被高估为 P1，实际应为 P2。Auditor 未能发现代码中已有的多层保护机制。

### 独立反证证据

1. **Circuit Breaker + Retry Buffer** — `chat_history.go:237-250`:
   当 persist queue 超过 `breakerThreshold` 时，消息不丢弃，进入本地 `retryBuf`（最大 `breakerRetryBufMax` 条）。这不是 Auditor 说的"静默丢弃"。

2. **retryWorker** — `chat_history.go:123`:
   独立 goroutine 每 `breakerRetryInterval` 刷新 retry buffer 到 persist queue。已标注为"P1修复: 队列过载时进入本地重试缓冲...不再直接丢弃"（line 241）。

3. **DB Fallback on Reads** — `chat_history.go:308-309`:
   `GetMessages` 在 Redis 查询失败时自动降级到 DB 查询。即使 Redis 历史缺失，用户重连后仍可能从 DB 恢复历史。

4. **消息交付不受影响**:
   `saveMessage` 仅写 Redis 历史，不影响消息转发到 Python gRPC 处理。用户的消息仍然被 AI 正常处理和回复。

### 三问回答

- **预期是否成立**：部分成立。理想情况下所有消息都应持久化。但 Auditor 说的"不可恢复丢失"不准确——有 retry buffer + DB fallback。
- **配置/flag 覆盖**：无 feature flag，但 `breakerThreshold` 和 `breakerRetryBufMax` 可配置。
- **修复回归风险**：在 Redis 完全不可用时添加重试也无法解决（重试也需要 Redis）。这是基础设施级故障，不是代码缺陷。

### 建议处置

- **降级为 P2**：这是质量加固（在现有保护机制上增加一层重试），不是链路断裂
- **不建议修复**：在 Redis 完全不可用的极端情况下，添加重试也不会有效（retryWorker 也依赖 Redis）。现有机制已足够
- 若 Verifier 认为仍需修复，建议方案 B（saveMessage 调用侧加一次短间隔重试），但实际收益有限

## [Fix] 变更摘要

无代码修改。保护机制已存在。
