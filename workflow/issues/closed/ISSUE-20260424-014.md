## [Audit] 证据

**问题**: `ConnectionRegistry.GetWriter` 和 `Get` 在用户有多条连接时返回非确定性的连接，导致服务器推送（如 PushIntervention）可能发送到错误的设备。

**证据 1** — ws_registry.go:115-128，`GetWriter` 遍历 map 取第一个非 nil writer：
```go
for _, entry := range entries {  // ← Go map 遍历顺序不确定
    if entry != nil && entry.writer != nil {
        return entry.writer, true
    }
}
```

**证据 2** — ws_registry.go:102-113，`Get` 同样遍历 map：
```go
for conn := range entries {  // ← 非确定性
    return conn, true
}
```

**证据 3** — chat_orchestrator.go:603-631，`PushIntervention` 调用 `GetWriter`：
```go
writer, exists := h.getConnectionWriter(userID)
if err := writer.WriteJSON(message); err != nil { ... }
```

**证据 4** — 当 `cfg.WSMaxConnections > 1` 时，同一用户可有多条连接（ws_registry.go:49-54 允许）。

**预期**: 服务器推送应发送到用户当前活跃的设备，或广播到所有连接。
**实际**: 推送发送到 Go map 迭代的第一个连接（非确定性），可能发到后台设备。

**复现步骤**:
1. 用户在手机和电脑同时登录（WSMaxConnections ≥ 2）
2. 后端触发 PushIntervention
3. 干预消息只到达其中一台设备（非确定哪台）

## [Audit] 建议修复方向

1. **方案 A（推荐）**: `GetWriter`/`Get` 返回最近活跃的连接（`connectionEntry` 记录 `lastActivity` 时间戳）
2. **方案 B**: 修改 `PushIntervention` 等推送方法，广播到该用户所有连接
3. 如果多连接是设计意图，考虑将推送改为广播模式

## [Audit] 潜在副作用

- 方案 A 增加每次消息的元数据更新开销（微小）
- 方案 B 改变推送语义（一条消息发多次），需确认消费端幂等
- 影响 PushIntervention 和所有使用 getConnection/getConnectionWriter 的调用者
