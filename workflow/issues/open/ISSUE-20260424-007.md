## [Audit] 证据

**saveMessage 静默丢弃 Redis 写入失败，用户消息不可恢复丢失**

`chat_orchestrator_feedback.go:67-69`:
```go
if err := h.chatHistory.SaveMessage(ctx, sessionID, data); err != nil {
    log.Printf("Failed to save chat message: %v", err)
}
```

`chat_orchestrator_chatflow.go:224-228` 在发送到 Python gRPC **之前**就调用了 `h.saveMessage`:
```go
if input.SessionID != "" {
    sessionID := input.SessionID
    message := input.Message
    h.saveMessage(userID, sessionID, "user", message, nil)
}
```

**预期**: 用户消息应当持久化。如果 Redis 写入失败，应当至少重试一次或通知客户端消息未保存。
**实际**: 错误只写 log.Printf。如果 Redis 闪断或不可用，用户发送的消息被转发到 Python 处理，但 **Redis 侧的聊天历史不会包含该消息**。重连后历史记录丢失，用户无法看到自己之前发的消息。

复现: 在 Redis 连接闪断时（例如 redis restart），发送聊天消息。消息会被正常处理和回复，但 Redis 历史中缺失这条消息。

## [Audit] 建议修复方向

1. 方案 A：在 `saveMessage` 失败时返回 error，由 `handleChatMessage` 决定是否继续（可能给客户端发一条 "消息已发送但历史保存失败" 的提示）
2. 方案 B：在 `saveMessage` 内加一次简单重试（1 次，短间隔）
3. 方案 C：将 saveMessage 的失败写入 DLQ，由后台 worker 异步补写

## [Audit] 潜在副作用

- `saveMessage` 被 `handleChatMessage` (user message) 和第 668 行 (assistant response) 两处调用
- 如果方案 A 要求 return error，assistant 侧的 saveMessage 也需要处理
- ChatHistoryService.SaveMessage 内部实现可能有自身重试逻辑，需确认
