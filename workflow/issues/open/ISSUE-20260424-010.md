## [Audit] 证据

**客户端发送的 active_tools 未做白名单校验，可注入任意工具名**

`orchestrator.py:699-715`:
```python
def _resolve_active_tools(self, request, user_message):
    requested = [tool.strip() for tool in list(request.active_tools) if str(tool).strip()]
    explicit_request = bool(requested)
    for inferred in self._infer_bridge_tool_names(user_message):
        if inferred not in requested:
            requested.append(inferred)
    if not explicit_request:
        # ... capability selection
    return requested
```

`request.active_tools` 来自客户端 WebSocket 消息的 `active_tools` 字段（`chat_orchestrator.go:51` → `chatInput.ActiveTools` → `agentv1.ChatRequest.ActiveTools`）。

**预期**: 客户端请求的工具名应被限定在 `DynamicToolRegistry` 已注册的工具范围内。
**实际**: `requested` 列表仅做 trim + 空过滤，无白名单校验。虽然 `_resolve_active_tools` 的返回值最终需要在 `DynamicToolRegistry` 中查找才能获得实际工具实例，恶意工具名不会导致注入执行，但未被识别的工具名会：
1. 被写入 `state.context_data["resolved_active_tools"]` (line 1174)
2. 可能在 prompt 中被引用，浪费 token
3. 可能在日志/指标中产生噪音

这是一个**注入安全边界缺失**而非直接可利用的漏洞。

复现: 发送 WebSocket 消息 `{"message":"test","active_tools":["../../etc/passwd","FAKE_TOOL"]}`。观察 orchestrator 日志中 `resolved_active_tools` 是否包含这些值。

## [Audit] 建议修复方向

在 `_resolve_active_tools` 返回前，与 `DynamicToolRegistry.list_tool_names()` 做交集过滤：
```python
registered = set(self.tool_registry.list_tool_names())
requested = [t for t in requested if t in registered]
```

## [Audit] 潜在副作用

- `_infer_bridge_tool_names` 推断出的工具名应该都在 registry 中，不会受影响
- `CapabilitySelectionPolicy.choose_pre_context_tools` 返回的工具名同理
- 需确认 `DynamicToolRegistry` 是否暴露 `list_tool_names()` 方法
