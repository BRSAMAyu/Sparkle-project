## [Audit] 证据

**Flutter WS fallback 路径将 JWT 直接暴露在 URL query parameter 中**

`websocket_chat_service_v2.dart:1390-1396`:
```dart
final queryParameters = <String, String>{'user_id': userId};
if (wsTicket != null && wsTicket.isNotEmpty) {
  queryParameters['ticket'] = wsTicket;
} else if (effectiveToken != null && effectiveToken.isNotEmpty) {
  // Fallback for environments where ws ticket exchange is unavailable.
  queryParameters['token'] = effectiveToken;
}
```

当 `wsTicket` 获取失败时（如 `/api/v1/auth/ws-ticket` 端点不可用），JWT token 作为 `?token=` query parameter 发送。

**预期**: JWT 应通过 header 或一次性 ticket 传递，不应出现在 URL 中（URL 会被浏览器历史、代理日志、Referer header 记录）。
**实际**: fallback 路径将 JWT 放在 URL 里。虽然有 `ws_ticket` 机制作为主要路径，但 fallback 没有降级策略（如直接拒绝连接）。

Go 侧 `ws_auth.go:61-78` 确认 `AllowWsQueryToken` 开关控制此行为——如果为 false，query token 不被接受。但 Flutter 端代码**无条件**尝试 query token fallback，不顾 `AllowWsQueryToken` 的值。

**风险级别**: 生产环境中 `AllowWsQueryToken` 可能被设为 true（因为 Flutter 无法发送自定义 header 的场景），此时 JWT 会出现在 URL 中。

复现: 使 ws-ticket 端点返回错误（如返回 500），观察 Flutter 客户端连接 URL 中是否出现 `?token=eyJ...`。

## [Audit] 建议修复方向

1. 优先：确保 ws-ticket 端点高可用，Flutter 端在 ticket 失败时重试 1-2 次
2. 次优：如果 ticket 彻底不可用，fallback 应该只通过 `Sec-WebSocket-Protocol` header 传递（已支持：`ws_auth.go:144-161` 解析 ticket header），而不是 query parameter
3. 最小改动：在 Flutter 端加一个 warning log 当使用 query token fallback 时

## [Audit] 潜在副作用

- 如果移除 query token fallback，某些无法设置自定义 header 的环境（如旧版 Flutter web）可能无法连接
- `Sec-WebSocket-Protocol` header 方案已存在，但需要 Flutter 端适配
