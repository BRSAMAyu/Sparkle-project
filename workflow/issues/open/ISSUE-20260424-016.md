## Title

pending_actions_store get-then-delete 非原子操作，并发 SubmitPlanReview 可重复审批

## Evidence

`backend/app/orchestration/plan_review_service.py`:

- **Line 1485**: `action = await pending_actions_store.get(review_id, user_id)` — 读取存储的操作
- **Lines 1498-1560**: 多个 `await` 调用（`track_rejection_count`, `reset_rejection_count`, `_trigger_information_collection`, `feedback_service.update_feedback_decision` 等）— 每个 await 都是让出控制权的点
- **Line 1561**: `await pending_actions_store.delete(review_id, user_id)` — 最后才删除

`backend/app/core/pending_actions.py`:

- **Lines 104-128** (Redis path): `get` 方法先 GET 再检查 user_id，`delete` 方法先 GET 再 DELETE — 两次独立 Redis 调用
- **Lines 115-127** (内存路径): `get` 读 dict，`delete` 读 dict 再删 — 同样非原子

## Concurrency Scenario

```
Time    Request A                           Request B
─────   ──────────────────────────          ──────────────────────────
T1      get(review_id) → action ✓
T2                                          get(review_id) → action ✓  (未删除)
T3      track_rejection_count (await)       track_rejection_count (await)
T4      feedback_service.update (await)     feedback_service.update (await)
T5      delete(review_id) → True            delete(review_id) → False
T6      → 触发审批/拒绝                      → 也触发审批/拒绝
```

两次请求都通过了 `get` 检查，都会触发后续操作（任务生成、事件发布、反馈写入）。

## Impact

- 重复审批触发重复任务生成（用户看到两套任务）
- 重复反馈写入（feedback_log 出现重复条目）
- 重复事件发布（event_bus 事件重复消费）
- 重复拒绝计数增加（可能过早触发信息收集）

## Suggested Fix

使用 Redis Lua 脚本实现原子 get-and-delete：

```lua
local data = redis.call('GET', KEYS[1])
if data then
    local parsed = cjson.decode(data)
    if parsed.user_id == ARGV[1] then
        redis.call('DEL', KEYS[1])
        return data
    end
end
return nil
```

或在 `handle_review_feedback` 入口使用 `asyncio.Lock` 按 review_id 加锁。
