## Title

get_stored_plan 永远返回 None (stub)，计划恢复前无法验证计划存在

## Evidence

`backend/app/orchestration/plan_review_service.py`:

- **Lines 1571-1585**: `get_stored_plan` 方法
  ```python
  async def get_stored_plan(self, plan_id: str, user_id: str) -> dict[str, Any] | None:
      # This would integrate with a plan storage system
      # For now, plans are stored in orchestrator state
      logger.info(f"Retrieving stored plan {plan_id} for user {user_id}")
      return None
  ```

- **Line 1582**: 注释 "For now, plans are stored in orchestrator state" — 计划实际存在 orchestrator FSM 中

- `resume_plan_after_approval`（line 1587）不调用 `get_stored_plan`，直接通过 `pending_actions_store` 保存 `__plan_approved__` action 等待 orchestrator 消费

- Orchestrator 消费 `__plan_approved__` 时，无法验证 plan_id 对应的计划是否真实存在

## Impact

- 如果 plan_id 无效（不存在或已删除），审批仍会成功记录，但 orchestrator 无法恢复对应计划
- 用户看到"已批准"但计划不执行，与 ISSUE-015 叠加影响更大
- 反馈日志可能记录不存在计划的反馈

## Suggested Fix

1. 短期：`resume_plan_after_approval` 在保存 action 前查询 DB 验证 plan_id 存在
2. 中期：实现 `get_stored_plan` 从 DB 或 orchestrator state 中读取计划数据
3. 长期：将计划存储独立为 `PlanStorageService`
