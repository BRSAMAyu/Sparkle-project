## Title

BlockedPresentationHistoryStore 本地 fallback 字典无限增长，无淘汰机制

## Evidence

`backend/app/orchestration/ux_envelope.py`:

- **Lines 109-142**: `BlockedPresentationHistoryStore`
  - **Line 110**: `TTL_SECONDS = 60 * 60 * 24 * 30` (30 天)
  - **Lines 124-137**: Redis 路径正确使用 `setex` 带 TTL
  - **Lines 138-142**: 本地 fallback 路径:
    ```python
    payload = self._local_state.get(key) or {"count": 0}
    count = int(payload.get("count") or 0) + 1
    self._local_state[key] = {"count": count, "last_seen_at": now}
    ```
    - `_local_state` 是一个普通 `dict`（line 113）
    - **无 TTL 淘汰**：条目一旦写入永远不会被删除
    - **无大小限制**：每个 `user_id + failure_kind` 组合创建一个条目
    - key 格式为 `ux:blocking:{user_id}:{failure_kind}`（line 117），有 8 种 failure_kind

## Impact

- 在 Redis 不可用期间，每个用户的每个 failure_kind 会创建一个永不过期的本地缓存条目
- 长时间运行的进程中（celery worker、gRPC server），如果 Redis 偶尔不可用，`_local_state` 会持续增长
- 活跃用户数量 * 8 failure_kind = 大量内存占用
- 与 Redis 路径的 30 天 TTL 行为不一致

## Suggested Fix

1. 添加定期清理任务（类似 `pending_actions_store._cleanup_expired`）
2. 或为 `_local_state` 设置最大条目数（LRU 淘汰）
3. 或在 `record` 方法中检查 TTL：
   ```python
   last_seen = payload.get("last_seen_at")
   if last_seen and _parse_dt(last_seen) < _utcnow() - timedelta(seconds=self.TTL_SECONDS):
       del self._local_state[key]
       return 0
   ```
