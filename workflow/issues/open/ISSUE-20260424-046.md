## [Audit] 证据

**问题**: `AnalyzeError` gRPC handler 使用 `asyncio.create_task` fire-and-forget，分析任务不受追踪、错误静默丢失。

**证据** — error_book_grpc_service.py:159-170:
```python
async def AnalyzeError(self, request, context):
    async with self.db_session_factory() as db:
        service = ErrorBookService(db)
        error = await service.get_error(UUID(request.error_id), UUID(request.user_id))
        if not error:
            context.set_code(grpc.StatusCode.NOT_FOUND)
            return error_book_pb2.AnalyzeErrorResponse()

        import asyncio
        asyncio.create_task(self._run_analysis_task(UUID(request.error_id), UUID(request.user_id)))

        return error_book_pb2.AnalyzeErrorResponse(message="Analysis task submitted")
```

**对比** — 同文件 `CreateError` (line 58-59) 使用 `task_manager.spawn()`，具备追踪、统计和配额控制：
```python
await task_manager.spawn(
    self._run_analysis_task(error.id, UUID(request.user_id)),
    task_name="error_analysis",
    user_id=request.user_id
)
```

**预期**: 分析任务应使用 `task_manager.spawn()` 或至少有错误回调，与 `CreateError` 路径一致。
**实际**: `asyncio.create_task` 启动后无引用持有，任务失败无日志无重试。

**复现**:
1. 通过 gRPC 调用 `AnalyzeError` 触发重新分析
2. 如果 `_run_analysis_task` 内部异常（如 LLM 超时），异常被吞入 task，无任何 observable 输出
3. 用户刷新页面仍看到旧分析结果，不知道重新分析已失败

## [Audit] 建议修复方向

1. 将 `asyncio.create_task(...)` 替换为 `await task_manager.spawn(self._run_analysis_task(...), task_name="error_reanalysis", user_id=request.user_id)`
2. 与 `CreateError` 保持一致的错误追踪模式

## [Audit] 潜在副作用

- 纯后台任务管理变更，不影响前端交互
- 不改变分析结果本身
