## [Audit] 证据

**问题**: `_count_recent_triggering_errors` 在 SQL 层仅过滤 `user_id` 和 `is_deleted`，不加日期条件，将用户全部错题加载到 Python 内存后再逐条过滤。

**证据** — error_replan_bridge.py:471-481:
```python
result = await self.db.execute(
    select(
        ErrorRecord.id,
        ErrorRecord.created_at,
        ErrorRecord.latest_analysis,
        ErrorRecord.linked_knowledge_node_ids,
    )
    .where(ErrorRecord.user_id == user_id)
    .where(ErrorRecord.is_deleted.is_(False))
    .order_by(desc(ErrorRecord.created_at))
)
```

`cutoff = _utcnow() - timedelta(days=days)` 在 line 470 计算，但仅在 Python 循环 (line 488-489) 中使用：
```python
if normalized_created_at and normalized_created_at < cutoff:
    continue
```

**预期**: SQL 查询应加 `where(ErrorRecord.created_at >= cutoff)` 在数据库层过滤，避免传输大量历史数据。
**实际**: 所有非删除错题（含 JSONB `latest_analysis` 列）全量加载。活跃用户积累 1000+ 错题时，每次 `on_error_created` 触发此查询，内存和 DB 负载显著。

**复现**:
1. 用户累计 500+ 错题记录（含 `latest_analysis` JSONB 平均 2KB）
2. 创建新错题 → 触发 ErrorReplanBridge
3. `_count_recent_triggering_errors` 加载 ~1MB JSONB 数据到 Python，仅使用最近 7 天的几条

## [Audit] 建议修复方向

1. 在 SQL 查询中添加 `.where(ErrorRecord.created_at >= cutoff)`
2. 由于结果按 `created_at desc` 排序，`< cutoff` 的记录在尾部，加 SQL 过滤可减少 90%+ 传输量

## [Audit] 潜在副作用

- 纯查询优化，不改变业务逻辑
- `cutoff` 使用 naive datetime，需确保与 DB 时区一致
