## [Audit] 证据

**问题**: `delete_error` 查询条件不包含 `is_deleted == False` 过滤，对已软删除的错题仍返回 True，导致 REST/gRPC 返回 204 而非 404。

**证据** — error_book_service.py:714-726:
```python
async def delete_error(self, error_id: UUID, user_id: UUID) -> bool:
    stmt = select(ErrorRecord).where(
        and_(ErrorRecord.id == error_id, ErrorRecord.user_id == user_id)
    )
    result = await self.db.execute(stmt)
    error = result.scalar_one_or_none()

    if not error:
        return False

    error.is_deleted = True
    await self.db.commit()
    return True
```

**对比** — 同文件 `get_error` (line 567-568) 正确过滤了 `is_deleted`:
```python
stmt = select(ErrorRecord).where(
    and_(
        ErrorRecord.id == error_id,
        ErrorRecord.user_id == user_id,
        ErrorRecord.is_deleted.is_(False)
    )
)
```

**预期**: 已软删除的错题应返回 `False` → API 返回 404。
**实际**: 已删除错题被找到，`is_deleted = True` 再次设置（无操作幂等），返回 `True` → API 返回 204。

**复现**:
1. 创建错题 → DELETE → 得到 204（正确）
2. 再次 DELETE 同一错题 → 仍得到 204（应为 404）

## [Audit] 建议修复方向

1. 在 `delete_error` 的查询中添加 `ErrorRecord.is_deleted.is_(False)`
2. 或先调用 `get_error` 复用已存在的过滤逻辑

## [Audit] 潜在副作用

- 行为变更：第二次删除同一错题从 204 变为 404
- 前端需确认不依赖幂等 204 行为
