## [Audit] 证据

**问题**: `submit_review` 读取 error 当前状态、计算新 mastery/review 参数、写回，整个过程无乐观锁或原子更新保护。并发提交复习记录时存在 read-modify-write 竞态。

**证据** — error_book_service.py:728-753:
```python
async def submit_review(self, user_id: UUID, error_id: UUID, data: ReviewAction) -> ErrorRecord:
    error = await self.get_error(error_id, user_id)   # READ
    if not error:
        raise ValueError(...)

    previous_mastery = error.mastery_level or 0.0

    new_mastery, new_ef, new_interval, next_review = self.review_scheduler.calculate_next_review(
        current_mastery=error.mastery_level or 0.0,    # Uses READ value
        ...
        performance=data.performance
    )

    error.mastery_level = new_mastery                  # WRITE
    error.easiness_factor = new_ef
    ...
    await self.db.commit()
```

**预期**: 并发复习提交应串行化，后一次基于前一次的结果计算。或使用 `UPDATE ... SET mastery_level = mastery_level + delta` 等原子更新。
**实际**: 两个并发请求读同一 mastery_level，各自计算不同结果，后提交覆盖前者，丢失一次复习的效果。

**复现**:
1. 用户在两个设备上同时对同一错题提交复习
2. 两个请求都读到 `mastery_level=0.3`
3. 请求 A 算出 0.45，请求 B 算出 0.10
4. 请求 B 后写入，mastery_level=0.10（覆盖了 A 的 0.45）
5. 一次复习的进度提升被丢失

**注意**: 此竞态在当前移动端使用场景下概率较低（用户通常单设备操作），但作为 SM-2 算法正确性基础，应予防护。

## [Audit] 建议修复方向

1. 短期：在 UPDATE 前添加 `SELECT ... FOR UPDATE` 行锁
2. 长期：将 mastery 计算下推到 SQL 原子更新（`mastery_level = mastery_level + :delta`）

## [Audit] 潜在副作用

- 添加行锁可能在极端并发下增加 DB 等待
- 不影响单次复习的计算结果
