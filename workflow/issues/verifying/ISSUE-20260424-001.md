## [Audit] 证据

**问题**: Go Gateway `validateJWT` 不检查 `session_revoked:{sid}` 缓存键，导致用户通过"设备管理"界面下线设备后，被下线的 access token 在过期前仍被 Go Gateway 放行。

**证据 1** — Go `validateJWT` (auth.go:234-396) 只检查两个 Redis 键：
- `token_blacklist:{jti}` (line 302) — 单 token 撤销
- `user_revoked_before:{userID}` (line 328) — 用户级撤销

**从未检查** `session_revoked:{sessionID}` 键，也不从 JWT claims 中提取 `sid` 字段。

**证据 2** — Python `auth_session_service.revoke_session` (auth_session_service.py:132-137) 在用户下线设备时写入：
```python
await cache_service.set(f"{SESSION_REVOKED_PREFIX}{session.session_id}", "1", ttl=ttl_seconds)
```

**证据 3** — Python `revoke_session` API (users.py:425-451) 调用 `auth_session_service.revoke_session_by_id`，写入 DB + Redis cache。但 Go 侧对此毫不知情。

**证据 4** — JWT access token 中包含 `sid` 字段（auth.go:186, auth.py:137），Go `validateJWT` 解析了 claims 但未提取 `sid`。

**预期**: 用户在"设备管理"点击"下线"后，该设备的 access token 应立即被拒绝。
**实际**: 该设备的 access token 在 `ACCESS_TOKEN_EXPIRE_MINUTES`（默认30分钟）内仍被 Go Gateway 放行，直到自然过期。

**复现步骤**:
1. 用户 A 在设备 1 登录获取 access token
2. 用户 A 在设备 2 登录，进入"设备管理"
3. 用户 A 下线设备 1
4. 设备 1 用已有 access token 发请求 → Go Gateway 放行（应为拒绝）

## [Audit] 建议修复方向

在 `validateJWT` 中提取 `claims["sid"]`，检查 Redis `session_revoked:{sid}` 是否存在。若存在则拒绝。注意：
- 该检查应在 JTI 黑名单检查之后、exp 检查之前
- 需要处理 Redis 不可用时的 fail-closed/fail-open 行为（与现有策略一致）
- `session_revoked:` 前缀需要与 Python 端 `SESSION_REVOKED_PREFIX` 一致

## [Audit] 潜在副作用

- 增加一次 Redis GET 调用，对每请求延迟有微小影响
- 影响所有经过 `AuthMiddleware` 和 `WsAuthMiddleware` 的请求（两者都调用 `validateJWT`）
- 现有 Go 和 Python 的 session revocation 语义将统一
- 相关测试: backend/gateway 的 auth middleware 测试需补充 session revocation 场景

## [Fix] 复核结论

**判定: confirmed** — 问题成立。

独立验证证据：
1. Go `createAccessToken` (handler/auth.go:186): JWT 包含 `"sid": sessionID`
2. Go `validateJWT` (middleware/auth.go:234-396): 提取 sub/jti/iat/exp 但未提取 sid，未检查 `session_revoked:{sid}`
3. Python `revoke_session` (auth_session_service.py:136): 写入 `session_revoked:{session_id}` 到 Redis
4. Python `SESSION_REVOKED_PREFIX` = `"session_revoked:"` (auth_session_service.py:17) — 与 Go 修复中的前缀一致

三问：
- 预期是否成立：是。设备下线后 token 立即失效是基本安全预期。
- 配置/flag 覆盖：否。这是代码路径缺失。
- 修复回归风险：低。仅增加一次 Redis EXISTS 调用，复用现有 fail-closed/fail-open 策略。
