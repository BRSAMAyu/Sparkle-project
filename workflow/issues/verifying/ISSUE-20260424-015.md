## Title

asyncio.create_task fire-and-forget 导致计划批准后任务生成/记忆捕获静默失败

## Evidence

`backend/app/orchestration/plan_review_service.py`:

- **Line 1634-1648**: `resume_plan_after_approval` 用 `asyncio.create_task` 启动两个后台任务：
  - `_generate_tasks_after_approval` — 生成计划任务
  - `_capture_plan_goal_memory` — 捕获目标记忆
  - 两个 task 均无 try/except 包裹，失败时异常被 asyncio 静默吞噬

- **Line 1917-1924**: `trigger_replanning` 用 `asyncio.create_task` 启动 `_execute_replan_action`（重新规划执行），同样无错误处理

- **Line 1650-1655**: 函数返回 `{"status": "success", "message": "Plan approved and task generation initiated"}` — 即使后台 task 稍后失败，用户看到的仍是"成功"

## Impact

- 用户批准计划后，任务可能永远不生成（execution core 断裂）
- 目标记忆可能永远不捕获（cognitive core 数据缺失）
- 重新规划可能静默失败，用户以为方案已更新但实际未执行
- 无任何日志或通知告知用户/开发者失败

## Suggested Fix

为每个 `asyncio.create_task` 添加错误处理 wrapper：

```python
async def _safe_task(coro, task_name: str):
    try:
        await coro
    except Exception as e:
        logger.error(f"Background task {task_name} failed: {e}", exc_info=True)
        # 可选：发布 event_bus 事件通知前端

asyncio.create_task(_safe_task(self._generate_tasks_after_approval(...), "generate_tasks"))
```

## [Fix] 复核结论
disputed — Auditor claims "两个 task 均无 try/except 包裹，失败时异常被 asyncio 静默吞噬" and "无任何日志或通知告知用户/开发者失败"，这是不准确的。

### 独立反证证据

1. **`_generate_tasks_after_approval` 已有 try/except**: plan_review_service.py:1741-1801 整体包裹在 `try/except Exception as e` 中，失败时调用 `logger.error(f"Error in _generate_tasks_after_approval: {e}", exc_info=True)`（line 1800-1801）

2. **`_capture_plan_goal_memory` 已有两层 try/except**: line 1670-1675 捕获 `ValueError`（UUID 解析），line 1677-1709 捕获 `Exception` 并 `logger.warning(...)` (line 1708-1709)

3. **`_execute_replan_action` 已有 try/except + SSE 通知**: line 1974-2090 整体包裹在 `try/except Exception` 中，不仅有 `logger.error(..., exc_info=True)`（line 2076-2077），还通过 `sse_manager.send_to_user(user_id, "plan_replan_failed", ...)` 主动通知用户（line 2078-2088）

### 剩余的真实差距（P2 级别，非 P1）

1. `_generate_tasks_after_approval` 失败时只写 server log，没有向用户发送 SSE 通知（但错误确实被记录了，运维可见）
2. `_capture_plan_goal_memory` 使用 `logger.warning` 而非 `logger.error`，对认知核心数据丢失可能需要更高日志级别
3. 函数在后台任务完成前返回 "success" — 这是合理的异步设计（任务确实已启动），但用户不被告知后续失败

### 建议处置

- **降级为 P2**：错误处理已存在（server-side logging），只是缺少用户侧通知
- 不建议在 P1 修复中改动——这些 background task 的内部错误处理模式一致且合理
- 若 Verifier 认为需要改进，建议在 `_generate_tasks_after_approval` 的 except 块中添加 SSE 通知
