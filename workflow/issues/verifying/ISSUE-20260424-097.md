## Title

Leaderboard _get_global_leaderboard loads ALL active users into Python memory for scoring, unbounded OOM risk

## Evidence

`backend/app/services/leaderboard_service.py:209-232`:

```python
query = select(
    User.id, User.username, User.avatar_url,
    func.count(UserNodeStatus.user_id).label('node_count'),
    func.count(UserAchievement.id).label('achievement_count'),
    func.coalesce(UserStreakStats.longest_streak, 0).label('streak'),
    func.coalesce(UserStreakStats.total_checkin_days, 0).label('study_days')
).outerjoin(...).where(User.is_active, User.not_deleted_filter())
.group_by(...)

result = await self.db.execute(query)
rows = result.all()  # <-- ALL users loaded into Python

# Python-side scoring loop
scored_users = []
for row in rows:
    score = (row.node_count * 1.0 + row.study_days * 0.5 + ...)
    scored_users.append((row, score))
scored_users.sort(key=lambda x: x[1], reverse=True)
```

The `limit` parameter (line 249) only truncates AFTER loading and sorting all users. With 10K users, this loads 10K rows + creates 10K tuples + sorts them, all in Python. The `get_summary` method (line 156-196) calls this 4 times sequentially (global, friends, weekly, streak).

Same pattern applies to `_get_friends_leaderboard` (line 291), `_get_weekly_leaderboard`, `_get_streak_leaderboard`, and all other leaderboard type methods.

## Impact

Each leaderboard request loads all active users into memory. `get_summary` does this 4x sequentially. Under concurrent requests, this multiplies. Production OOM risk scales linearly with user count.

## Fix Direction

Move scoring computation into the SQL query using `func.sum` / arithmetic expressions with `ORDER BY score DESC LIMIT N`. Eliminate Python-side loading of all rows.
